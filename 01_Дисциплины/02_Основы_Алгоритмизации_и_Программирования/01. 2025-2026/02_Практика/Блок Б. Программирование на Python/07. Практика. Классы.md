# 07. Практика. Классы

> [!abstract] О чём эта практика
> Три задачи по лекции [[16. Объектно-ориентированное программирование]]: свой класс
> с проверкой данных, класс данных с вычисляемыми свойствами и маленькая система
> из двух классов — «книга» и «каталог».
>
> Правило этой практики простое: **данные проверяются там, где создаётся объект**. Если
> объект существует, значит его данные корректны — и об этом больше не нужно думать
> в каждой функции.

> [!important] Как работать с задачей
> 1. Прочитай условие и **не открывай разбор**.
> 2. Напиши класс и создай два-три объекта: правильных и заведомо неправильный — чтобы
>    увидеть, как срабатывает проверка.
> 3. Помни: вычисляемые величины (площадь, периметр) — это `@property`, а не методы
>    с пустыми скобками.
> 4. Сверься с разбором.
>
> Общий чек-лист — в [[00. Обзор практик блока Б]].

## Задача 1. Класс «Прямоугольник»

★☆☆ · класс, `__init__`, проверка данных, `@property`, `__str__`

**Условие.** Нужен класс `Rectangle` — прямоугольник с длинами сторон. Требования:

- стороны задаются при создании объекта и должны быть положительными;
- площадь и периметр — вычисляемые величины, а не отдельные поля;
- `print(rectangle)` печатает понятную строку, а не непонятный адрес объекта.

**Задание.** 1) Напиши класс. 2) Создай объект со сторонами `3` и `4` и выведи его,
а также площадь и периметр. 3) Попробуй создать прямоугольник со стороной `−1` и обработай
ошибку через `try` / `except`. 4) Объясни, почему `rect.area` — без скобок.

> [!example]- Разбор
> **Идея.** Площадь и периметр не хранятся, а вычисляются из сторон: если хранить их
> отдельными полями, при изменении стороны придётся не забыть обновить три места.
> `@property` ([[16. Объектно-ориентированное программирование]]) делает вычисляемую
> величину похожей на атрибут — обращение без скобок.
>
> **Код.**
>
> ```python
> class Rectangle:
>     """Прямоугольник с проверкой сторон и вычисляемыми свойствами."""
>
>     def __init__(self, width, height):
>         if width <= 0 or height <= 0:
>             raise ValueError("стороны должны быть положительными")
>         self.width = width
>         self.height = height
>
>     @property
>     def area(self):
>         """Площадь."""
>         return self.width * self.height
>
>     @property
>     def perimeter(self):
>         """Периметр."""
>         return 2 * (self.width + self.height)
>
>     def __str__(self):
>         return f"Прямоугольник {self.width}×{self.height}"
>
>
> rect = Rectangle(3, 4)
> print(rect)
> print(f"Площадь: {rect.area}")
> print(f"Периметр: {rect.perimeter}")
>
> try:
>     bad = Rectangle(-1, 5)
> except ValueError as error:
>     print(f"Ошибка: {error}")
> ```
>
> **Пример запуска**:
>
> ```text
> Прямоугольник 3×4
> Площадь: 12
> Периметр: 14
> Ошибка: стороны должны быть положительными
> ```
>
> **Что здесь важно.** Проверка стоит в `__init__`: объект с отрицательной стороной создать
> нельзя в принципе. `raise ValueError` — тот же способ сообщить об ошибке, что и у `int()`,
> знакомого по [[05. Язык Python - идентификаторы, операторы, типы данных]]: вызывающий код
> может это перехватить.
>
> **Типичная ошибка.** Считать площадь отдельным полем (`self.area = width * height`)
> и потом менять сторону: площадь останется старой. Вычисляемые величины описывают формулой,
> а не запоминают.
>
> **Граница.** Нулевая сторона — тоже ошибка: прямоугольника с нулевой стороной не бывает,
> поэтому проверка `<= 0`, а не `< 0`. Имя ошибки при этом остаётся понятным: `ValueError`
> с текстом «стороны должны быть положительными».

## Задача 2. Класс «Треугольник»

★★☆ · `@dataclass`, `__post_init__`, `@property`, формула Герона

**Условие.** Нужен класс `Triangle`, заданный длинами сторон `a`, `b`, `c`:

- стороны хранятся как поля класса данных (`@dataclass`);
- при создании объекта проверяется, что стороны положительные и что треугольник
  с такими сторонами существует (неравенство треугольника);
- периметр, площадь (по формуле Герона) и высоты — вычисляемые свойства;
- `print(triangle)` печатает название фигуры и стороны.

**Задание.** 1) Напиши класс. 2) Проверь на сторонах `3, 4, 5`: площадь должна быть `6.0`,
периметр — `12`, высоты — `4`, `3` и `2.4`. 3) Попробуй создать треугольник `1, 2, 10` и объясни, какая проверка сработала. 4) Почему удобно отсортировать стороны в начале?

> [!example]- Разбор
> **Идея.** `@dataclass` сам пишет `__init__`, `__repr__` и `__eq__` по полям, а вся
> «умная» часть собирается в `__post_init__`: это метод, который выполняется сразу после
> создания объекта. Так проверка оказывается в одном месте, и объект «неправильного»
> треугольника не существует.
>
> **Код.**
>
> ```python
> import math
> from dataclasses import dataclass
>
>
> @dataclass
> class Triangle:
>     """Треугольник, заданный длинами сторон."""
>
>     a: float
>     b: float
>     c: float
>
>     def __post_init__(self):
>         self.sides = sorted((self.a, self.b, self.c))
>         if self.sides[0] <= 0:
>             raise ValueError("стороны должны быть положительными")
>         if self.sides[0] + self.sides[1] <= self.sides[2]:
>             raise ValueError("треугольник с такими сторонами не существует")
>
>     @property
>     def perimeter(self):
>         """Периметр."""
>         return self.a + self.b + self.c
>
>     @property
>     def area(self):
>         """Площадь по формуле Герона."""
>         half = self.perimeter / 2
>         return math.sqrt(half * (half - self.a) * (half - self.b) * (half - self.c))
>
>     @property
>     def heights(self):
>         """Высоты к сторонам a, b, c."""
>         return (2 * self.area / self.a, 2 * self.area / self.b, 2 * self.area / self.c)
>
>     def __str__(self):
>         return f"Треугольник {self.a}×{self.b}×{self.c}"
>
>
> triangle = Triangle(3, 4, 5)
> print(triangle)
> print(f"Периметр: {triangle.perimeter}")
> print(f"Площадь: {triangle.area}")
> to_a, to_b, to_c = triangle.heights
> print(f"Высоты: {to_a:.4f}, {to_b:.4f}, {to_c:.4f}")
>
> try:
>     bad = Triangle(1, 2, 10)
> except ValueError as error:
>     print(f"Ошибка: {error}")
> ```
>
> **Пример запуска**:
>
> ```text
> Треугольник 3×4×5
> Периметр: 12
> Площадь: 6.0
> Высоты: 4.0000, 3.0000, 2.4000
> Ошибка: треугольник с такими сторонами не существует
> ```
>
> **Что здесь важно.** Запись `to_a, to_b, to_c = triangle.heights` — распаковка: три значения
> свойства раскладываются по трём переменным ([[11. Кортежи, списки, словари]]).
> Сортировка сторон делает проверку неравенства треугольника простой:
> после сортировки достаточно сравнить сумму двух меньших сторон с самой большой. Без
> сортировки пришлось бы проверять три пары. Это приём из [[11. Кортежи, списки, словари]]:
> `sorted` возвращает **новый** список, а исходные атрибуты остаются на месте.
>
> **Типичная ошибка.** Проверять неравенство треугольника уже после вычисления площади:
> под корнем формулы Герона окажется отрицательное число, и программа упадёт с
> `ValueError: math domain error` — сообщение непонятное, а причина не в математике,
> а в данных. Проверки ставят **до** расчётов.
>
> **Граница.** «Вырожденный» треугольник, где сумма двух сторон точно равна третьей
> (например, `1, 2, 3`), не существует: три точки лягут на одну прямую. Поэтому в проверке
> стоит `<=`, а не `<`. Обрати внимание на `area` и `heights`: они вычисляются заново
> при каждом обращении — значит, всегда соответствуют текущим сторонам.

## Задача 3. «Книга» и «Каталог»

★★★ · два класса, список объектов, поиск, свойство-статистика

**Условие.** Нужны два класса:

- `Book` — книга: название, автор, число страниц; страницы должны быть положительными;
- `Catalog` — каталог книг: добавление книги, поиск всех книг заданного автора, среднее
  число страниц.

Также `print(book)` должен печатать книгу в читаемом виде.

**Задание.** 1) Напиши оба класса. 2) Добавь в каталог три книги и выведи количество книг,
среднее число страниц и список книг Тургенева. 3) Проверь каталог без книг: что вернёт
среднее число страниц? 4) Объясни, почему `Catalog` не должен сам создавать книги.

> [!example]- Разбор
> **Идея.** Два класса работают вместе: `Catalog` хранит **список объектов** `Book`,
> но ничего не знает о том, откуда книги берутся. Книга попадает в каталог методом `add` —
> так каталог можно наполнить из файла, из ввода или вручную, не меняя его код. Это первый
> шаг к тому, что в больших проектах называют внедрением зависимостей.
>
> **Код.**
>
> ```python
> class Book:
>     """Книга: название, автор, число страниц."""
>
>     def __init__(self, title, author, pages):
>         if pages <= 0:
>             raise ValueError("число страниц должно быть положительным")
>         self.title = title
>         self.author = author
>         self.pages = pages
>
>     def __str__(self):
>         return f"«{self.title}» — {self.author}, {self.pages} с."
>
>
> class Catalog:
>     """Каталог книг: добавление, поиск по автору, статистика."""
>
>     def __init__(self):
>         self.books = []
>
>     def add(self, book):
>         """Добавляет книгу в каталог."""
>         self.books.append(book)
>
>     def by_author(self, author):
>         """Список книг указанного автора."""
>         found = []
>         for book in self.books:
>             if book.author == author:
>                 found.append(book)
>         return found
>
>     @property
>     def average_pages(self):
>         """Среднее число страниц; 0, если каталог пуст."""
>         if len(self.books) == 0:
>             return 0.0
>         total = 0
>         for book in self.books:
>             total += book.pages
>         return total / len(self.books)
>
>
> catalog = Catalog()
> catalog.add(Book("Муму", "Тургенев", 96))
> catalog.add(Book("Отцы и дети", "Тургенев", 288))
> catalog.add(Book("Преступление и наказание", "Достоевский", 672))
>
> print(f"Книг в каталоге: {len(catalog.books)}")
> print(f"Среднее число страниц: {catalog.average_pages:.1f}")
> print("Книги Тургенева:")
> for book in catalog.by_author("Тургенев"):
>     print(f"  {book}")
> ```
>
> **Пример запуска**:
>
> ```text
> Книг в каталоге: 3
> Среднее число страниц: 352.0
> Книги Тургенева:
>   «Муму» — Тургенев, 96 с.
>   «Отцы и дети» — Тургенев, 288 с.
> ```
>
> **Что здесь важно.** Один объект внутри другого — обычное дело: каталог хранит книги,
> а поиск по автору просто перебирает список и сравнивает поля. Обрати внимание, как
> в `by_author` работает `book.author`: у каждого объекта свои данные.
>
> **Типичная ошибка.** Сделать `by_author` методом класса `Book` («список всех книг автора»
> в одной книге) — тогда книга должна знать про остальные книги, чего быть не должно.
> Каталог — то место, где живёт список; книга отвечает только за себя.
>
> **Граница.** Пустой каталог: среднее число страниц — `0.0`, потому что делить на ноль
> нельзя, а возвращать `None` и потом форматировать его в `main.py` неудобно.
> Для реального проекта это спорное решение — `None` честнее, — но здесь важнее показать
> саму проверку «а есть ли данные».
>
> **Что дальше.** Такие классы ложатся в основу проекта: в Django модель — это почти
> то же самое, только данные хранятся не в списке, а в базе данных.
