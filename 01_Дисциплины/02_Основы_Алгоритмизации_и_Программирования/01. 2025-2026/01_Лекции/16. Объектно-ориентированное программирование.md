# 16. Объектно-ориентированное программирование

> [!abstract] О чём эта лекция
> Последняя тема курса. До сих пор данные и действия жили отдельно: список значений — сам
> по себе, функции — сами по себе. **Объектно-ориентированное программирование (ООП)** соединяет
> их: класс описывает, **какие данные** есть у сущности и **что она умеет**.
>
> **Зачем это нужно.** Чем больше программа, тем важнее, чтобы её части собирались в понятные
> сущности: не «словарь со строкой, числом и флагом», а `Book` с полями и поведением. Django,
> к которому ведёт курс, целиком построен на объектах: модель — класс, представление — метод,
> форма — класс. Здесь разбирается самое нужное: класс и объект, инкапсуляция, наследование,
> `@property` и классы данных.
>
> **Что ты должен уметь после лекции:** описать сущность классом; создавать объекты с проверкой
> данных при создании; сделать вычисляемое свойство через `@property`; использовать наследование
> и `super()` там, где оно уместно; собрать класс данных через `@dataclass`; объяснить, зачем
> нужно `__str__`.
>
> **Куда идти дальше:** инженерный модуль (тесты, типизация, инструменты), затем Django.

> [!tip] Что нужно знать заранее
> [[11. Кортежи, списки, словари]] (словарь — «предшественник» объекта),
> [[14. Функции и модули]] (метод — функция внутри класса), [[15. Работа с файлами]] (`__post_init__`
> и JSON удобно соединяются), [[08. Разветвляющийся алгоритм]] (проверка значений).

# Зачем класс, если есть словарь

Данные о книге можно хранить словарём:

```python
book = {"title": "Мастер и Маргарита", "author": "Булгаков", "pages": 480}
print(book["title"])
```

Работает, но у словаря есть слабые места:

- **опечатка в ключе** обнаружится только при выполнении: `book["titel"]` → `KeyError`;
- **никто не проверяет данные**: `book["pages"] = -10` пройдёт молча;
- **поведение снаружи**. Книга «умеет» выдавать краткое описание? Это функция в другом месте:
  `short_info(book)`. Логика живёт отдельно от данных, и её легко потерять.

**Класс** решает это: описывает, какие поля есть у сущности и какие действия с ней возможны.

```python
class Book:
    """Книга: данные и короткое описание."""

    def __init__(self, title, author, pages):
        self.title = title
        self.author = author
        self.pages = pages

    def short_info(self):
        """Возвращает строку для списка литературы."""
        return f"{self.author}. {self.title} — {self.pages} с."


book = Book("Мастер и Маргарита", "Булгаков", 480)
print(book.short_info())          # Булгаков. Мастер и Маргарита — 480 с.
```

# Класс и объект

| Термин | Что это |
|---|---|
| **Класс** | описание: какие данные есть у сущности и что она умеет |
| **Объект (экземпляр)** | конкретная сущность, созданная по этому описанию |
| **`__init__`** | метод, который выполняется при создании объекта и заполняет его данными |
| **`self`** | ссылка на сам объект: через него методы видят его данные |
| **Атрибут** | «поле» объекта: переменная внутри него (`self.title`) |
| **Метод** | функция внутри класса, работающая с атрибутами объекта |

```python
class Book:
    def __init__(self, title, author, pages):
        self.title = title            # атрибуты объекта
        self.author = author
        self.pages = pages

    def is_long(self):                # метод
        return self.pages > 300


first = Book("Мастер и Маргарита", "Булгаков", 480)
second = Book("Муму", "Тургенев", 96)

print(first.is_long())        # True
print(second.is_long())       # False
print(first.title)            # Мастер и Маргарита
```

> [!important] `self` — это «этот объект»
> `self.pages = pages` читается как «положить в поле `pages` **этого объекта** значение `pages`».
> Методы всегда начинаются с `self`, а при вызове его не передают: `first.is_long()` — Python
> сам подставит `first` вместо `self`.

# Инкапсуляция: что наружу, что внутрь

**Инкапсуляция** — принцип «внутренние детали скрыты, наружу видно только нужное». В Python она
держится на соглашениях, а не на запретах:

| Запись | Смысл | Как относиться |
|---|---|---|
| `self.pages` | открытый атрибут | можно читать и менять снаружи |
| `self._cache` | защищённый, «одно подчёркивание» | «внутреннее: снаружи не трогать без необходимости» |
| `self.__secret` | приватный, «два подчёркивания» | Python затрудняет доступ извне, но не запрещает |

Главное — не сами подчёркивания, а идея: **данные меняют через понятные операции, а не наугад**.
Если цену нельзя сделать отрицательной, это должно быть нельзя и через атрибут.

# `@property`: вычисляемые свойства и проверка при изменении

**Декоратор** — «обёртка», которая добавляет функции дополнительное поведение.
`@property` превращает метод в «атрибут только для чтения»: снаружи это выглядит как обычное
поле, а внутри — вызов кода.

```python
class Circle:
    """Круг: радиус и вычисляемые свойства."""

    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        """Площадь круга — считается при обращении."""
        return 3.14159 * self.radius ** 2

    @property
    def diameter(self):
        """Диаметр круга."""
        return self.radius * 2


circle = Circle(2)
print(circle.area)       # 12.56636 — без скобок: выглядит как атрибут
```

Проверка при установке значения — через сеттер:

```python
class Circle:
    """Круг с проверкой радиуса."""

    def __init__(self, radius):
        self.radius = radius          # идёт через сеттер ниже

    @property
    def radius(self):
        """Радиус круга."""
        return self._radius

    @radius.setter
    def radius(self, value):
        if value <= 0:
            raise ValueError("радиус должен быть больше нуля")
        self._radius = value


circle = Circle(2)                # ок
# circle.radius = -5              # ValueError: радиус должен быть больше нуля
```

Теперь неверные данные в объект не попадут — и это гарантия на уровне класса, а не надежда
на дисциплину того, кто им пользуется.

> [!note] Про `raise` и свои ошибки
> `raise` — «поднять ошибку вручную»: программа останавливается с понятным сообщением вместо
> того, чтобы молча работать с неправильными данными. Здесь используется готовая ошибка
> `ValueError` — она знакома по [[05. Язык Python - идентификаторы, операторы, типы данных]].
> **Свои** классы ошибок — тема инженерного модуля: там видно, зачем заводить собственную
> ошибку вместо готовой.

# Наследование, полиморфизм, `super()`

**Наследование** — создание нового класса на основе существующего: дочерний получает атрибуты
и методы родителя.

```python
class EBook(Book):
    """Электронная книга: всё как у книги, плюс размер файла."""

    def __init__(self, title, author, pages, file_size):
        super().__init__(title, author, pages)      # настройки родителя — его же кодом
        self.file_size = file_size

    def short_info(self):
        """Возвращает строку для списка литературы с размером файла."""
        base = super().short_info()
        return f"{base} ({self.file_size} МБ)"


digital = EBook("Питон для всех", "Иванов", 200, 4)
print(digital.short_info())          # Иванов. Питон для всех — 200 с. (4 МБ)
```

- `super().__init__(...)` вызывает конструктор родителя — не нужно повторять присваивание полей;
- **полиморфизм** — «один и тот же метод у разных классов работает по-своему»: `short_info()`
  у `Book` и `EBook` называется одинаково, но выдаёт разное. Код, который вызывает
  `book.short_info()`, работает с обоими.

> [!warning] Наследование — не всегда решение
> Наследование уместно, когда «дочерний класс **является** родительским»: электронная книга —
> книга. Если связь «имеет» (у книги есть издательство, а не «книга — это издательство»),
> нужен не наследник, а отдельный класс или поле. Лишнее наследование запутывает сильнее
> копипаста.

# Специальные методы: как объект выглядит снаружи

**Специальные методы** — имена в двойных подчёркиваниях (`__str__`, `__eq__`, `__len__`).
Они позволяют объекту «подружиться» с привычными действиями: печатью, сравнением, `len()`.

```python
class Book:
    """Книга с читаемым выводом и сравнением по названию."""

    def __init__(self, title, author, pages):
        self.title = title
        self.author = author
        self.pages = pages

    def __str__(self):
        return f"«{self.title}», {self.author}, {self.pages} с."

    def __repr__(self):
        return f"Book({self.title!r}, {self.author!r}, {self.pages})"

    def __eq__(self, other):
        if not isinstance(other, Book):
            return NotImplemented
        return self.title == other.title and self.author == other.author


book = Book("Муму", "Тургенев", 96)
print(book)                      # «Муму», Тургенев, 96 с. — сработал __str__
print(book == Book("Муму", "Тургенев", 96))     # True — сработал __eq__
```

| Метод | Зачем |
|---|---|
| `__init__` | создание объекта |
| `__str__` | «красивый» текст для человека: `print(book)` |
| `__repr__` | «точная» запись для отладки: как объект создать заново |
| `__eq__` | сравнение двух объектов (`==`) |
| `__len__` | что вернёт `len(obj)` |
| `__add__` | что делает `obj + other` |

`!r` в `__repr__` показывает значение так, как его записали бы в коде: строки — в кавычках.
Без него получится `Book(Муму, Тургенев, 96)` — такую запись нельзя скопировать и запустить.

# Атрибуты класса, `@classmethod`, `@staticmethod`

```python
class Book:
    """Книга с фабрикой из словаря и вспомогательной проверкой."""

    species = "печатное издание"          # атрибут класса: общий для всех объектов

    def __init__(self, title, pages):
        self.title = title
        self.pages = pages

    @classmethod
    def from_dict(cls, data):
        """Создаёт книгу из словаря — например, прочитанного из JSON."""
        return cls(data["title"], data["pages"])

    @staticmethod
    def is_title_valid(title):
        """Проверяет, что название не пустое."""
        return bool(title and title.strip())


book = Book.from_dict({"title": "Муму", "pages": 96})
print(book.species)                          # печатное издание
print(Book.is_title_valid(""))               # False
```

| Что | Отличие | Когда применять |
|---|---|---|
| обычный метод | принимает `self` | работает с данными объекта |
| `@classmethod` | принимает `cls` — сам класс | создать объект другим способом: из JSON, из строки |
| `@staticmethod` | не принимает ни `self`, ни `cls` | вспомогательная проверка, логически связанная с классом |
| атрибут класса | общий для всех объектов | версия, единица измерения, вид |

# Классы данных: `@dataclass`

Большинство классов нужны только для хранения данных. Для них есть готовый декоратор:

```python
from dataclasses import dataclass, field


@dataclass
class Student:
    """Студент с оценками и вычисляемым средним баллом."""

    name: str
    group: str
    scores: list = field(default_factory=list)

    def __post_init__(self):
        """Проверяет данные сразу после создания объекта."""
        if not self.name.strip():
            raise ValueError("имя не может быть пустым")

    @property
    def average(self):
        """Средний балл; 0, если оценок нет."""
        if not self.scores:
            return 0.0
        return sum(self.scores) / len(self.scores)


student = Student("Аня", "П-21", [5, 4, 5])
print(student.average)          # 4.666666666666667
print(student)                  # Student(name='Аня', group='П-21', scores=[5, 4, 5])
```

> [!note] Аннотации у полей: `name: str`
> Поля класса данных записывают с **аннотацией типа** — `name: str`, «здесь будет строка».
> Интерпретатор её не проверяет: это подсказка человеку и редактору, а `@dataclass` по этим
> записям понимает, какие у объекта поля. Типизация подробно разбирается в инженерном модуле;
> пока достаточно читать `имя: тип` как «поле такого-то типа».

Что даёт `@dataclass`:

- автоматически создаёт `__init__`, `__repr__` и `__eq__` по списку полей — не нужно писать
  одно и то же в каждом классе;
- `__post_init__` — проверка и вычисления сразу после создания объекта;
- `field(default_factory=list)` — правильный способ задать «пустой список по умолчанию»
  (та же ловушка изменяемого значения, что и в [[14. Функции и модули]]).

> [!note] Проверка типа в `__eq__` (продвинутое)
> `isinstance(other, Book)` спрашивает «это тоже книга?», а `NotImplemented` — служебный ответ
> «с таким объектом я сравнивать не умею»: Python попробует сравнить по-своему. Без этой проверки
> `book == "текст"` падал бы с ошибкой вместо того, чтобы вернуть `False`. Подробно — в инженерном
> модуле; пока запомни смысл: сравнение с объектом другого типа — не ошибка.

> [!note] Дескрипторы и абстрактные классы (продвинутое)
> **Дескриптор** — объект, перехватывающий доступ к атрибуту; `@property` — самый известный
> его пример. **Абстрактный класс** — класс-шаблон, который нельзя создать напрямую: он задаёт
> обязательные методы, а реализуют их наследники (модуль `abc`). Оба инструмента встречаются
> в библиотеках и в больших проектах; подробно они разбираются в инженерном модуле. Пока
> достаточно понимать, что это про «единый интерфейс» и «контроль доступа».

# Как это делают в проекте

**Привычка 1. Класс отвечает за одну сущность.** Если в классе живут «книга и ещё немного
читатель», это два класса. Один класс — одна ответственность: так проще читать и менять.

**Привычка 2. Данные проверяют при создании.** `__init__` или `__post_init__` — то место,
где объект с неверными данными просто не появится. Это лучше, чем проверять каждое поле
в каждом месте использования.

**Привычка 3. Хранилище — `@dataclass`, поведение — обычный класс.** Если класс только держит
данные, `@dataclass` избавит от лишнего кода.

**Привычка 4. `__str__` — для человека.** Печать объекта без него показывает что-то вроде
`<Book object at 0x…>`; с ним — понятную строку.

**Привычка 5. Наследование — только для «является».** Электронная книга является книгой —
можно. «Книга является каталогом» — нет: это два разных класса, связанных полем.

**Привычка 6. Приватное — по соглашению.** `_name` и `__name` сообщают читателю «внутреннее».
Если очень нужно дать доступ — лучше сделать `@property`, а не открывать поле наугад.

# Ключевые термины

| Термин | Определение |
|---|---|
| **ООП** | подход, при котором данные и действия объединены в объекты |
| **Класс** | описание сущности: какие данные и какие действия |
| **Объект (экземпляр)** | конкретная сущность, созданная по классу |
| **Атрибут** | поле объекта (`self.title`) |
| **Метод** | функция внутри класса, работающая с объектом |
| **`__init__`** | конструктор: выполняется при создании объекта |
| **`self`** | ссылка на текущий объект |
| **Инкапсуляция** | скрытие внутренних деталей; в Python — по соглашению (`_`, `__`) |
| **Наследование** | класс-наследник получает поля и методы родителя |
| **`super()`** | доступ к методам родительского класса |
| **Полиморфизм** | один и тот же метод у разных классов работает по-своему |
| **Специальные методы** | `__str__`, `__eq__`, `__len__` и другие: «встраивают» объект в язык |
| **`@property`** | делает метод похожим на атрибут; используется для вычислений и проверок |
| **`@dataclass`** | декоратор: автоматически создаёт `__init__`, `__repr__`, `__eq__` по полям |
| **`__post_init__`** | метод, выполняющийся после `__init__` у `@dataclass`: проверки, вычисления |
| **`raise`** | поднять ошибку вручную: остановить программу с понятным сообщением |
| **Аннотация типа** | запись «какой тип ожидается»: `name: str`; интерпретатор её не проверяет |

# Типичные заблуждения

- ❌ **«ООП — это обязательно сложно».** Минимальный класс — три строки: данные и один метод.
  Начинать стоит с самого простого класса, а не с иерархии из пяти уровней.
- ❌ **«Класс нужен для всего».** Для «найти максимум в списке» класс не нужен — это функция.
  Класс уместен, когда есть сущность, у которой данные и поведение связаны.
- ❌ **«`self` — это какое-то ключевое слово».** Это обычный параметр, просто с обязательным
  первым местом в методе; вместо `self` можно написать другое имя, но так никто не делает.
- ❌ **«`_` и `__` — защита от доступа».** Это соглашение и (для `__`) лёгкое «запутывание» имени.
  Смысл в договорённости: внутренние поля не трогают снаружи.
- ❌ **«Наследование экономит код, значит, его надо применять шире».** Наследование — сильная
  связь: изменение родителя ломает наследников. Его применяют для отношений «является»,
  а «имеет» — это поле.
- ❌ **«`self.pages` и `pages` — одно и то же».** `pages` — локальное имя внутри метода,
  `self.pages` — поле объекта, которое останется после выхода из метода.
- ❌ **«`@dataclass` — просто синтаксический сахар без последствий».** Декоратор меняет
  поведение: например, сравнение объектов идёт по полям, а `__str__` показывает поля.
  Это ровно то, что нужно для классов-хранилищ, но не для классов со сложным поведением.
- ❌ **«Изменяемое значение по умолчанию в `@dataclass` — можно».** Нельзя, как и в функциях:
  нужен `field(default_factory=list)`.

# Проверь себя

1. Чем класс отличается от объекта?
2. Зачем нужен `self` и что произойдёт без него?
3. Что даёт `@property` и когда он особенно полезен?
4. Когда наследование уместно, а когда лучше обойтись полем?
5. Что автоматически создаёт `@dataclass` и что в нём делает `__post_init__`?
6. Зачем нужен `__str__` и чем он отличается от `__repr__`?

> [!example]- Ответы
> 1. **Класс** — описание: какие данные будут и что объект умеет. **Объект** — конкретная
>    сущность, созданная по этому описанию: у неё свои значения полей. Класс один, объектов
>    по нему можно создать сколько угодно.
> 2. `self` — ссылка на сам объект: через него метод читает и меняет поля именно этого объекта.
>    Без `self` метод не знает, к какому объекту относится (`self.pages` — «поле этого объекта»),
>    и методы с другими именами полей вообще не смогут работать.
> 3. `@property` позволяет обращаться к методу как к атрибуту — без скобок. Особенно полезен
>    для **вычисляемых величин** (площадь, средний балл, длина) и **проверок при установке**
>    значения (сеттер), когда неверные данные не должны попасть в объект.
> 4. Наследование уместно, когда связь «**является**»: электронная книга является книгой,
>    преподаватель является сотрудником. Когда связь «**имеет**» (у книги есть издательство),
>    делают поле или отдельный класс: наследование тут запутает.
> 5. `@dataclass` создаёт `__init__`, `__repr__` и `__eq__` по списку полей — то, что раньше
>    писалось вручную. `__post_init__` выполняется сразу после создания объекта: в нём проверяют
>    данные и вычисляют производные значения.
> 6. `__str__` даёт «человеческую» строку для `print` (`«Муму», Тургенев, 96 с.`),
>    `__repr__` — точную запись для отладки (`Book('Муму', 'Тургенев', 96)`), по которой объект
>    можно воссоздать. Оба полезны: первый — для пользователя, второй — для программиста.
