# 06. Среды разработки и виртуальное окружение

> [!abstract] О чём эта лекция
> Код надо где-то писать и где-то запускать. Эта лекция — про рабочее место программиста:
> VS Code, запуск программы, отладчик и изоляция зависимостей проекта. Как читать ошибки
> и обрабатывать ожидаемые — в [[05. Язык Python - идентификаторы, операторы, типы данных]];
> здесь видно, **где** ошибку искать и как пройти программу по шагам.
>
> **Зачем это нужно.** Три вещи отличают «учебный код в блокноте» от работы: умение **запускать
> проект одной командой**, умение **читать ошибку** и умение **остановить программу и посмотреть,
> что в ней происходит**. А зависимостей со временем становится так много, что без изоляции
> окружений они начинают ломать друг друга.
>
> **Что ты должен уметь после лекции:** открыть папку проекта в VS Code и запустить файл; найти
> ошибку в панели Problems и в терминале; поставить точку останова и пройти программу по шагам,
> наблюдая за переменными; создать окружение через `uv`, добавить зависимость и запустить
> программу командой `uv run`.
>
> **Куда идти дальше:** [[07. Линейный алгоритм]] — первая полноценная программа.

> [!tip] Что нужно знать заранее
> [[05. Язык Python - идентификаторы, операторы, типы данных]] — типы данных, `print`, `input`,
> `import`, чтение сообщений об ошибке. Опыт работы с редакторами и терминалом не требуется:
> все команды разбираются по ходу.

# Что такое среда разработки

**Среда разработки** — программа, в которой пишут код. Она не «учит программировать»
и не заменяет понимание: это удобный инструмент с набором функций, которых нет у обычного
блокнота.

| Функция среды | Зачем она |
|---|---|
| подсветка синтаксиса | служебные слова, строки и числа видны с первого взгляда |
| автодополнение | подсказывает имена, снижает опечатки |
| проверка на лету | подчёркивает явные ошибки ещё до запуска |
| запуск одной кнопкой | не нужно набирать команду в терминале |
| терминал внутри | команды и вывод программы рядом с кодом |
| отладчик | позволяет остановить программу и посмотреть значения переменных |

Бывают **редакторы** (VS Code, Sublime Text) — легче и быстрее, и **IDE** (PyCharm, IDLE) —
больше возможностей «из коробки». В курсе используется **VS Code** с расширением Python:
он бесплатный и настраивается под что угодно.

## Что нужно настроить в VS Code

1. Установить расширение **Python** (`ms-python.python`).
2. Открыть **папку проекта** целиком (`File → Open Folder`), а не отдельный файл: тогда редактор
   видит структуру, находит модули и сам подхватывает окружение. Открытый «просто файл» —
   самая частая причина, почему не работают импорты.
3. Выбрать интерпретатор (`Python: Select Interpreter` → окружение проекта). Признак того, что
   выбран не тот: нет автодополнения, а на установленную библиотеку жалуется `ModuleNotFoundError`.
4. Запускать файл клавишей `F5` или кнопкой ▶.

### Клавиши и панели, которые нужны в первый день

| Что | Как | Зачем |
|---|---|---|
| палитра команд | `Ctrl+Shift+P` | поиск любой команды, включая «Python: Select Interpreter»: не нужно помнить, где она в меню |
| терминал | `` Ctrl+` `` | запустить `python файл.py` руками и увидеть вывод программы и ошибки |
| панель Problems | `Ctrl+Shift+M` | что редактор заметил ещё до запуска |
| запуск | `F5` | выполнить программу |
| точка останова | `F9` | метка на строке: программа дойдёт до неё и остановится |
| шаг | `F10` (через строку), `F11` (внутрь вызова) | пройти программу по одной строке |
| панель Variables | слева, в режиме отладки | значения всех переменных на каждом шаге |

> [!tip] Зачем отладчик, если есть `print`
> `print` показывает значение в одной точке. Отладчик показывает **все** значения сразу и идёт
> по шагам: на циклах из [[09. Циклический алгоритм - цикл for]] это заменяет десяток `print`
> и экономит много времени.

### Настройки проекта — `.vscode/settings.json` и `extensions.json` (базовый уровень: «могу использовать»)

Настройки VS Code живут на **двух уровнях**, и их важно не путать:

| Уровень | Где лежит файл | Действует на | Попадает в репозиторий |
|---|---|---|---|
| Пользовательский (User) | `%APPDATA%\Code\User\settings.json` (Windows), `~/.config/Code/User/settings.json` (Linux) | все проекты сразу | нет |
| Проектный (Workspace) | `.vscode/settings.json` в папке проекта | только этот проект | **да** |

Проектные настройки **перекрывают** пользовательские. Поэтому в репозиторий кладут именно папку
`.vscode/`: тогда у всей группы одинаковые подсказки и одинаковое форматирование, а личные
предпочтения — тема, шрифт, поведение вкладок — остаются в пользовательском файле и никому
не навязываются.

**`.vscode/extensions.json`** — чтобы VS Code сам предложил поставить нужные расширения:

```json
{
  "recommendations": [
    "ms-python.python",
    "ms-python.vscode-pylance",
    "ms-python.vscode-python-envs",
    "ms-python.debugpy",
    "charliermarsh.ruff",
    "ms-toolsai.jupyter",
    "ms-toolsai.jupyter-keymap",
    "ms-toolsai.jupyter-renderers",
    "ms-toolsai.vscode-jupyter-cell-tags",
    "ms-toolsai.vscode-jupyter-slideshow"
  ],
  "unwantedRecommendations": [
    "ms-python.black-formatter",
    "kevinrose.vsc-python-indent",
    "njqdev.vscode-python-typehint"
  ]
}
```

Что здесь что:

- `recommendations` — список расширений, которые VS Code предложит установить при открытии
  папки. Появится окно «Установить рекомендованные?» → `Install` → среда уже подсвечивает
  и форматирует как надо.
- `ms-python.python` — базовое расширение: запуск, интерпретатор, отладка.
- `ms-python.vscode-pylance` — языковой сервер: подсказки, автодополнение, проверка типов.
- `ms-python.vscode-python-envs` — находит виртуальные окружения и показывает, какое выбрано.
  Благодаря ему не нужно вручную прописывать путь к интерпретатору.
- `ms-python.debugpy` — отладчик, тот самый, что запускается по `F5`.
- `charliermarsh.ruff` — форматирование и линтинг одним инструментом.
- `ms-toolsai.jupyter*` — пять расширений для ноутбуков `.ipynb`: сами ноутбуки, горячие
  клавиши, рендер вывода, теги ячеек и режим слайдов. В базовом курсе не обязательны,
  но мешать не будут.
- `unwantedRecommendations` — обратный список: «это **не** предлагать». Здесь
  `ms-python.black-formatter` — VS Code по умолчанию советует его вместе с Python, но в курсе
  форматированием занимается `ruff`, и два форматтера в одном проекте будут спорить.
  Остальные два устарели: их функции давно внутри Pylance.

> [!tip] `black` vs `ruff`
> Раньше форматировали `black`, проверяли `flake8`, типы — `mypy`. Сейчас `ruff` заменяет их
> одним инструментом и работает в 10–100 раз быстрее. В курсе используется `ruff`; `black`
> знать полезно, но ставить отдельно не нужно (источник —
> [документация ruff](https://docs.astral.sh/ruff/)).

Разбор по группам.

**Языковой сервер и типы.**

- `python.languageServer: "Pylance"` — какой движок разбирает код. Pylance даёт подсказки,
  переход к определению и проверку типов.
- `languageServerMode: "full"` — насколько полно Pylance анализирует проект. Бывает `light`
  (экономит память, меньше подсказок), `default` и `full` (все возможности, но тяжелее).
  Для учебных проектов `full` не мешает: код небольшой.
- `typeCheckingMode: "standard"` — строгость проверки типов. Четыре ступени, каждая включает
  все правила предыдущей — они разобраны в таблице ниже.
- `inlayHints.*` — «подсказки-призраки», серый текст прямо в строке кода. `variableTypes`
  показывает выведенный тип переменной, `functionReturnTypes` — тип возврата функции,
  `parameterNames: "literals"` — имена параметров только когда аргумент передан литералом
  (`open(path, mode="r")` понятнее, чем `open(path, "r")`). `callArgumentNames: "off"` —
  не дублировать имена при каждом вызове, иначе код пестрит.

Четыре ступени `typeCheckingMode`, от мягкой к строгой. Каждая включает все правила предыдущей:

| Режим | Что добавляет |
|---|---|
| `off` | только неразрешённые импорты и неопределённые переменные |
| `basic` | частые ошибки: не тот тип аргумента, не тот тип возврата, обращение к `None` |
| `standard` | плюс несовместимые переопределения методов и «возможно, переменная не присвоена» |
| `strict` | плюс «тип неизвестен» на всё подряд — требует аннотаций везде |

`standard` — разумный потолок для курса: ловит настоящие ошибки, но не заваливает
предупреждениями на каждой строке. `strict` включают в больших проектах с полной типизацией.

**Форматирование.**

- Блок `[python]` — настройки **только** для файлов `.py`. Так в одном проекте Python
  форматирует `ruff`, а JSON и Markdown — `prettier`.
- `editor.formatOnSave` — файл приводится в порядок при сохранении; не нужно помнить команду.
- `codeActionsOnSave` — при сохранении `ruff` сортирует импорты
  (`source.organizeImports.ruff`) и чинит то, что чинится автоматически (`source.fixAll.ruff`).
  Значение `"explicit"` значит «только когда сохранил сам», а не при автосохранении.
- `ruff.organizeImports: true` — включает сортировку импортов как отдельное действие.

**Тесты.** `python.testing.pytestEnabled` — VS Code ищет тесты через `pytest` и показывает их
в отдельной панели: можно запускать один тест мышкой, не набирая команду. `unittestEnabled: false`
— встроенный `unittest` выключен, чтобы два механизма не путались.
`autoTestDiscoverOnSaveEnabled` — новый тест находится сразу после сохранения файла.

**Вид редактора.**

- `editor.rulers: [100]` — вертикальная линия на 100-м символе: видно, когда строка
  становится слишком длинной.
- `editor.wordWrap: "off"` — длинные строки уходят за экран, а не переносятся. Для кода это
  правильно: перенос ломает представление об отступах, а в Python отступы — часть синтаксиса.
- `files.exclude` и `search.exclude` — прячут `__pycache__`, `.venv` и кэши из дерева файлов
  и из поиска. Без этого в проводнике тонет полезный код, а поиск находит совпадения внутри
  виртуального окружения.
- `errorLens.messageMaxChars: 80` — текст ошибки прямо в строке кода обрезается до 80 символов,
  чтобы не перекрывать половину экрана.

> [!warning] Линейка на 100, а `ruff` режет на 88
> `editor.rulers: [100]` рисует линию на 100-м символе, но `ruff` по умолчанию считает пределом
> **88** (проверено на ruff 0.16.10: `linter.line_length = 88`). Это не ошибка, а два разных
> соглашения. Если хочется, чтобы они совпадали, либо ставят `"editor.rulers": [88]`,
> либо поднимают предел в `pyproject.toml`:
>
> ```toml
> [tool.ruff]
> line-length = 100
> ```
>
> 88 — это длина строки, которую `black` выбрал когда-то вместо 79 из PEP 8, и `ruff format`
> унаследовал её по умолчанию.

> [!note] Для продвинутого — `launch.json`
> Конфигурации запуска (`python --module`, аргументы, env) разбираются в инженерном модуле:
> там `launch.json` привязывают к тестам и зависимостям. Для базового уровня достаточно `F5`
> и `uv run`.

**Что стоит взять из пользовательских настроек.** Проектный конфиг намеренно короткий — в него
кладут только то, что обязательно для всей группы. Личные удобства настраиваются один раз
в пользовательском `settings.json` и дальше работают во всех проектах:

| Настройка | Что даёт |
|---|---|
| `"editor.fontFamily": "Fira Code"` + `"editor.fontLigatures": true` | моноширинный шрифт со шрифтовыми лигатурами: `!=`, `<=`, `->` сливаются в один знак |
| `"editor.renderWhitespace": "all"` | пробелы и табы видны как точки — в Python это спасает, когда отступ «съехал» |
| `"editor.bracketPairColorization.enabled": true` | парные скобки подсвечены одним цветом: сразу видно, где закрывается блок |
| `"editor.guides.bracketPairs": "active"` | вертикальная линия к открывающей скобке текущего блока |
| `"editor.stickyScroll.enabled": true` | заголовок функции «прилипает» сверху: видно, внутри чего ты сейчас |
| `"editor.minimap.enabled": true` | карта файла справа — быстрая навигация по длинному коду |
| `"files.insertFinalNewline"` + `"files.trimTrailingWhitespace"` | в конце файла ровно один перевод строки, хвостовые пробелы убираются: diff в git чище |
| `"terminal.integrated.scrollback": 10000` | буфер терминала на 10 000 строк — длинный вывод не обрезается |
| `"git.autofetch": true` | VS Code сам проверяет, есть ли новые коммиты в удалённом репозитории |
| `"extensions.autoUpdate": "off"` | расширения не обновляются сами: версия инструмента не меняется посреди работы |
| `"telemetry.telemetryLevel": "off"` | редактор не отправляет статистику использования |

Из расширений сверх обязательных полезны `usernamehw.errorlens` (текст ошибки прямо в строке),
`gruntfuggly.todo-tree` (список всех `TODO` и `FIXME` в проекте одной панелью),
`eamodio.gitlens` (кто и когда изменил строку) и `streetsidesoftware.code-spell-checker`
с русским словарём (ловит опечатки в именах переменных и комментариях).

**Кодировка.** VS Code сохраняет новые файлы в UTF-8, и это тот случай, когда «по умолчанию»
правильно: русский текст не превратится в «кракозябры», когда в лекции [[15. Работа с файлами]]
программа начнёт читать и записывать файлы.

> [!note] Как запускается программа
> Интерпретатор читает файл сверху вниз и выполняет строку за строкой. Поэтому порядок строк —
> часть программы: если строка использует переменную, которой ещё не присвоили значение, — это
> ошибка, и она случится именно в этот момент.

# Ошибки первого запуска

Программа падает с ошибкой не потому, что «всё сломано»: Python сам объясняет, что случилось
и где. **Как читать traceback, какие ошибки бывают и как обработать ожидаемую — в лекции
[[05. Язык Python - идентификаторы, операторы, типы данных]].** Здесь важно другое: где эту
ошибку видно в VS Code.

| Где смотреть | Что там |
|---|---|
| терминал после запуска | вывод программы и traceback: последняя строка — тип и причина ошибки |
| панель **Problems** (`Ctrl+Shift+M`) | ошибки и предупреждения, заметные **до** запуска: незакрытые скобки, опечатки в именах |
| подчёркивание в коде | то же, что в Problems, но прямо на строке |
| панель **Run and Debug** | что происходит во время выполнения: значения переменных, порядок строк (об отладчике — ниже) |

> [!note] Почему «программа не запустилась» — это нормально
> Ошибка в записи (`SyntaxError`) не даёт начать выполнение вообще: VS Code подчеркнёт её сразу,
> ещё до запуска. Ошибка во время работы (`ValueError`) останавливает программу на конкретной
> строке. В обоих случаях смотрят на строку, которую назвал Python, а не переписывают файл целиком.

# Виртуальное окружение

**Зависимости** — сторонние библиотеки, которые использует проект (например, `requests` для
запросов в интернет). Проблема начинается, когда у двух проектов нужны разные версии одной
библиотеки: общая «системная» установка тут же превращается в конфликт.

**Виртуальное окружение** — отдельная папка со своим набором библиотек для одного проекта.
Правило простое и обязательное: **один проект — одно окружение**. Внутри окружения лежит
и копия интерпретатора, так что версия Python тоже закрепляется за проектом.

Что при этом хранится в проекте:

| Файл | Что это |
|---|---|
| `pyproject.toml` | описание проекта: имя, версия Python, список зависимостей |
| `uv.lock` | точные версии всех библиотек — чтобы у всех было одинаково |
| `.venv/` | само окружение; в репозиторий не попадает (добавляется в `.gitignore`) |
| `README.md` | как запустить проект: пара команд |

> [!warning] Почему `.venv` не коммитят
> Папка окружения — сотни мегабайт машинозависимых файлов. В репозиторий кладут описание
> зависимостей (`pyproject.toml` + `uv.lock`), а окружение каждый разворачивает у себя командой
> установки. Так проект работает у всех одинаково и не «потянет» за собой чужие пути.

# Инструмент курса: `uv`

Раньше окружение создавали командой `python -m venv .venv` и ставили библиотеки через `pip`.
Способ рабочий и его стоит знать: он встроен в Python и упоминается в любой документации.
Сейчас тот же результат быстрее даёт **`uv`** — один инструмент вместо цепочки `venv` + `pip`,
и именно он используется в проектах курса.

```bash
uv init proj          # создать проект: появится pyproject.toml
cd proj

uv add requests       # добавить зависимость (и записать её в pyproject.toml + uv.lock)
uv remove requests    # убрать зависимость
uv sync               # развернуть окружение по uv.lock (например, после git clone)

uv run main.py        # запустить программу внутри окружения проекта
uv run python -c "import requests; print(requests.__version__)"  # выполнить команду в окружении
```

Почему так удобнее:

- `uv run` **не требует** активировать окружение вручную — команда сама понимает, какое
  окружение относится к проекту;
- версия Python закрепляется за проектом и не зависит от системы;
- `uv.lock` фиксирует точные версии — «у меня работает, у тебя нет» исчезает как класс.

> [!tip] Как выбрать версию Python для проекта
> `uv python pin 3.12` — записать нужную версию в проект; `uv run` сам её найдёт и при
> необходимости скачает. Проверить, что используется: `uv run python --version`.

# Приёмы `uv` в рабочем проекте

Команд выше хватает для учебных задач. В рабочем проекте появляются новые потребности: тесты и линтер, которые нужны только разработчику; одноразовые скрипты; воспроизводимая сборка на сервере. Для них в `uv` есть отдельные приёмы.

> [!note] Как проверены команды этого раздела
> Команды сверены с официальной документацией `docs.astral.sh/uv` (29.09.2026, в примерах документации указана версия `uv` 0.12.20). **В среде, где готовилась заметка, `uv` не установлен, поэтому команды не прогонялись.** Проверь их при первом использовании и, если вывод отличается, доверяй документации и `uv --help`.

## Зависимости для разработки: группы

Библиотеки, которые нужны только при разработке (тесты, форматтер), не должны попадать в основной список зависимостей. Их добавляют в **группу**:

```bash
uv add --dev pytest          # добавить pytest в группу dev (только для разработки)
uv add --group docs mkdocs   # добавить mkdocs в свою группу с именем docs
uv sync --no-dev             # развернуть окружение без группы dev (например, на сервере)
uv sync --group docs         # развернуть окружение вместе с группой docs
```

В `pyproject.toml` группы лежат отдельной таблицей (это стандарт, определённый в PEP 735):

```toml
[project]
dependencies = ["django"]    # нужны программе всегда

[dependency-groups]
dev = ["pytest"]             # нужны только разработчику
```

Группа `dev` устанавливается по умолчанию при `uv sync` и `uv run`, остальные группы подключают явно флагом `--group`.

## Воспроизводимая установка: `--locked` и `--frozen`

`uv run` и `uv sync` сами обновляют `uv.lock` и окружение, если ты изменил зависимости. Для сервера и проверок так удобно не всегда: нужно, чтобы **ничего не менялось молча**.

```bash
uv sync --locked         # ошибка, если uv.lock не соответствует pyproject.toml
uv sync --frozen         # взять uv.lock как есть, не проверяя его актуальность
uv lock --check          # только проверить актуальность lock-файла, ничего не менять
uv lock --upgrade-package django   # обновить одну библиотеку, остальные версии не трогать
uv lock --upgrade        # обновить все библиотеки в пределах заданных ограничений
```

Новые версии библиотек сами в `uv.lock` не попадают: пока ты не попросил обновить, версии остаются прежними.

## Одноразовые скрипты

Не каждому скрипту нужен проект. Для файла, которому нужна одна-две библиотеки, есть два способа.

Разово, без правки файла:

```bash
uv run --with rich script.py   # запустить script.py; библиотеку rich подставить во временное окружение
```

Или записать зависимости в сам файл. Блок `# /// script` — специальный комментарий (стандарт PEP 723), внутри него текст в формате TOML:

```python
# /// script
# requires-python = ">=3.12"
# dependencies = [
#   "requests<3",
# ]
# ///
import requests

print(requests.get("https://example.com").status_code)
```

```bash
uv add --script script.py "requests<3"   # то же самое, но блок записывает сам uv
uv run script.py                          # uv создаст окружение и подберёт нужный Python
```

Список `dependencies` в блоке обязателен, даже если он пустой. Если такой скрипт лежит внутри проекта, зависимости проекта при запуске игнорируются: используется только блок в файле.

## Инструменты: `uvx` и `uv tool`

Некоторые программы на Python — самостоятельные инструменты, а не библиотеки: линтер `ruff`, форматтеры, генераторы документации. Их не добавляют в проект, а запускают или устанавливают отдельно:

```bash
uvx ruff check .           # запустить ruff во временном изолированном окружении, без установки
uv tool install ruff       # установить ruff надолго; команда ruff станет доступна в терминале
uv tool upgrade ruff       # обновить установленный инструмент
```

`uvx` — короткое имя для `uv tool run`. Инструмент, которому нужен код твоего проекта (например, `pytest` или `mypy`), запускают через `uv run`, а не `uvx`: иначе он окажется в окружении, изолированном от проекта, и не найдёт твои модули.

## Интерфейс, совместимый с `pip`

Старые проекты ведут списком `requirements.txt` и командами `pip`. `uv` умеет и такой режим:

```bash
uv venv                        # создать окружение в папке .venv
uv pip install -r requirements.txt   # поставить зависимости из requirements.txt
uv add -r requirements.txt     # или перенести их в pyproject.toml и uv.lock
uv export --format requirements.txt  # выгрузить uv.lock обратно в requirements.txt
```

`uv pip` работает только внутри виртуального окружения (найденного автоматически или созданного `uv venv`) и не меняет `pyproject.toml` и `uv.lock`: это режим для совместимости, а не основной способ работы.

## Docker и проверки в CI (справка)

На сервере и в автоматических проверках окружение собирают заново по `uv.lock`. Схема для Docker-образа:

```dockerfile
FROM python:3.12-slim-trixie
COPY --from=ghcr.io/astral-sh/uv:0.12.20 /uv /uvx /bin/   # взять программу uv из официального образа
COPY . /app                                                # скопировать проект в образ
WORKDIR /app
ENV UV_NO_DEV=1                                            # не ставить группу dev
RUN uv sync --locked                                       # собрать окружение точно по uv.lock
```

Версию `uv` в образе закрепляют. Папку `.venv` добавляют в `.dockerignore`: окружение зависит от платформы и в образе создаётся заново.

Шаги в GitHub Actions после установки `uv` (официальным действием `astral-sh/setup-uv`, версию действия и `uv` закрепляют):

```yaml
- name: Install the project
  run: uv sync --locked --all-extras --dev   # окружение точно по uv.lock, с группой dev
- name: Run tests
  run: uv run pytest tests                   # запустить тесты в окружении проекта
```

## Рабочие пространства (workspaces)

Если в одном репозитории лежит несколько связанных пакетов (приложение и две библиотеки), их объединяют в **рабочее пространство**: у каждого пакета свой `pyproject.toml`, а `uv.lock` общий, поэтому версии библиотек согласованы. В учебных проектах это не нужно, но термин встретится в чужих репозиториях.

```toml
[tool.uv.workspace]
members = ["packages/*"]   # каждая папка внутри packages — участник пространства
```

```bash
uv run --package bird-feeder pytest   # выполнить команду в конкретном участнике пространства
```

Когда у пакетов конфликтующие требования или нужно отдельное окружение на каждый, рабочие пространства не подходят: пакеты делают независимыми проектами и связывают путями.

# Структура проекта

Даже маленький проект удобнее держать в порядке:

```text
proj/
├── pyproject.toml     # описание проекта и зависимостей
├── uv.lock            # точные версии библиотек
├── README.md          # как запускать
└── src/
    └── main.py        # код
```

Папка `src` — просто договорённость: так сразу видно, где код, а где служебные файлы.
В маленьких учебных задачах достаточно одного файла `main.py` — главное, чтобы он лежал
в проекте со своим окружением, а не «где-то на рабочем столе».

# Как это делают в проекте

**Привычка 1. Один проект — одно окружение.** Не ставить библиотеки «в систему»: чужая версия
рано или поздно сломает другой проект. Начинается работа командой `uv sync`.

**Привычка 2. Запускать через `uv run`.** Команда выбирает окружение проекта сама — не нужно
помнить, активирован ли `venv`.

**Привычка 3. Читать ошибку целиком, снизу вверх.** Последняя строка говорит причину, строка
`File ... line N` — место. Разбор traceback — в [[05. Язык Python - идентификаторы, операторы, типы данных]].

**Привычка 4. Останавливать программу отладчиком.** Когда непонятно, почему цикл даёт не тот
результат, ставят `F9` на подозрительную строку и смотрят значения в Variables — вместо того
чтобы расставлять `print` по всему коду и потом их убирать.

**Привычка 5. Проверять, чем запускается код.** Если программа ведёт себя не так, как ожидалось,
полезно убедиться, что запускается нужный интерпретатор и нужное окружение: `uv run python --version`.

> [!example] Приём из прошлого кода — поиск корня проекта (наследие `CopyPaste.py`)
> Раньше путь к модулям искали подсчётом `../..`. Надёжнее искать маркер проекта вверх по дереву:
> ```python
> from pathlib import Path
> 
> def find_project_root(start: Path, marker: str = "pyproject.toml") -> Path:
>     for p in (start, *start.parents):
>         if (p / marker).exists():
>             return p
>     return start
> 
> ROOT = find_project_root(Path(__file__).resolve())
> DATA = ROOT / "data" / "grades.csv"
> ```
> Идея сохранена, хрупкий подсчёт `..` — нет. Тот же приём — в лекции 15 для `pathlib`.

# Ключевые термины

| Термин | Определение |
|---|---|
| **Среда разработки** | программа для написания и запуска кода: редактор или IDE |
| **Интерпретатор** | программа, которая выполняет код Python; читает файл сверху вниз |
| **Traceback** | сообщение об ошибке: тип, причина и место, где она случилась |
| **Отладчик** | режим запуска, в котором программа останавливается на точках останова и показывает значения |
| **Точка останова** | метка на строке (`F9`): дойдя до неё, программа останавливается |
| **Палитра команд** | поиск команд VS Code по имени (`Ctrl+Shift+P`) |
| **Панель Problems** | список ошибок и предупреждений, найденных редактором до запуска |
| **Зависимость** | сторонняя библиотека, используемая проектом |
| **Виртуальное окружение** | отдельный набор библиотек для одного проекта (`.venv`) |
| **`pyproject.toml`** | файл с описанием проекта и списком зависимостей |
| **`uv.lock`** | файл с точными версиями зависимостей |
| **`uv`** | инструмент курса: создаёт окружение, ставит зависимости, запускает код |
| **`uv run`** | запуск команды внутри окружения проекта |
| **Группа зависимостей** | именованный список библиотек в `[dependency-groups]`; `dev` — для разработки |
| **`--locked` / `--frozen`** | режимы `uv`: ошибка при устаревшем `uv.lock` / использование `uv.lock` без проверки |
| **Встроенные метаданные скрипта (PEP 723)** | блок `# /// script` в начале файла со списком зависимостей скрипта |
| **`uvx`** | запуск инструмента (линтера и т. п.) во временном окружении без установки |
| **Рабочее пространство `uv`** | несколько пакетов одного репозитория с общим `uv.lock` |

# Типичные заблуждения

- ❌ **«Ошибка — это провал».** Ошибка — обычная часть работы: traceback сообщает причину и место.
  Плохо не то, что ошибка есть, а то, что её не видно.
- ❌ **«Ошибка в первой строке сообщения».** Читать надо **последнюю** строку — там тип и причина,
  выше — путь к месту.
- ❌ **«Открыть в VS Code отдельный файл или папку — разницы нет».** Есть: без открытой папки
  редактор не видит структуру проекта, не находит модули и хуже подсказывает.
- ❌ **«Отладчик нужен только в сложных программах».** Наоборот: на маленьком цикле он за минуту
  показывает, как меняются переменные, — быстрее, чем расставлять `print`.
- ❌ **«Библиотеки ставят в систему — так короче».** Тогда версии конфликтуют между проектами,
  а на другой машине ничего не запускается. Стандарт — окружение на проект.
- ❌ **«Окружение нужно активировать вручную».** При работе через `uv run` — нет: команда сама
  находит окружение проекта.
- ❌ **«`.venv` стоит закоммитить, чтобы у всех работало».** Наоборот: коммитят `pyproject.toml`
  и `uv.lock`, а окружение разворачивают командой `uv sync`.
- ❌ **«Питон должен быть один на машине».** Версия закрепляется за проектом; разные проекты
  могут требовать разные версии, и это нормально.

# Проверь себя

1. Чем редактор отличается от IDE и что входит в минимум удобств?
2. Зачем ставят точку останова и что видно в панели Variables?
3. Почему проект открывают папкой, а не отдельным файлом?
4. Зачем нужно виртуальное окружение и что из него попадает в репозиторий?
5. Какие три файла описывают проект и зачем каждый нужен?
6. Что такое палитра команд и почему ей удобнее пользоваться, чем меню?
7. Как отделить библиотеки для тестов от основных зависимостей и не ставить их на сервер?
8. Чем `uvx ruff` отличается от `uv run pytest` и почему для `pytest` нужен именно `uv run`?

> [!example]- Ответы
> 1. IDE — среда «всё в одном» (редактор, отладчик, инструменты проекта); редактор легче
>    и расширяется плагинами (VS Code). Минимум удобств: подсветка синтаксиса, автодополнение,
>    проверка на лету, запуск файла, терминал и отладчик.
> 2. Чтобы остановить программу в нужном месте (`F9`) и посмотреть, какие значения у переменных
>    там оказались: в панели Variables видно их все сразу, а не по одному через `print`.
> 3. Открытая папка даёт редактору всю структуру проекта: он находит модули, подхватывает
>    окружение, правильно подсказывает имена. Отдельный файл редактор видит «в отрыве» —
>    отсюда и неработающие импорты.
> 4. Чтобы у каждого проекта был свой набор библиотек и не было конфликтов версий между
>    проектами и система. В репозиторий попадают описание и версии (`pyproject.toml`, `uv.lock`),
>    а сама папка `.venv` — нет, её добавляют в `.gitignore`.
> 5. `pyproject.toml` — что за проект, какая версия Python и какие зависимости;
>    `uv.lock` — точные версии всех библиотек; `README.md` — как проект запускать.
> 6. Палитра (`Ctrl+Shift+P`) ищет команды по имени: не нужно помнить, в каком меню лежит
>    «Python: Select Interpreter» или «Format Document». Это быстрее и точнее, чем искать
>    команду глазами.
> 7. Добавить их в группу разработки: `uv add --dev pytest`. На сервере окружение собирают с `uv sync --no-dev` (или задают `UV_NO_DEV=1`), и группа `dev` не устанавливается.
> 8. `uvx` запускает инструмент во временном изолированном окружении и не видит модули проекта. `pytest` должен импортировать твой код, поэтому его запускают в окружении проекта: `uv run pytest`.
