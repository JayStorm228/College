# Паттерны программирования

> [!abstract] О чём эта лекция
> **Зачем это нужно.** Ты уже знаешь ЖЦ, роли, ветки и техдолг. Но когда пишешь код, регулярно упираешься в одни и те же вопросы: как создать объект без привязки к классу, как нарастить функциональность без правки исходника, как уведомить кучу подписчиков без связанности. Паттерны — это проверенные ответы на такие типовые задачи.
> **Что ты должен уметь после лекции:** объяснить, что такое паттерн и чем он отличается от библиотеки/алгоритма; назвать три категории GoF и 9 паттернов из презентации занятия 11; для каждого кратко сформулировать проблему/решение, пример-аналогию и показать минимальный пример на Python и Rust; отличить паттерн от антипаттерна и объяснить связь с DRY/KISS.

> [!note] Границы материала
> Основа — **HTML-презентация занятия 11** рядом с конспектом (30 слайдов, 23 паттерна GoF, подробно 9). Эта лекция даёт **лёгкое углубление по каждому из 9** — по абзацу текста, структуре и запускаемому примеру Python + краткому Rust-эквиваленту. Внешние сведения помечены как дополнения, а не как материал пары. Отдельные глубокие разборы каждого паттерна вынесены в будущие мини-материалы (см. [[Доска_задач]] ^patternDeepSeparate).

# Зачем нужны паттерны

Представь, что ты архитектор. Ты не изобретаешь фундамент каждый раз заново — берёшь проверенное решение, адаптируя под грунт и этажность. В коде так же: одни и те же проблемы — создание объектов, наращивание поведения, уведомления — встречаются в любом проекте.

Без паттерна ты пишешь `if/else` по типам, копируешь код, связываешь модули жёстко. Техдолг растёт, тесты ломаются. Паттерн даёт **общий язык**: сказав «здесь Фабрика», команда понимает, где создаётся объект и почему.

> [!tip] Когда паттерн не нужен
> Если задача простая, нет ветвления по типам и дублирования — паттерн только усложнит. Лучший паттерн — тот, что не понадобился.

---

# Понятие паттерна

**Паттерн проектирования** — проверенное временем решение типовой задачи проектирования. Это не готовый код, а шаблон, который адаптируешь под язык и контекст.

| Паттерн — это | Паттерн — это НЕ |
|---|---|
| идея, концепция решения | готовая библиотека |
| шаблон для адаптации | конкретная функция |
| проверенное решение из практики | универсальное решение на всё |
| общий язык команды | обязательное требование |

> [!example] Аналогия с рецептом
> Рецепт говорит, какие ингредиенты и в каком порядке смешивать, но ты подстраиваешь соль, температуру и замену продуктов. Так и паттерн — идея, а не копия кода.

# Историческая справка: «Банда четырёх»

В 1994 году Эрих Гамма, Ричард Хелм, Ральф Джонсон и Джон Влиссидес издали книгу *Design Patterns: Elements of Reusable Object-Oriented Software*. В ней они систематизировали **23 паттерна**, уже применявшихся в индустрии. Авторов прозвали **Gang of Four (GoF)**.

Паттерны не изобрели — их **обнаружили и описали**. С тех пор они — мировой стандарт проектирования.

---

# Три категории паттернов

Все 23 паттерна GoF делятся по типу решаемой проблемы:

- **Порождающие (5)** — как создаются объекты. Скрывают детали создания. *Аналогия: как производятся кирпичи.*
- **Структурные (7)** — как объекты соединяются в большие структуры. Упрощают связи. *Аналогия: как кирпичи складываются в стены.*
- **Поведенческие (11)** — как объекты взаимодействуют и делят ответственность. *Аналогия: как жители дома общаются.*

В презентации подробно разобраны 9 паттернов (по 3 из каждой категории) — им и посвящено лёгкое углубление ниже. Остальные 14 упомянуты обзорно.

---

# Порождающие паттерны

> [!abstract] Идея категории
> Отделить **создание** объекта от его **использования**, чтобы клиент не зависел от конкретных классов и мог легко расширяться.

Пять порождающих по GoF: **Одиночка, Фабричный метод, Абстрактная фабрика, Строитель, Прототип**. Углубляем три из презентации; два — краткой справкой.

## 1. Одиночка (Singleton) — порождающий

**Проблема:** нужен единственный экземпляр — подключение к БД, логгер, кэш — и глобальная точка доступа.

**Решение:** класс сам контролирует создание и отдаёт один и тот же объект.

**Аналогия:** президент страны — в момент времени один; все обращения идут к нему.

**Когда использовать:** конфигурация приложения, логгер, пул соединений. **Осторожно:** часто называют антипаттерном — создаёт глобальное состояние, мешает тестам, скрывает зависимости.

**Python — через `__new__` (упрощённо):**
```python
class Config:
    _instance = None
    def __new__(cls, *a, **kw):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.value = {}
        return cls._instance

a = Config(); b = Config()
assert a is b  # один объект
```

**Rust — через `OnceLock` (без глобальной мутабельности «в лоб»):**
```rust
use std::sync::OnceLock;
struct Config { value: String }
static INSTANCE: OnceLock<Config> = OnceLock::new();
fn config() -> &'static Config {
    INSTANCE.get_or_init(|| Config { value: "prod".into() })
}
```

> [!warning] Тестируемость
> В тестах одиночку лучше заменять внедрением зависимости (DI), чтобы не тащить глобальное состояние.

## 2. Фабричный метод (Factory Method) — порождающий

**Проблема:** код привязан к конкретным классам. Добавление нового типа требует правки `if/else` по всему проекту.

**Решение:** вынести создание в отдельный метод/класс-фабрику. Клиент просит у фабрики, не зная деталей.

**Аналогия:** пиццерия — говоришь «хочу пиццу», а как её собрать, решает фабрика.

> [!example] Твой код как пример фабрики
> В проекте Software ты сделал `SoftwareFactories: dict[int, Callable] = {1: Commercial..., 2: OpenSource..., 3: Freemium...}` и фабричные методы `CommercialSoftware.Date_str(...)` с `parse_date` и валидацией. `main` выбирает фабрику по ключу, не зная конструкторов — это и есть Фабрика (подробный разбор — в [[07. Работа на основе лекции 09]]).

**Python (минимальный):**
```python
from abc import ABC, abstractmethod
class Button(ABC): 
    @abstractmethod
    def render(self): ...
class WinButton(Button): 
    def render(self): return "Win"
class MacButton(Button): 
    def render(self): return "Mac"
def button_factory(os: str) -> Button:
    return WinButton() if os == "win" else MacButton()
```

**Rust (trait + фабрика):**
```rust
trait Button { fn render(&self) -> &'static str; }
struct WinButton; impl Button for WinButton { fn render(&self)->&'static str{"Win"}}
struct MacButton; impl Button for MacButton { fn render(&self)->&'static str{"Mac"}}
fn button_factory(os: &str) -> Box<dyn Button> {
    if os=="win" { Box::new(WinButton) } else { Box::new(MacButton) }
}
```

**Когда использовать:** семейство типов с разной логикой создания, выбор типа в рантайме.

## 3. Строитель (Builder) — порождающий

**Проблема:** сложный объект с 10+ параметрами — конструктор неудобен, часть параметров опциональна.

**Решение:** строить пошагово, вызывая методы `with_*`, в конце `build()`.

**Аналогия:** дом — фундамент → стены → крыша → окна; прораб управляет шагами.

**Python:**
```python
@dataclass
class House:
    walls: int = 0
    roof: str = ""
    garage: bool = False

class HouseBuilder:
    def __init__(self): self.h = House()
    def walls(self, n): self.h.walls=n; return self
    def roof(self, r): self.h.roof=r; return self
    def garage(self): self.h.garage=True; return self
    def build(self): return self.h

house = HouseBuilder().walls(4).roof("tile").garage().build()
```

**Rust:**
```rust
struct House { walls: u8, roof: String, garage: bool }
struct Builder { walls: u8, roof: String, garage: bool }
impl Builder {
    fn new()->Self{Self{walls:0, roof:String::new(), garage:false}}
    fn walls(mut self, n:u8)->Self{self.walls=n; self}
    fn roof(mut self, s:&str)->Self{self.roof=s.into(); self}
    fn garage(mut self)->Self{self.garage=true; self}
    fn build(self)->House{House{walls:self.walls, roof:self.roof, garage:self.garage}}
}
let house = Builder::new().walls(4).roof("tile").garage().build();
```

### Кратко об остальных порождающих

- **Абстрактная фабрика** — создаёт *семейства* связанных объектов (например, `WinFactory` даёт `WinButton+WinCheckbox`, `MacFactory` — `MacButton+MacCheckbox`) без привязки к конкретным классам. Нужна, когда нужны согласованные наборы.
- **Прототип** — создаёт объекты клонированием существующего (`copy.copy` в Python, `Clone` в Rust), удобно когда создание дорого или нужен снимок состояния.

# Структурные паттерны

> [!abstract] Идея категории
> Собрать из простых объектов гибкую структуру, скрыть сложность связей и сделать интерфейсы совместимыми.

Семь структурных по GoF: Адаптер, Декоратор, Фасад, Заместитель, Компоновщик, Мост, Легковес. Углубляем три из презентации.

## 4. Адаптер (Adapter) — структурный

**Проблема:** интерфейс нужного класса не совпадает с ожидаемым клиентом.

**Решение:** прослойка-переходник, переводящая один интерфейс в другой.

**Аналогия:** переходник вилки Type A → розетка Type C; ни вилку, ни розетку не меняем.

**Python:**
```python
class OldPrinter:
    def print_old(self, text): return f"OLD:{text}"

class PrinterAdapter:
    def __init__(self, old: OldPrinter): self.old = old
    def print(self, text: str):  # ожидаемый интерфейс
        return self.old.print_old(text.upper())

adapter = PrinterAdapter(OldPrinter())
assert adapter.print("hi") == "OLD:HI"
```

**Rust:**
```rust
trait NewPrinter { fn print(&self, t: &str) -> String; }
struct OldPrinter; impl OldPrinter { fn print_old(&self, t:&str)->String{format!("OLD:{t}")}}
struct Adapter(OldPrinter);
impl NewPrinter for Adapter {
    fn print(&self, t: &str)->String { self.0.print_old(&t.to_uppercase()) }
}
```

**Когда:** интеграция старой библиотеки, стороннего API с другим форматом.

## 5. Декоратор (Decorator) — структурный

**Проблема:** добавить поведение объекту динамически, не плодя подклассы и не меняя класс.

**Решение:** обернуть объект в декоратор с тем же интерфейсом; декораторы можно вкладывать.

**Аналогия:** подарок → обёрточная бумага → бант → открытка — каждый слой добавляет свойство.

**Python (функции и классы):**
```python
def bold(fn):
    def wrapper(*a, **kw): return f"<b>{fn(*a, **kw)}</b>"
    return wrapper

@bold
def text(s): return s
assert text("hi") == "<b>hi</b>"

# для объектов — композиция
class Coffee:
    def cost(self): return 5
class Milk:
    def __init__(self, c): self.c=c
    def cost(self): return self.c.cost()+2
assert Milk(Coffee()).cost() == 7
```

**Rust (композиция через trait):**
```rust
trait Coffee { fn cost(&self)->u32; }
struct Simple; impl Coffee for Simple { fn cost(&self)->u32{5}}
struct Milk<T: Coffee>(T);
impl<T: Coffee> Coffee for Milk<T> { fn cost(&self)->u32{self.0.cost()+2}}
let c = Milk(Simple); assert_eq!(c.cost(),7);
```

## 6. Фасад (Facade) — структурный

**Проблема:** подсистема из многих классов сложна для клиента.

**Решение:** простой фасад с 1–2 методами, скрывающий детали.

**Аналогия:** ресепшн отеля — говоришь «забронировать», а внутри проверка наличия, расчёт, БД.

**Python:**
```python
class CPU: 
    def start(self): pass
class Memory: 
    def load(self): pass
class ComputerFacade:
    def __init__(self): self.cpu=CPU(); self.mem=Memory()
    def start(self): self.mem.load(); self.cpu.start()
ComputerFacade().start()
```

**Rust:**
```rust
struct Cpu; impl Cpu{fn start(&self){}}
struct Memory; impl Memory{fn load(&self){}}
struct Computer{ cpu: Cpu, mem: Memory}
impl Computer{ fn start(&self){self.mem.load(); self.cpu.start();}}
```

### Кратко об остальных структурных

- **Заместитель (Proxy)** — контролирует доступ (ленивая загрузка, кэш, проверка прав) через объект-заместитель с тем же интерфейсом.
- **Компоновщик (Composite)** — дерево объектов, где лист и группа обрабатываются одинаково (файл/папка, `render()`).
- **Мост (Bridge)** — разделяет абстракцию и реализацию, чтобы менять независимо (фигура ↔ способ рисования).
- **Легковес (Flyweight)** — разделяет общие данные множества мелких объектов для экономии памяти (символы, частицы).

# Поведенческие паттерны

> [!abstract] Идея категории
> Распределить ответственность за взаимодействие, чтобы объекты не знали лишнего друг о друге и могли меняться независимо.

Одиннадцать поведенческих по GoF; углубляем три ключевых из презентации.

## 7. Наблюдатель (Observer) — поведенческий

**Проблема:** один объект меняется, другие должны узнать без жёсткой привязки.

**Решение:** издатель хранит список подписчиков и уведомляет их.

**Аналогия:** подписка на YouTube-канал — автор не знает всех подписчиков, но уведомляет всех.

**Python:**
```python
class Store:
    def __init__(self): self.subs=[]
    def subscribe(self, fn): self.subs.append(fn)
    def notify(self, msg): [fn(msg) for fn in self.subs]

store = Store()
store.subscribe(lambda m: print(f"email: {m}"))
store.notify("товар в наличии")
```

**Rust:**
```rust
struct Store { subs: Vec<Box<dyn Fn(&str)>> }
impl Store {
    fn notify(&self, msg:&str){ for f in &self.subs { f(msg)}}
}
```

**Когда:** уведомления, обновление UI при изменении модели, события.

## 8. Стратегия (Strategy) — поведенческий

**Проблема:** несколько алгоритмов одной задачи, выбор в рантайме. `if/else` в каждом месте — плохо.

**Решение:** каждый алгоритм — отдельный класс с общим интерфейсом, контекст хранит выбранную стратегию.

**Аналогия:** навигатор — быстрый/короткий/без платных дорог — стратегии; навигатор не меняется.

**Python:**
```python
class PriceStrategy:
    def calc(self, km, mins): raise NotImplementedError
class ByKm(PriceStrategy): 
    def calc(self, km, mins): return km*10
class ByTime(PriceStrategy): 
    def calc(self, km, mins): return mins*5
class Taxi:
    def __init__(self, s: PriceStrategy): self.s=s
    def price(self, km, mins): return self.s.calc(km, mins)
assert Taxi(ByKm()).price(10,0)==100
```

**Rust:**
```rust
trait Price { fn calc(&self, km:u32, mins:u32)->u32; }
struct ByKm; impl Price for ByKm{ fn calc(&self,km:u32,_:u32)->u32{km*10}}
struct Taxi { strat: Box<dyn Price> }
impl Taxi{ fn price(&self,km:u32,mins:u32)->u32{self.strat.calc(km,mins)}}
```

## 9. Состояние (State) — поведенческий

**Проблема:** поведение зависит от внутреннего состояния; `if state == "red": ... elif ...` запутывает код.

**Решение:** каждое состояние — отдельный класс, объект делегирует ему поведение и переключает состояние.

**Аналогия:** светофор — красный «стоять», жёлтый «готовиться», зелёный «ехать».

**Python:**
```python
class Red:
    def next(self, ctx): ctx.state = Yellow()
    def action(self): return "стой"
class Yellow:
    def next(self, ctx): ctx.state = Green()
    def action(self): return "жди"
class Green:
    def next(self, ctx): ctx.state = Red()
    def action(self): return "едь"
class Traffic:
    def __init__(self): self.state = Red()
    def next(self): self.state.next(self)
    def act(self): return self.state.action()
```

**Rust (enum + match — идиоматично):**
```rust
enum State { Red, Yellow, Green }
impl State { fn next(&self)->Self{ match self{Self::Red=>Self::Yellow, Self::Yellow=>Self::Green, Self::Green=>Self::Red}}}
struct Traffic{ state: State}
impl Traffic{ fn act(&self)->&str{ match self.state{State::Red=>"стой", State::Yellow=>"жди", State::Green=>"едь"}}}
```

### Кратко об остальных поведенческих

- **Команда (Command)** — превращает действие в объект с `execute()/undo()`, удобно для очередей и отмены.
- **Итератор** — обходит коллекцию без раскрытия структуры (`for x in coll`).
- Остальные — Посредник, Снимок, Цепочка обязанностей, Шаблонный метод, Посетитель — разбираются в отдельных мини-материалах.

# Как выбрать паттерн

Спрашивай не «какой паттерн я знаю?», а **«какая проблема?»**

| Проблема | Смотри в сторону |
|---|---|
| Один экземпляр | Одиночка |
| Выбор типа при создании | Фабрика |
| Много параметров | Строитель |
| Несовместимые интерфейсы | Адаптер |
| Добавить поведение динамически | Декоратор |
| Упростить сложную подсистему | Фасад |
| Уведомить подписчиков | Наблюдатель |
| Подменить алгоритм на лету | Стратегия |
| Поведение зависит от состояния | Состояние |

> [!warning] Цена паттерна
> Каждый паттерн добавляет классы и косвенность. Если проблема надуманна — код станет сложнее без выгоды. Сначала DRY/KISS, затем паттерн.

# Антипаттерны

**Антипаттерн** — распространённое решение, которое кажется удобным, но приносит больше вреда, чем пользы.

- **Золотой молоток** — один любимый паттерн на всё («везде фабрика»).
- **Божественный объект (God Object)** — класс на 1000 строк делает всё; нарушает единственную ответственность.
- **Копипаста** — дублирование вместо функции/модуля; нарушает DRY.

Знать антипаттерны так же важно, как паттерны: они показывают, как *не* делать.

---

# Связь с остальным курсом

- **Качество кода (DRY/KISS, техдолг):** паттерны помогают DRY (Фабрика убирает `if/else`) и KISS (Стратегия упрощает ветвления), но неправильный выбор сам создаёт техдолг.
- **Архитектура:** MVC/MVP строятся на Наблюдателе и Стратегии.
- **Гибкие методологии:** в Scrum требования меняются — паттерны делают код гибким к изменениям.
- **ИИ в разработке:** ИИ может предложить паттерн, но выбор и обоснование — за человеком; без понимания паттерна примешь неподходящий совет.

> [!note] Дальше — отдельные мини-материалы
> По решению владельца эта лекция оставляет лёгкое углубление. Глубокие разборы с UML, расширенными примерами и тестами выносятся в отдельные заметки по каждому паттерну (см. доску ^patternDeepSeparate). Так материал остаётся кратким для экзамена, а для практики можно уйти глубже по ссылке.

# Типичные заблуждения

- ❌ **«Паттерн — готовая библиотека».** Паттерн — идея; библиотека — код. Паттерн адаптируешь, библиотеку подключаешь.
- ❌ **«Чем больше паттернов, тем лучше архитектура».** Лишние паттерны усложняют и создают техдолг.
- ❌ **«Одиночка — всегда хорошо для одного экземпляра».** Глобальное состояние мешает тестам; часто лучше внедрение зависимости.
- ❌ **«Фабрика нужна для любого создания».** Для простых объектов прямой `new`/`dataclass` проще и читаемее.
- ❌ **«Паттерны — только для ООП».** Идеи применимы и в функциональном Rust — через `enum`, `trait`, композицию.
