# Тестирование программного обеспечения

> [!abstract] О чём эта лекция
> **Зачем это нужно.** Запуск программы ещё не означает, что она соответствует требованиям. Тестирование даёт информацию о качестве и снижает риск изменений.
> **Что ты должен уметь после лекции:** различать ошибку, дефект и отказ; выбирать виды и уровни проверок; применять классы эквивалентности и граничные значения; составлять тест-кейс и баг-репорт.


# Зачем нужно тестирование

**Тестирование ПО** — процесс исследования, испытания и проверки программного продукта для оценки качества, выявления дефектов и подтверждения соответствия требованиям.

- **Исследование:** изучить поведение в разных условиях и сценариях.
- **Испытание:** подвергнуть программу нагрузке и нестандартным ситуациям.
- **Проверка:** сравнить фактический результат с ожидаемым.

Программа может запускаться, но неправильно обрабатывать ввод, одновременные обращения или нагрузку в тысячу пользователей. Поэтому тестирование — **не только поиск багов**, а получение информации для решения, можно ли пользоваться продуктом и что нужно исправить. Успешные проверки не доказывают отсутствие всех дефектов.

# Ошибка, дефект и отказ

| Понятие | Что означает | Пример |
|---|---|---|
| **Ошибка (Error)** | Действие человека, приводящее к неправильному результату | Разработчик неверно понял требование или опечатался |
| **Дефект (Defect, Bug)** | Изъян в программном продукте; в примерах лекции — в коде | В коде отсутствует необходимая проверка |
| **Отказ (Failure)** | Наблюдаемое неправильное поведение при выполнении | Пользователь получает неверный результат |

```mermaid
flowchart LR
    A[Ошибка человека] --> B[Дефект в продукте]
    B --> C[Условия, активирующие дефект]
    C --> D[Отказ при выполнении]
```

Дефект существует и до запуска программы, а проявляется не при каждом выполнении. Аналогия с тортом: повар перепутал соль с сахаром (ошибка), в смеси оказался неверный ингредиент (дефект), готовый торт оказался несъедобным (отказ).


# Тестовая документация

## Тест-кейс

**Тест-кейс (Test Case)** — набор входных данных, условий выполнения и ожидаемого результата для проверки определённого аспекта программы. Это инструкция «что сделать и что должно получиться».

| Поле | Что записывать |
|---|---|
| Идентификатор | Уникальный номер, например TC-001 |
| Название | Краткое описание проверяемого поведения |
| Предусловия | Состояние системы до начала проверки |
| Шаги | Последовательность действий с конкретными входными данными |
| Ожидаемый результат | Что должно произойти по требованиям |
| Фактический результат | Что произошло при выполнении |
| Статус | Passed — прошёл; Failed — не прошёл |

**Пример преподавателя — регистрация пользователя:**

| Поле | Содержание |
|---|---|
| Идентификатор | TC-001 |
| Название | Успешная регистрация нового пользователя |
| Предусловия | Сайт открыт; пользователь не авторизован; email test@example.com не зарегистрирован |
| Ожидаемый результат | Сообщение «Регистрация успешна», переход в личный кабинет |
| Фактический результат | Заполняется после выполнения |
| Статус | Passed / Failed — определяется после выполнения |

Шаги:
1. Перейти на страницу регистрации.
2. Ввести имя «Иван».
3. Ввести email `test@example.com`.
4. Ввести пароль `SecurePass123!`.
5. Подтвердить пароль.
6. Нажать «Зарегистрироваться».

Ожидаемый результат задаётся заранее. Фактический результат и статус нельзя выдавать за наблюдение, пока тест не выполнен.

## Баг-репорт

**Баг-репорт (Bug Report)** — документ об обнаруженном дефекте, передаваемый разработчикам для исправления.

| Поле | Что записывать |
|---|---|
| Заголовок | Краткое описание проблемы |
| Шаги воспроизведения | Действия и данные, позволяющие повторить проблему |
| Ожидаемый результат | Поведение по требованиям |
| Фактический результат | Наблюдаемое отклонение |
| Окружение | ОС, браузер при наличии, версия приложения и другие значимые условия |
| Приоритет | Насколько срочно нужно исправление |
| Серьёзность | Насколько сильно дефект влияет на работу продукта |

Тест-кейс описывает **проверку**, баг-репорт — **найденную проблему**. Воспроизводимое описание облегчает диагностику: «не работает» без шагов, данных и окружения недостаточно. Невоспроизводимость не означает, что дефекта нет, но затрудняет его исправление.

# Виды тестирования

Это разные оси классификации: одна проверка может одновременно быть функциональной, ручной и выполняться методом чёрного ящика.

## Функциональное и нефункциональное

| Вид | Главный вопрос | Примеры из материала |
|---|---|---|
| **Функциональное** | **Что** делает система, соответствует ли функция требованиям? | Регистрация, расчёт стоимости заказа, формирование отчёта |
| **Нефункциональное** | **Как** работает система, каковы её характеристики качества? | Скорость загрузки, работа при 10 000 пользователей, защищённость данных |


## Чёрный, белый и серый ящик

| Подход                      | На чём основаны проверки                                          |
| --------------------------- | ----------------------------------------------------------------- |
| **Чёрный ящик (Black Box)** | Входы, выходы и требования без опоры на внутреннюю структуру кода |
| **Белый ящик (White Box)**  | Знание и анализ внутренней логики программы                       |
| **Серый ящик (Grey Box)**   | Частичное знание устройства системы при проверке через интерфейс  |


## Ручное и автоматизированное

**Ручное тестирование:** человек выполняет действия и оценивает результат. Оно гибко, подходит для нестандартных сценариев и оценки удобства; написание кода теста не обязательно.

**Автоматизированное тестирование:** проверки выполняются программами. Это удобно для частых повторений, но требует разработки и сопровождения тестов. Автоматизация уменьшает ошибки ручного выполнения, а не исключает человеческий фактор: сценарии и ожидаемые результаты задают люди.

Подходы дополняют друг друга. Существование и кликабельность кнопки можно проверять автоматически; оценка её удобства и привлекательности требует участия человека. Автоматические визуальные сравнения помогают находить изменения, но сами по себе не определяют качество дизайна.

# Уровни тестирования

| Уровень | Объект и цель | Кто обычно проводит | Когда и пример |
|---|---|---|---|
| **Модульное (Unit)** | Отдельные функции, методы, классы изолированно | Разработчики | При написании кода: правильность функции, обработка границ |
| **Интеграционное** | Взаимодействие компонентов | Разработчики или тестировщики | При соединении модулей: авторизация → профиль, фронтенд → бэкенд через API, работа с БД |
| **Системное** | Продукт целиком в условиях, близких к реальным | Тестировщики | После интеграции: полный сценарий, соответствие ТЗ, поведение под нагрузкой |
| **Приёмочное** | Соответствие бизнес-требованиям и готовность к использованию | Заказчик, бизнес-аналитики, конечные пользователи | Перед выпуском: решает ли продукт нужную задачу и удобно ли им пользоваться |

**API** — интерфейс взаимодействия программных компонентов. **ТЗ** — техническое задание, фиксирующее требования к продукту.


## Пирамида тестирования

**Пирамида тестирования** — ориентир распределения автоматизированных проверок: много небольших быстрых тестов в основании и меньше дорогих проверок продукта целиком наверху.

| Слой снизу вверх | Относительное количество | Типичные свойства |
|---|---|---|
| Модульные проверки | Много | Быстрые, изолированные, проще локализовать причину сбоя |
| Интеграционные проверки | Меньше | Проверяют связи, зависят от нескольких компонентов |
| Проверки системы целиком | Ещё меньше | Дороже и медленнее, больше зависимостей и сложнее диагностика |

> [!note] Пирамида и уровни — не одно и то же
> Пирамида показывает рекомендуемое соотношение проверок, а не отождествляет системное и приёмочное тестирование. Системное тестирование проверяет продукт целиком, приёмочное — его пригодность для заказчика. Все четыре уровня определены отдельно в таблице выше.

Почему рекомендуют такую форму:

1. **Экономика:** сбой отдельной функции обычно проще воспроизвести и исправить, чем сбой большого сценария.
2. **Скорость:** короткие проверки дают быструю обратную связь; сценарий всей системы требует подготовки и выполнения большего числа действий.
3. **Стабильность:** сеть, база данных и браузер добавляют причины нестабильных результатов, не обязательно связанные с проверяемой логикой.
4. **Диагностика:** узкий тест помогает локализовать ошибку; большой сценарий прежде всего показывает, что нарушено поведение продукта.


# Методы тест-дизайна

**Тест-дизайн** — проектирование проверок: выбор данных, условий и ожидаемых результатов.

## Эквивалентное разделение

**Эквивалентное разделение** — деление входных данных на классы, внутри которых ожидается одинаковое поведение системы. Для проверки выбирают представителей каждого класса, а не перебирают все значения.

Поле «возраст» принимает целые числа от **18 до 60 включительно**.

| Класс | Пример представителя | Ожидаемое поведение |
|---|---|---|
| Меньше 18 | 15 | Отклонить |
| От 18 до 60 | 35 | Принять |
| Больше 60 | 65 | Отклонить |

Так можно сократить число проверок. Предположение об одинаковой обработке внутри класса нужно обосновывать требованиями: один представитель не доказывает правильность всех значений.

## Анализ граничных значений

**Анализ граничных значений** — выбор значений на границах диапазона и рядом с ними. Здесь часто обнаруживаются ошибки сравнения: например, `> 18` вместо `>= 18`.

Для того же целочисленного возраста:

| Значение | Положение | Ожидаемое поведение |
|---|---|---|
| 17 | Чуть ниже минимума | Отклонить |
| 18 | Минимум | Принять |
| 19 | Чуть выше минимума | Принять |
| 59 | Чуть ниже максимума | Принять |
| 60 | Максимум | Принять |
| 61 | Чуть выше максимума | Отклонить |

Методы дополняют друг друга: классы помогают охватить разные варианты обработки, границы — проверить переходы между ними.

# Тестирование, технический долг и ИИ

**Технический долг** — будущие дополнительные затраты из-за принятых упрощений и недостатков решения. **Рефакторинг** — изменение внутренней структуры кода без изменения его внешнего поведения.

Без тестов сложнее понять последствия правки, поэтому рефакторинг становится рискованным, а разработчики боятся менять код. Тесты фиксируют ожидаемое поведение, помогают новичкам понять систему и замечать нарушения при изменениях. В этом смысле они — **инвестиция в дальнейшую разработку**, а не только сегодняшние затраты.

Наличие тестов не гарантирует отсутствия долга или безопасного изменения: важны качество проверок и охват значимых сценариев. Тесты **снижают риск** накопления долга, но не предотвращают его автоматически.

**ИИ** может помочь с рутинными задачами: предложить тест-кейсы по описанию функции, граничные значения, unit-тесты и тестовые данные. Его результат нужно сверять с требованиями. Оценка удобства, визуального дизайна, бизнес-контекста и работа в неопределённости не должны полностью передаваться ИИ. Он помогает тестировщику, а не заменяет критическое мышление.

# Ключевые термины

| Термин | Определение |
|---|---|
| Тестирование | Получение информации о качестве через исследование, испытание и проверку продукта |
| Ошибка / дефект / отказ | Неверное действие человека / изъян продукта / наблюдаемое неправильное поведение |
| Тест-кейс | Данные, условия, действия и ожидаемый результат проверки |
| Баг-репорт | Описание обнаруженной проблемы для диагностики и исправления |
| Функциональное / нефункциональное тестирование | Проверка функций / характеристик качества |
| Чёрный / белый / серый ящик | Проверки без знания внутренней структуры / на основе структуры / с частичным знанием |
| Модульное / интеграционное тестирование | Проверка отдельного компонента / взаимодействия компонентов |
| Системное / приёмочное тестирование | Проверка продукта целиком / пригодности для заказчика |
| Пирамида тестирования | Ориентир: много быстрых узких проверок, меньше дорогих проверок целого |
| Класс эквивалентности | Группа входных данных с ожидаемо одинаковой обработкой |
| Граничное значение | Значение на границе диапазона; при анализе проверяют также соседние значения |

# Типичные заблуждения

- ❌ «Запускается — значит, работает правильно». Требования, неверный ввод и нагрузку нужно проверять отдельно.
- ❌ «Ошибка, дефект и отказ — синонимы». Это разные звенья причинной цепочки.
- ❌ «Один системный тест заменит все модульные». Он не даёт столь же быстрой и точной локализации проблемы.
- ❌ «Автоматизация исключает человеческие ошибки». Ошибка может оказаться в самом тесте или его ожидаемом результате.
- ❌ «Тесты гарантируют отсутствие технического долга». Они снижают риски, но не заменяют качественное проектирование и сопровождение.
