# Проблема: хаос ручного управления
1. Непонятно, что именно изменилось между версиями
2. Непонятно, кто и когда внёс изменения
3. Если два человека начнут редактировать одну и ту же версию одновременно, их версии невозможно объединить
# Решение: Система контроля версий
- Система контроля версий(VCS) - программная модель, предназначенная для отслеживания документирования и управления изменениями в наборе данных во времени, а так же для координации совместной работы.
- VCS решает проблему хаоса, превращая линейный набор файлов в структурированную историю изменений, которой можно управлять.
# Ключевая единица: Коммит
- Коммит - атомарная единица истории VCS.
- Коммит - полный снимок состояния всех файлов проекта в конкретный момент времени, а не просто разница между файлами
- Аналогия: Фотоальбом
	- Каждый коммит - фотография вашего рабочего стола. Если вы изменили только один файл, система всё равно делает фото всего проекта, но для неизменённых файлов она просто ставит ссылку на старую версию, чтобы экономить место.
# Анатомия коммита
- Каждый коммит в системе сторого формализирован и содержит:
	- **Уникальный хеш (SHA-1)**: Криптографический отпечаток пальца. 
		- Гарантирует, что историю невозможно изменить
	- **Ссылка на родителя**: Указатель на предыдущий коммит.
		- Именно это выстраивает коммиты в цепочку
	- **Метаданные**: Автор, дата и время создания.
	- **Сообщение**: Текстовое описание того, что и почему было изменено
# Хранилище: Репозиторий
- Репозиторий - структурированное хранилище, которое содержит не только текущие файлы проекта, но и полную хронологическую историю всех их изменений
- Важно понимать: репозиторий хранит не просто папку с файлами, а ориентированный ациклический граф (DAG) коммитов, связанных ссылками "родитель-потомок"
# Логика ветвления
## 1. Branch
- Ветка(Branch) - не копия файлов и не отдельная папка.
- В контексте VCS ветка - всего лишь легковесный подвижной указатель на конкретный коммит
## 2. Head
- Специальный системный указатель, который показывает, на каком коммите и в какой ветке находится пользователь в данный момент времени
- Когда происходит переключение между ветками, система просто перемещает Head на нужный коммит и заменяет файлы в вашей рабочей папке на те, что соответствуют этому коммиту.
# Зачем нужно ветвление?
- Ветвление позволяет создавать изолированные линии разработки
- Основные сценарии:
	- Изоляция функций: Разработка новой большой функции не ломает стабильную версию в главной ветке.
	- Параллельная работа: Несколько разработчиков могут работать над разными задачами одновременно, не мешая друг другу.
	- Безопасные эксперименты: Можно создать ветку для проверки гипотезы.
		- Если не получилось - ветка просто удаляется, не оставляя следа в основной истории.
# Переход к слиянию: Merge
- Когда работа в изолированной ветке завершена, её изменения необходимо вернуть в основную линию разработки
- Слияние(Merge) - Операция объединения изменений из одной ветки в другую. Алгоритм VCS анализирует общую историю двух веток и принимает решение о том, как их соединить
## Правила слияния
### 1. Быстрая перемотка (Fast-Forward)
- Условие: в целевой ветке не было новых коммитов с момента создания ветки.
- Логика решения:
	- Системе не нужно ничего объединять. Она просто перемещает указатель ветки main вперёд к коммиту с изменениями ветки. История остаётся линейной
### 2. Трёхстороннее слияние (3-Way Merge)
- Условие: в обеих ветках появились новые коммиты после точки их разделения
- Логика решения:
	- Алгоритм находит общего предка - последний коммит, который был в обеих ветках
	- затем система проверяет три состояния:
		1. Состояние общего предка
		2. Состояние файлов в ветке А
		3. Состояние файлов в ветке Б
	- Результат: Если изменения в ветках касались разных частей файла, то алгоритм автоматически объединяет их и создаёт новый Коммит Слияния, у которого уже два родителя.
### 3. Конфликт слияния (Merge conflict)
- Конфликт слияния - ситуация, при которой алгоритм 3-Way Merge обнаруживает, что в двух ветках были изменены одни и те же строки одного и того же файла относительно общего предка
- Почему алгоритм не решает сам?
	- У алгоритма нет семантического понимания текста. Он работает с байтами. Если в одной позиции байты разные, он не может угадать, какое изменение логически вернее: удалить чужой код или перезаписать свой. Поэтому он останавливается и передаёт управление человеку.
# Архитектурные модели VCS
- Существуют два типа архитектуры: Централизованная и Распределённая
## 1. Централизованная (CVCS)
- Существует единственный центральный сервер, который хранит полную историю
- У разработчиков есть только текущая рабочая версия файлов без истории
- Критические недостатки:
	- Нет сети - нет работы
	- Поломка центрального сервера - полная потеря всей истории проекта.
## 2. Распределённая (DVCS)
- Нет главного сервера
- Каждый разработчик, клонируя проект, получает полную копию репозитория со всей историей коммитов и всеми ветками
- Преимущества DVCS:
	- Автономность: все операции происходят локально и мгновенно. Интернет нужен только для синхронизации.
	- Отказоустойчивость: если у 10 разработчиков есть полная копия репозитория, проект не может быть потерян, пока жив хотя бы один компьютер.
	- Гибкость рабочих процессов: разработчик может коммитить любые изменения локально каждые 10 минут для себя, а отправлять на общий обзор только один большой, чистый коммит в конце дня.
# Роль удалённых хостингов
- Зачем нужны GitHub/GitLab?
- Удалённый репозиторий - договорённость о том, какая из распределённых копий считается официальной точной обмена данными. 
- Архитектурно она ничем не отличается от копии на компьютере разработчика
- Хостинги предоставляют:
	- Удобную точку синхронизации для команды
	- Визуальный интерфейс для просмотра кода и истории
	- Инструменты для Code Review
