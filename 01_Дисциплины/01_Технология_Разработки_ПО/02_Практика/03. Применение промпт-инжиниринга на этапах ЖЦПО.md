## Исходные данные проекта

> Эти данные использовались как первоначальный контекст для начала работы над проектом с помощью ИИ-агентов

### Название проекта
- Консольный менеджер задач (Task CLI)

---

### Краткое описание проекта
- Простое консольное приложение на Rust для управления личными задачами. Позволяет добавлять, просматривать, отмечать выполненными и удалять задачи. Данные хранятся в локальном JSON-файле.

---

### Жизненный цикл проекта

#### 1. Планирование (Planning)

**Цель этапа:** определить целесообразность проекта, оценить ресурсы, сроки и риски.

**Ключевые активности:**
- Описание бизнес-цели: создать простой консольный менеджер задач для личного использования и изучения Rust.
- Оценка целевой аудитории: студенты, начинающие разработчики, пользователи CLI.
- Определение ограничений: проект учебный, без графического интерфейса, без сетевой функциональности.
- Оценка ресурсов: один разработчик, стандартный ноутбук, бесплатные инструменты (Rust, Cargo, VS Code).
- Предварительная оценка сроков: 2–4 недели на базовую версию (MVP).
- Выявление рисков: нехватка времени, сложность с ownership в Rust, проблемы с сериализацией.

**Результаты этапа:**
- Устав проекта (краткое описание цели, scope, ограничений).
- Предварительный план работ.
- Список основных рисков и способов их минимизации.

---

#### 2. Анализ требований (Requirements Analysis)

**Цель этапа:** сформулировать функциональные и нефункциональные требования.

**Функциональные требования:**
- FR1: Добавление новой задачи с заголовком и описанием.
- FR2: Просмотр всех задач.
- FR3: Фильтрация задач по статусу (все/активные/завершённые).
- FR4: Отметка задачи как выполненной по ID.
- FR5: Удаление задачи по ID.
- FR6: Сохранение данных в JSON-файл.
- FR7: Загрузка данных из JSON-файла при старте.

**Нефункциональные требования:**
- NFR1: Приложение работает в консоли на Windows 10/11.
- NFR2: Время отклика команд менее 1 секунды для 100 задач.
- NFR3: Данные сохраняются корректно после каждого изменения.
- NFR4: Код написан на Rust stable, без unsafe.
- NFR5: Проект компилируется командой `cargo build` без ошибок.
- NFR6: Наличие базовой обработки ошибок (не падает с паникой при отсутствии файла).

**Результаты этапа:**
- Документ с требованиями (можно в Markdown).
- Список User Stories.
- Критерии приёмки MVP.

---

#### 3. Проектирование (Design)

**Цель этапа:** разработать архитектуру, структуру данных и модульную организацию.

**Архитектурное решение:**
- Однопроцессное консольное приложение.
- Монолитная структура с разделением на модули.
- Хранение данных в локальном JSON-файле.

**Структура данных:**
- Структура `Task`:
  - `id: u32`
  - `title: String`
  - `description: Option<String>`
  - `status: TaskStatus` (enum: `Active`, `Completed`)
  - `created_at: String` (формат YYYY-MM-DD)

**Модульная структура проекта:**
- `main.rs` — точка входа, парсинг аргументов, вызов команд.
- `task.rs` — определение структуры `Task` и `TaskStatus`.
- `storage.rs` — функции загрузки и сохранения JSON.
- `commands.rs` — реализация команд: add, list, done, remove.
- `error.rs` — типы ошибок и их обработка.

**Пример схемы модулей:**
```text
src/
	main.rs
	task.rs
	storage.rs
	commands.rs
	error.rs
```

**Интерфейс команд:**
- `add <title> [--desc <description>]`
- `list [--status <all|active|completed>]`
- `done <id>`
- `remove <id>`

**Результаты этапа:**
- Схема модулей.
- Описание структур данных.
- Прототип интерфейса команд.
- План тестирования.

---

#### 4. Разработка (Implementation / Coding)

**Цель этапа:** реализовать функциональность согласно требованиям и проекту.

**Итерация 1: Базовая структура**
- Инициализация проекта: `cargo new task-cli`.
- Добавление зависимостей: `serde`, `serde_json`.
- Реализация структур `Task` и `TaskStatus` с сериализацией.
- Создание пустых функций для команд.

**Итерация 2: Хранение данных**
- Реализация функции загрузки списка задач из `tasks.json`.
- Реализация функции сохранения списка задач в `tasks.json`.
- Обработка случая, когда файл не существует (создание нового).

**Итерация 3: Команды**
- Реализация команды `add`: создание задачи, добавление в список, сохранение.
- Реализация команды `list`: вывод всех задач с форматированием.
- Реализация команды `done`: поиск по ID, смена статуса, сохранение.
- Реализация команды `remove`: поиск по ID, удаление, сохранение.

**Итерация 4: Улучшения**
- Добавление фильтрации по статусу в `list`.
- Обработка ошибок: неверный ID, файл не читается, некорректный JSON.
- Форматированный вывод задач (таблица или нумерованный список).

**Итерация 5: Финализация**
- Добавление README с примерами использования.
- Проверка кода через `cargo clippy`.
- Форматирование через `cargo fmt`.
- Написание простых модульных тестов для `storage.rs` и `commands.rs`.

**Результаты этапа:**
- Рабочий код в репозитории.
- Компилируемый бинарный файл.
- Базовые тесты.
- README с инструкцией.

---

#### 5. Тестирование (Testing)

**Цель этапа:** убедиться в корректности работы и соответствии требованиям.

**Виды тестирования:**
- Модульные тесты:
  - Тест загрузки и сохранения JSON.
  - Тест добавления задачи.
  - Тест отметки задачи как выполненной.
  - Тест удаления задачи.
- Интеграционные тесты:
  - Последовательность: добавить → вывести список → отметить → удалить → проверить файл.
- Ручное тестирование:
  - Запуск команд в консоли, проверка вывода.
  - Проверка поведения при отсутствии файла.
  - Проверка реакции на неверный ID.

**Тест-кейсы (примеры):**
- TC1: Добавить задачу, проверить, что она появилась в списке.
- TC2: Отметить задачу выполненной, проверить изменение статуса.
- TC3: Удалить задачу, проверить, что её нет в списке и файле.
- TC4: Запустить приложение без файла `tasks.json`, проверить создание нового.
- TC5: Ввести неверный ID для `done`, проверить корректное сообщение об ошибке.

**Критерии прохождения:**
- Все модульные тесты проходят: `cargo test` без ошибок.
- Ручные сценарии работают согласно требованиям.
- Нет паник при стандартных ошибках (файл не найден, неверный аргумент).

**Результаты этапа:**
- Отчёт о тестировании (можно кратко в README).
- Список найденных и исправленных ошибок.
- Финальная версия кода.

---

#### 6. Внедрение и развёртывание (Deployment)

**Цель этапа:** подготовить приложение к использованию.

**Активности:**
- Сборка релизной версии: `cargo build --release`.
- Проверка бинарного файла в отдельной директории.
- Создание архива с бинарником и README (опционально).
- Публикация на GitHub (если планируется открытый проект).

**Результаты этапа:**
- Готовый к использованию бинарный файл.
- Инструкция по установке и запуску.
- Репозиторий с кодом (опционально).

---

#### 7. Сопровождение (Maintenance)

**Цель этапа:** поддерживать работоспособность и развивать проект.

**Возможные активности:**
- Исправление ошибок, обнаруженных при использовании.
- Добавление новых функций: приоритеты, категории, поиск.
- Обновление зависимостей при выходе новых версий `serde` и `clap`.
- Рефакторинг кода для улучшения читаемости.
- Написание дополнительных тестов при расширении функциональности.

**План развития:**
- Версия 1.0: базовый MVP (add, list, done, remove).
- Версия 1.1: фильтрация по статусу, улучшенный вывод.
- Версия 1.2: приоритеты задач, категории.
- Версия 2.0: экспорт в Markdown/CSV, статистика.

**Результаты этапа:**
- Журнал изменений (CHANGELOG).
- Обновлённые версии приложения.
- Документация по новым функциям.

# Ключевые термины

| Термин | Определение |
|---|---|
| **Промпт-инженеринг** | Практика проектирования, тестирования и оптимизации запросов к ИИ-моделям |
| **Формула промпта** | Роль + Контекст + Задача + Ограничения + Формат вывода |
| **Роль (Persona)** | Указание модели, с позиции какого специалиста отвечать |
| **Контекст** | Вводные данные: стек, версии, фрагменты кода, требования, ограничения |
| **Ограничения** | Рамки: язык, библиотеки, стиль, длина ответа, запрещённые приёмы |
| **Формат вывода** | Явно заданная структура ответа: Markdown, JSON, только код, таблица |
| **Chain-of-Thought** | Просьба рассуждать пошагово перед ответом |
| **Few-shot** | Приёмы, когда в промпт добавляют 1–5 примеров «вход → выход» |
| **Self-consistency** | Несколько генераций на один промпт и выбор наиболее частого ответа |
| **Meta-prompting** | Сначала просить модель улучшить сам промпт, потом ответить на улучшенный |
| **User story** | Требование в форме «Как `<роль>`, я хочу `<действие>`, чтобы `<ценность>`» |
| **Acceptance Criteria** | Критерии приёмки истории, часто в формате Given–When–Then |
| **Матрица трассировки** | Таблица, связывающая каждое требование с покрывающими его тестами |
| **Edge case** | Крайний сценарий: пустой ввод, битый файл, неверный идентификатор |

# Типичные ошибки в такой работе

- ❌ **Разные промпты для разных нейросетей.** Тогда сравниваются не модели, а формулировки. Промпт должен быть максимально одинаковым — это прямое требование задания.
- ❌ **Вставлять в отчёт большие фрагменты ответов.** По заданию нужна краткая выжимка: что получилось, где ошибки и пропуски.
- ❌ **Не указывать версии моделей.** «Gemini» и «Qwen» — это семейства. Для воспроизводимости результата нужно указывать конкретную версию.
- ❌ **Оставлять чек-боксы внутри текста промпта.** Плагин задач воспринимает их как настоящие незакрытые задачи.
- ❌ **Делать вывод без аргументов.** Итоговый выбор нейросети должен опираться на баллы таблицы и на 2–3 конкретные причины, а не на общее впечатление.
