# Ход работы

## Часть А. Тестовые задания

**1.** Что такое паттерн проектирования?

а) Готовая библиотека функций.  
б) Проверенная идея для решения типовой задачи.  
в) Обязательное требование для всех проектов.  
г) Конкретный алгоритм сортировки.

> [!example]- Ответ
> **б) Проверенная идея для решения типовой задачи.** Паттерн — не код и не библиотека, а переносимый шаблон решения, который адаптируешь под конкретный язык и контекст.

**2.** Сколько категорий паттернов выделяют?

а) 2 (порождающие и структурные).  
б) 3 (порождающие, структурные, поведенческие).  
в) 4 (порождающие, структурные, поведенческие, архитектурные).  
г) 5.

> [!example]- Ответ
> **б) 3 (порождающие, структурные, поведенческие).** Так делит «Банда четырёх»; архитектурные шаблоны — другой уровень.

**3.** Какой паттерн гарантирует, что у класса только один экземпляр?

а) Фабрика.  
б) Строитель.  
в) Одиночка.  
г) Прототип.

> [!example]- Ответ
> **в) Одиночка (Singleton).** Класс сам контролирует создание и отдаёт единственную точку доступа. Часто считается спорным из-за глобального состояния.

**4.** Какой паттерн позволяет менять алгоритм на лету?

а) Наблюдатель.  
б) Стратегия.  
в) Адаптер.  
г) Фасад.

> [!example]- Ответ
> **б) Стратегия (Strategy).** Выносишь семейство алгоритмов в отдельные классы с общим интерфейсом и подменяешь их во время выполнения.

**5.** Что из перечисленного является антипаттерном?

а) Использование паттерна Стратегия для выбора алгоритма.  
б) Класс на 1000 строк, который делает всё.  
в) Вынесение повторяющегося кода в функцию.  
г) Использование Фасада для упрощения интерфейса.

> [!example]- Ответ
> **б) Класс на 1000 строк, который делает всё** — антипаттерн «Божественный объект» / «Швейцарский нож» (God Object). Нарушает единственную ответственность и KISS.

## Часть Б. Установление соответствий

| Паттерн     | Категория     | Какую проблему решает                                |
| ----------- | ------------- | ---------------------------------------------------- |
| Адаптер     | структурный   | несовместимые интерфейсы                             |
| Наблюдатель | поведенческий | уведомление всех подписчиков об изменении состояния  |
| Строитель   | порождающий   | создание объекта с множеством параметров пошагово    |
| Декоратор   | структурный   | добавить функциональность без изменения исходника    |
| Стратегия   | поведенческий | выбор подходящего алгоритма для задачи               |

## Часть В. Анализ ситуаций

**Ситуация 1.** Интернет-магазин должен уведомлять пользователей о появлении товара, на который они подписались. Какой паттерн подходит и почему?

> [!example]- Ответ
> **Наблюдатель (Observer).** Магазин — издатель, пользователи — подписчики. При изменении статуса товара издатель рассылает событие всем подписчикам, не зная их заранее и не связывая их жёстко с базой. Это снимает опрос базы и дублирование кода уведомлений.

**Ситуация 2.** Приложение для рисования позволяет применять к изображению фильтры: размытие, яркость, контраст. Пользователь может применять несколько фильтров в любом порядке. Какой паттерн подходит и почему?

> [!example]- Ответ
> **Декоратор (Decorator).** Каждый фильтр — декоратор над базовым изображением: оборачивает его, добавляет своё поведение и передаёт дальше. Комбинация собирается как цепочка `Изображение → Размытие → Яркость → Контраст` без изменения исходного класса и без взрывного числа подклассов.

**Ситуация 3.** Приложение для заказа такси должно рассчитывать стоимость поездки разными способами: по километражу, по времени, по фиксированной цене. Пользователь выбирает способ расчёта. Какой паттерн подходит и почему?

> [!example]- Ответ
> **Стратегия (Strategy).** Три алгоритма расчёта — три стратегии с общим интерфейсом `calculate(price_context)`. Контекст (заказ) хранит выбранную стратегию и вызывает её, не разветвляясь на `if/else` в каждом месте расчёта. Алгоритмы легко тестировать и подменять.

## Часть Г. Открытые вопросы на размышление

**Вопрос 1.** Объясните своими словами разницу между паттерном и антипаттерном. Приведите по одному примеру каждого.

> [!example]- Ответ
> **Паттерн** — проверенный способ строить решение, чтобы код оставался понятным и расширяемым. **Антипаттерн** — кажущееся удобным решение, которое на практике плодит проблемы.
> - Паттерн — **Фабрика**: выносишь создание разных `Software` (OpenSource/Commercial/Freemium) в одно место, клиент не знает деталей конструкторов и валидации.
> - Антипаттерн — **«Швейцарский нож» / God Object**: один класс на 1000 строк делает всё — парсит даты, валидирует, хранит Data.json и рисует UI. Нарушает единственную ответственность, ломает DRY/KISS, трудно тестировать.

**Вопрос 2.** Ваш коллега говорит: «Давай используем паттерн Фабрика для создания каждой кнопки в интерфейсе». Объясните, почему это плохая идея и когда Фабрика действительно нужна.

> [!example]- Ответ
> Для каждой отдельной кнопки со своим набором свойств фабрика избыточна: усложнит код, добавит лишний уровень абстракции без выгоды, нарушит KISS. Фабрика оправдана, когда у тебя **семейство типов с разной логикой создания** и выбор типа делается динамически.
> Пример — фигуры: `ShapeFactory.get("circle", radius=10)` или `get("rect", w=20, h=30)` возвращает нужный класс, клиент не плодит `if name == "circle": return Circle(...)` по всему коду. Аналогично в коде Software — словарь `SoftwareFactories` по ключу 1/2/3 создаёт Comercial/OpenSource/Freemium с разной валидацией.

**Вопрос 3.** Как паттерны проектирования связаны с принципами DRY и KISS? Могут ли паттерны нарушить эти принципы? Приведите пример.

> [!example]- Ответ
> Паттерны при правильном выборе **помогают** DRY (устраняют дублирование — например, Фабрика убирает повторяющиеся `if/else` по типам) и KISS (упрощают расширение — добавляешь новую Стратегию, а не усложняешь `if`). Но **неправильный** паттерн нарушает оба принципа: применить Одиночку везде создаст скрытое глобальное состояние и усложнит тесты; нагромоздить Декораторы там, где достаточен один `if`, — усложнит понимание. Критерий — нужен ли паттерн для снятия реальной сложности, а не для «красоты».

**Вопрос 4.** Придумайте свой пример из жизни (не из лекции) для любого паттерна. Опишите ситуацию, проблему и как паттерн её решает.

> [!example]- Ответ
> **Ситуация.** Учебный проект прошлого года — генерация тестовой выборки ПО из `Data.json` для проверки логики `match_InstallDate`. Нужно было случайным образом создавать объекты трёх типов: `OpenSourceSoftware` (без дат), `CommercialSoftware` (Price, InstallDate/ExpireDate) и `FreemiumSoftware` (InstallDate/TrialExpireDate), затем фильтровать их по дате запроса.
>
> **Проблема.** У каждого типа свой конструктор и правила валидации (`Validate_Price`, `Validate_Date`, `Validate_DateOrder`, `parse_date("дд.мм.гггг")`, проверка `InstallDate < ExpireDate`). Прямой код в `main()` превращался в каскад `if type == 1: parse_date(...); validate...; CommercialSoftware(...) elif type == 2: ...` — дублирование парсинга/валидации, жёсткая связность `main` с конкретными классами, сложно добавить новый тип или поменять источник данных (`SoftwareTitle`/`SoftwareManufacturer`/`Date` из JSON).
>
> **Решение — Фабричный метод / простая Фабрика.** Вынес создание в реестр фабрик:
> ```python
> SoftwareFactories: dict[int, Callable[[dict], Software]] = {
>     1: lambda data: CommercialSoftware.Date_str(..., Price=..., InstallDate_str=..., ExpireDate_str=...),
>     2: lambda data: OpenSourceSoftware(...),
>     3: lambda data: FreemiumSoftware.Date_str(...),
> }
> SoftwareList = [SoftwareFactories[randint(1,3)](data) for _ in range(n)]
> ```
> Фабричные методы `Date_str` инкапсулируют `parse_date` и валидацию, а словарь фабрик отделяет **создание** от **использования**: `main` выбирает фабрику по ключу, не зная деталей конструкторов, и легко расширяется новым типом. Фильтрация `software.match_InstallDate(date)` далее работает полиморфно через общий интерфейс `Software`.
>
> *Примечания к реализации:* в исходном примере фабрики хранят лямбды с `random.choice(data[...])` — для воспроизводимости лучше зафиксировать `random.seed` или заменить на детерминированный источник; опечатка `data["Manufacturer"]` vs `data["SoftwareManufacturer"]` в ветке OpenSource требует унификации ключей JSON.
>
> Тот же принцип на Rust можно выразить через `enum Software { OpenSource {..}, Commercial {..}, Freemium {..} }` и функцию-фабрику `fn create(kind: u8, data: &Data) -> Software`, либо через `trait SoftwareFactory`.

# Вывод

Практика закрепляет трёхступенчатую логику выбора паттерна: **категория → конкретный паттерн → обоснование через проблему**. Тесты проверяют базовые определения, таблица — связь паттерна с проблемой, ситуации — умение подобрать порождающий/структурный/поведенческий паттерн под условие, открытые вопросы — способность отличить паттерн от антипаттерна и объяснить цену/выгоду решения на примере фабрики. Собственный пример показывает, как Фабрика снимает дублирование создания и валидации разнотипных объектов и делает `main` независимым от конкретных классов.
