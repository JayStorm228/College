# 09. Структура проекта и модули

> [!abstract] О чём лекция
> Пока программа — один файл, всё просто. Но в настоящем проекте файлов десятки, и главный
> вопрос: **что где лежит и кто кого импортирует**. Здесь — структура проекта, пакеты,
> импорты, файл настроек `pyproject.toml`, конфигурация через окружение и точка входа.
>
> Лекция отвечает на вопросы, которые появляются на второй неделе работы: почему
> `ModuleNotFoundError`, куда положить данные и настройки, почему пароли не пишут в коде.

# Структура: как выглядит проект

```text
bank/
├── src/
│   └── bank/
│       ├── __init__.py     ← пакет: «здесь модули проекта»
│       ├── money.py        ← модуль: функции про деньги
│       ├── storage.py      ← модуль: сохранение
│       └── cli.py          ← вход: общение с пользователем
├── tests/
│   ├── test_money.py
│   └── test_storage.py
├── data/
│   └── sample.csv          ← данные для примеров и тестов
├── .gitignore
├── pyproject.toml          ← зависимости и настройки проекта
└── README.md               ← что это и как запускать
```

Это **src-layout**: код лежит в `src/`, рядом — тесты, данные и файлы проекта. Плюсы:
тесты импортируют пакет так же, как пользователь, а не «случайно из текущей папки».

Есть и обратная сторона: Python не ищет модули внутри `src/` сам, и без подготовки
получится `ModuleNotFoundError: No module named 'bank'`. Способов два:

- **для учёбы** — сказать Python, где искать: `PYTHONPATH=src python3 main.py`
  (в PowerShell: `$env:PYTHONPATH = "src"`, затем `python main.py`); для `pytest` то же
  задаёт строка `pythonpath = ["src"]` в разделе `[tool.pytest.ini_options]` файла
  `pyproject.toml`;
- **для настоящего проекта** — описать в `pyproject.toml` сборку пакета (раздел
  `[build-system]`; проект, созданный командой `uv init --package`, уже устроен так)
  и установить проект в окружение: тогда `uv sync` ставит пакет `bank` в `.venv`,
  и он импортируется откуда угодно.

Пакет отличается от обычной папки файлом `__init__.py` (в новых версиях Python он
не обязателен, но он явно говорит «это пакет» и служит местом для общих экспортов).

# Импорты

```python
# src/bank/money.py
"""Работа с деньгами."""


def rubles(amount: float) -> str:
    """Форматирует сумму по-русски: 1234.5 → «1234.50 руб.»."""
    return f"{amount:.2f} руб."
```

```python
# src/bank/report.py
"""Отчёты по операциям."""
from bank.money import rubles


def total_line(operations: list[float]) -> str:
    """Строка «Итого» по списку операций."""
    return f"Итого: {rubles(sum(operations))}"
```

```python
# main.py
from bank import report

print(report.total_line([100.5, 250, 12.25]))
```

```text
Итого: 362.75 руб.
```

Правила импортов, которые стоит держать в голове:

| Правило | Почему |
|---|---|
| сначала стандартная библиотека, потом сторонние, потом свои | так принято (PEP 8), и видно, от чего зависит модуль |
| `from bank.money import rubles` — конкретные имена | `from bank.money import *` скрывает, откуда что взялось |
| не импортировать «через папку вверх» (`from ..utils import ...`) в прикладном коде | ломается при запуске файла напрямую |
| импорт не должен выполнять работу | при импорте модуля код не должен печатать, писать файлы и ходить в сеть |

Последний пункт можно сформулировать так: **импорт ничего не делает**. Вся работа
выполняется в функциях, а вызов — в точке входа:

```python
def main() -> None:
    """Точка входа: вся работа программы."""
    print("Программа запущена")


if __name__ == "__main__":
    main()
```

Этот приём уже знаком из курса Python: при импорте модуля `main()` не выполняется.

# `pyproject.toml`: паспорт проекта

Один файл описывает проект: имя, версию Python, зависимости, инструменты разработки.

```toml
[project]
name = "bank"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["numpy>=2.4.2", "pandas>=2.0,<3.0"]

[dependency-groups]
dev = ["black>=26.1.0", "ruff>=0.15.2"]
```

Читается как оглавление: что это за проект, на какой версии Python работает, что нужно
для работы и что — для разработки. Зависимости и версии — как в [[05. Сторонние библиотеки]].

# Конфигурация: настройки отдельно от кода

Правило: **в коде нет паролей, адресов и путей к чужим данным**. Они приходят из окружения:

```bash
# .env — локальные настройки, в git НЕ попадает
DATABASE_URL=postgres://user:pass@localhost/bank
DEBUG=true
```

```python
# src/bank/config.py
import os
from dataclasses import dataclass


@dataclass
class Config:
    """Настройки приложения, собранные из переменных окружения."""

    database_url: str
    debug: bool

    @classmethod
    def from_env(cls) -> "Config":
        """Читает настройки из окружения; понятно падает, если чего-то нет."""
        url = os.environ.get("DATABASE_URL")
        if not url:
            raise RuntimeError("не задан DATABASE_URL: проверь .env")
        return cls(database_url=url, debug=os.environ.get("DEBUG", "") == "true")


if __name__ == "__main__":
    print(Config.from_env())
```

Ожидаемый вывод при заданных переменных:

```text
Config(database_url='postgres://user:pass@localhost/bank', debug=True)
```

Важная деталь: Python **сам не читает файл `.env`** — `os.environ` содержит только те
переменные, которые задали при запуске. Поэтому программу запускают одним из способов:

```bash
# bash, macOS, Linux: переменные — прямо в команде
DATABASE_URL=postgres://user:pass@localhost/bank DEBUG=true python3 config.py

# PowerShell (Windows)
$env:DATABASE_URL = "postgres://user:pass@localhost/bank"; $env:DEBUG = "true"; python config.py

# uv читает файл .env сам
uv run --env-file .env python config.py
```

Загружать `.env` изнутри программы умеют библиотеки: маленькая `python-dotenv` и
`pydantic-settings` из курса [[00. Pydantic]], который заодно проверяет значения. Без переменной `DATABASE_URL` запуск закончится сообщением
`RuntimeError: не задан DATABASE_URL: проверь .env` — как и задумано.

Почему так, а не константы в коде:

| Настройки в коде | Настройки в окружении |
|---|---|
| пароль попадает в git | секрет остаётся у владельца |
| одна версия настроек для всех | у каждого своё окружение (локально, тест, сервер) |
| чтобы поменять адрес, нужна правка кода | достаточно поменять переменную и перезапустить |

Рядом с `.env` в репозиторий кладут `.env.example` — те же имена без значений:
по нему новый человек понимает, что нужно задать. Проверку настроек удобно поручать
Pydantic ([[00. Pydantic]]): он сам скажет, чего не хватает и где ошибка.

# Как это делают в проекте

1. **Код, тесты и данные разделены.** Данные для тестов — небольшие файлы в `data/`,
   большие данные — не в репозитории.
2. **Точка входа одна.** `main()` в отдельном модуле: её легко найти и запустить.
3. **Настройки — через окружение, с проверкой при старте.** Если `DATABASE_URL` не задан,
   программа падает сразу и с понятным сообщением, а не через час работы.
4. **Структура повторяет предметную область.** Если появилось 20 модулей «про всё»,
   пора разложить их по папкам (`bank/operations/`, `bank/reports/`).
5. **README отвечает на два вопроса:** что это и как запустить. Остальное — в коде и docstring.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Пока проект маленький, структура не нужна» | Два-три модуля — уже пора: перекладывать потом дороже |
| «`__init__.py` обязателен» | Формально нет, но он отмечает пакет и удобен для общих экспортов |
| «Настройки можно хранить в константах» | Только не секреты и не то, что меняется между окружениями |
| «`ModuleNotFoundError` — ошибка Python» | Почти всегда это неверный путь запуска или отсутствующий пакет |
| «Импорт — бесплатная операция» | Модуль выполняется при импорте: тяжёлая работа на верхнем уровне замедляет всё |

# Проверь себя

1. Чем пакет отличается от обычной папки с файлами?
2. Почему работу выполняют в `main()`, а не при импорте?
3. Что описывает `pyproject.toml`?
4. Почему `.env` не коммитят и что кладут вместо него?
5. Что делать, если настройка не задана, — работать «на значениях по умолчанию»?
6. Почему `from bank.money import *` — плохая привычка?

> [!success]- Ответы
> 1. Пакет — папка, которую Python умеет импортировать целиком: `from bank import ...`.
>    Его отмечает файл `__init__.py` (в новых версиях Python он не обязателен, но явно
>    говорит «это пакет» и служит местом для общих экспортов).
> 2. Чтобы импорт модуля не запускал программу: тесты и другие модули смогут использовать
>    функции, не выполняя работу.
> 3. Имя проекта, версию Python, зависимости и инструменты разработки — паспорт проекта.
> 4. В нём секреты и локальные значения. Вместо него — `.env.example` с именами без значений.
> 5. Нет: настройки проверяют при старте и падают с понятным сообщением. Молчаливое значение
>    по умолчанию для пароля или адреса базы — источник странных ошибок в работе.
> 6. Не видно, откуда взялось имя, и легко перекрыть своё чужое: например, своё `sum`
>    вместо встроенного.
