# 17. Датаклассы — когда и как, и где дополняет Pydantic

> [!abstract] О чём лекция
> В базовом курсе [[16. Объектно-ориентированное программирование]] `@dataclass` — короткий способ хранить данные без ручного `__init__`/`__repr__`. Здесь — глубоко для грамотного разработчика: полный набор настроек (`frozen`, `slots`, `kw_only`, `order`), `field`, `__post_init__`, сравнение с `namedtuple` и обычным классом, и честный ответ, где заканчивается `dataclass` и начинается `Pydantic`.
> **Ключевая мысль:** `dataclass` — «класс как запись» без валидации при парсинге; `Pydantic` дополняет его, когда данные приходят извне и нужна проверка.

> [!tip] Что нужно знать заранее
> [[16. Объектно-ориентированное программирование]] — `__init__`, `__repr__`, `@property`, `field(default_factory=list)`; [[02. Типизация и аннотации]] — `name: str` как подсказка. Вся магия здесь — расширение знакомого.

---

# База — что уже было, но напомним

```python
from dataclasses import dataclass, field

@dataclass
class Student:
    name: str
    group: str
    scores: list = field(default_factory=list)

    def __post_init__(self):
        if not self.name.strip():
            raise ValueError("имя не может быть пустым")

    @property
    def average(self) -> float:
        return sum(self.scores) / len(self.scores) if self.scores else 0.0

s = Student("Аня", "П-21", [5, 4, 5])
print(s)          # Student(name='Аня', group='П-21', scores=[5, 4, 5])
print(s.average)  # 4.666...
```

Что делает декоратор: генерирует `__init__`, `__repr__`, `__eq__` по полям. Без него то же — 20 строк руками.

# `field` — тонкая настройка поля

```python
from dataclasses import dataclass, field

@dataclass
class Item:
    name: str
    price: float
    tags: list = field(default_factory=list)          # не `[]`! Иначе один список на всех
    secret: str = field(repr=False, compare=False, default="")  # не показывать и не сравнивать
    created: float = field(init=False, default=0.0)   # не в __init__, заводится позже
```

| Параметр `field` | Зачем |
|---|---|
| `default` / `default_factory` | значение по умолчанию; `list` — только через `factory` |
| `init=False` | поле не попадает в `__init__` — его ставит `__post_init__` или метод |
| `repr=False` | не показывать в `repr` (секреты, большие поля) |
| `compare=False` | не участвует в `==` (кэш, `id`) |
| `hash=False` | не участвует в `hash` (если класс `frozen`) |
| `kw_only=True` | только именованным аргументом `name="..."` (Python 3.10+) |
| `metadata={}` | место для своих пометок (не влияет на поведение) |

> [!warning] Ловушка изменяемого значения
> `tags: list = []` — один список на все объекты, как и в функциях (`def f(items=[])`). Всегда `field(default_factory=list)`.

# Настройки декоратора — когда датакласс ведёт себя как «значение»

```python
@dataclass(frozen=True, slots=True, order=True, kw_only=True)
class Point:
    x: float
    y: float
```

| Опция | Смысл |
|---|---|
| `frozen=True` | объект неизменяемый: `p.x = 1` → `FrozenInstanceError`. Можно хешировать и класть в `set`/`dict` как ключ. |
| `slots=True` | без `__dict__`: экономит память и быстрее доступ (важно для миллионов объектов) |
| `order=True` | генерирует `<, <=, >, >=` по полям по порядку — для сортировки |
| `kw_only=True` | все поля только `name=value` — меньше путаницы при многих полях |
| `eq=True` (по умолчанию) | сравнение по полям (`==`) |
| `repr=True` (по умолчанию) | печать как `Point(x=1, y=2)` |

Нюанс `frozen + slots`: самый экономный и безопасный «значение-объект», как `Point` из `namedtuple`, но с методами и проверкой.

# `__post_init__` — проверки и производные поля

```python
from dataclasses import dataclass, field

@dataclass
class Circle:
    radius: float
    area: float = field(init=False)

    def __post_init__(self):
        if self.radius <= 0:
            raise ValueError("радиус должен быть > 0")
        self.area = 3.14 * self.radius ** 2  # производное, не в init

c = Circle(5)
print(c.area)  # 78.5
```

Правило: **что можно проверить сразу — проверяй в `__post_init__`**, а не «где-то потом».

# `dataclass` vs `namedtuple` vs обычный класс

| Вопрос | `dataclass` | `namedtuple` | Обычный класс |
|---|---|---|---|
| Изменяемость | по выбору (`frozen`) | неизменяемый | изменяемый |
| Память | `slots=True` — экономно | экономно | `__dict__` |
| Методы/`@property` | да | почти нет | да |
| Значения по умолчанию/`field` | да, гибко | ограничено | руками |
| Наследование/проверки | да | почти нет | да |

Для «просто запись» `Point(x,y)` `namedtuple` ещё короче, но как только нужны проверка, `@property` или `default_factory` — бери `dataclass`.

# Где дополняет Pydantic — честно и коротко

В этом модуле — **только** `dataclass`, со ссылкой, что `Pydantic` существует и расширяет возможности. Подробное сравнение — в курсе `03. Pydantic/08. Альтернативы и место Pydantic`, здесь развязка:

| Задача | `dataclass` | `Pydantic` |
|---|---|---|
| Проверка при запуске от тебя | `__post_init__` руками | есть: `field_validator`, `model_validator`, типы `PositiveInt`, `EmailStr` |
| Парсинг внешних данных (`"17"` → `17`, `{"a":1}` → объект) | нет, руками | да: `Model.model_validate({...})`, `model_validate_json(...)` |
| Сообщения об ошибках с путём к полю | руками | да: `ValidationError` с `loc` |
| JSON (`dump`/`load`) | `asdict`/`astuple` + `json` руками | `model_dump()` / `model_dump_json()` |
| Настройки из `.env` | руками | `pydantic-settings` |

Пример границы:

```python
from dataclasses import dataclass

@dataclass
class UserDC:
    name: str
    age: int
    # UserDC(age="17") — запустится, age будет строкой "17" (типы не проверяются)

# --- то же как Pydantic (в курсе Pydantic) ---
from pydantic import BaseModel, ValidationError

class UserMD(BaseModel):
    name: str
    age: int

try:
    u = UserMD(name="Аня", age="17")  # парсит "17" -> 17
    print(u)  # name='Аня' age=17
    UserMD(name="Аня", age="семнадцать")  # упадёт с ValidationError
except ValidationError as e:
    print(e)
```

> [!tip] Когда переходить
> Пока данные создаёшь ты в коде — достаточно `dataclass`. Как только данные приходят **извне** (форма, файл, API) и нужна проверка/парсинг — бери `Pydantic` (он дополняет, а не заменяет `dataclass`).

# Хорошие практики

1. **Не храни изменяемое как `field(default=[])` — только `default_factory`.**
2. **Держи `__post_init__` коротким:** проверки и одно-два производных поля; сложную логику — в методы/`@classmethod from_dict`.
3. **Для значений — `frozen=True` + `slots=True`.** Так объект ведёт себя как число/точка и экономит память.
4. **Скрывай внутреннее `repr=False, compare=False`.** Пароли, кэши, «сырые» поля — не в `repr` и не в `==`.
5. **Не смешивай валидацию.** В `dataclass` — только то, что можно проверить без парсинга; всё, что требует парсинга строки → число, вынеси в `Pydantic`.

---

# Типичные заблуждения

- ❌ **«`dataclass` проверяет типы»** — нет, аннотация `age: int` — подсказка для `mypy`, запуск с `"17"` не упадёт.
- ❌ **«`frozen=True` делает глубокий `frozen`»** — только сам объект, вложенный `list` внутри остаётся изменяемым.
- ❌ **«`slots=True` всегда быстрее»** — на парe объектов разница не заметна; выигрыш на миллионах.
- ❌ **«`Pydantic` — замена `dataclass`»** — дополняет там, где нужен парсинг/валидация внешних данных; внутри программы `dataclass` легче и быстрее.

# Ключевые термины

| Термин | Определение |
|---|---|
| **`@dataclass`** | декоратор-класс-хранилище: генерирует `__init__`/`__repr__`/`__eq__` |
| **`field`** | описание поля: значение по умолчанию, участие в `repr`/`compare` |
| **`__post_init__`** | проверки сразу после `__init__` |
| **`frozen` / `slots`** | неизменяемость / экономия памяти |
| **`namedtuple`** | лёгкая неизменяемая запись без методов |
| **`Pydantic`** | дополнение для проверки/парсинга внешних данных (отдельный курс) |

# Проверь себя

1. Чем `field(default_factory=list)` отличается от `scores: list = []`?
2. Что даёт `frozen=True` и почему `tags: list` внутри остаётся изменяемым?
3. Когда выбрать `dataclass`, а когда уже `Pydantic`?
4. Для чего `__post_init__`?
5. Как не показывать поле `secret` в `print(obj)`?

> [!example]- Ответы
> 1. Первое создаёт новый список для каждого объекта, второе — один общий на всех (ловушка).
> 2. Запрещает менять поля объекта; вложенный список — отдельный объект, его защита не касается (нужен `tuple` или своё).
> 3. `dataclass` — когда данные создаёшь ты и проверки простые; `Pydantic` — когда данные приходят извне и нужен парсинг/ValidationError.
> 4. Проверить данные и посчитать производные поля сразу после создания.
> 5. `secret: str = field(repr=False, compare=False)`.
