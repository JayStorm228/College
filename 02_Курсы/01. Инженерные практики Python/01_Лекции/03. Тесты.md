# 03. Тесты

> [!abstract] О чём лекция
> Тест — это код, который проверяет код. Он нужен не «для галочки»: тест позволяет менять программу и **знать**, что не сломал старое. В курсе Python все проверки делались руками: запустил, посмотрел на вывод, сверил с ответом. Здесь то же самое превращается в автоматическую проверку, которую можно запустить одной командой — хоть сто раз.
>
> Ключевая мысль: писать тест **до** или **вместе** с кодом дешевле, чем отлаживать
> программу целиком.

# От `assert` к `pytest`

Минимальный тест — это утверждение (`assert`): «результат должен быть таким».

```python
def rubles(amount):
    return f"{amount:.2f} руб."


assert rubles(100) == "100.00 руб."
assert rubles(0) == "0.00 руб."
print("проверки прошли")
```

```text
проверки прошли
```

Работает — но при ошибке непонятно, что именно пошло не так и сколько проверок упало.
Поэтому проверки оформляют как **тестовые функции** и запускают через `pytest`:

```python
import pytest


class BalanceError(Exception):
    """Не хватает денег на счёте."""


def withdraw(balance, amount):
    """Снимает сумму со счёта или объясняет, почему нельзя."""
    if amount <= 0:
        raise ValueError("сумма должна быть положительной")
    if amount > balance:
        raise BalanceError("недостаточно средств")
    return balance - amount


def test_withdraw_reduces_balance():
    assert withdraw(100, 30) == 70


def test_withdraw_whole_balance():
    assert withdraw(50, 50) == 0


@pytest.mark.parametrize("amount", [0, -1, -100])
def test_withdraw_rejects_non_positive(amount):
    with pytest.raises(ValueError):
        withdraw(100, amount)


def test_withdraw_more_than_balance():
    with pytest.raises(BalanceError, match="недостаточно"):
        withdraw(100, 250)
```

```text
......                                                                   [100%]
6 passed in 0.01s
```

Установка и запуск:

```bash
uv add --dev pytest     # тесты нужны только разработчику, поэтому --dev
uv run pytest -q        # -q — короткий вывод
```

# Правила, из которых состоит pytest

| Правило | Смысл |
|---|---|
| файл называется `test_*.py` | `pytest` сам находит тесты по имени |
| функция называется `test_*` | то же — для функций внутри файла |
| проверка — обычный `assert` | не нужно учить специальные методы `assertEqual` |
| одно поведение — один тест | упавший тест сразу говорит, **что** сломалось |
| имя теста описывает ожидание | `test_withdraw_rejects_non_positive` читается как требование |

Полезные инструменты:

- `pytest.raises(Тип)` — проверяет, что функция **падает** нужной ошибкой. Это тоже поведение,
  и его нужно тестировать;
- `match="текст"` — проверяет, что сообщение содержит нужные слова;
- `@pytest.mark.parametrize` — один тест на несколько наборов данных: не надо копировать
  четыре почти одинаковые функции;
- фикстуры (`@pytest.fixture`) — общая подготовка: временная папка, объект, тестовые данные.

```python
import pytest


@pytest.fixture
def balance():
    """Счёт, с которого начинают тесты."""
    return 100


def test_withdraw_from_fixture(balance):
    assert withdraw(balance, 30) == 70
```

# Что тестировать в первую очередь

1. **Границы.** Пустой список, ноль, отрицательное число, максимальное значение.
   Для `withdraw` это `amount=0`, `amount == balance`, `amount > balance`.
2. **То, что уже ломалось.** Нашли баг — сначала тест, который его повторяет («красный»), потом правка, после которой он становится «зелёным». Так баг не вернётся.
3. **Чистые функции.** Функция, которая считает и возвращает, тестируется тривиально: данные пришли, результат сравнили. Именно поэтому в курсе столько раз повторялось «считает и возвращает, а печатает — вызывающий код».
4. **Разбор данных.** Функция чтения файла проверяется на строке, на пустом файле
   и на битой строке.

Тесты, которые **не** нужны: «тест на то, что язык работает» (`assert 1 + 1 == 2`),
тест без проверки (`def test_x(): withdraw(100, 30)` — падения нет, смысла нет),
тест, который проверяет реализацию, а не поведение (сравнение внутреннего списка вместо результата).

# Красный — зелёный — рефакторинг

Так выглядит рабочий цикл разработки через тесты:

| Шаг | Что делаешь | Что видишь |
|---|---|---|
| 1. Красный | пишешь тест на ещё не написанное поведение | тест падает — так и должно быть |
| 2. Зелёный | пишешь простейший код, который прошёл тест | 6 passed |
| 3. Рефакторинг | улучшаешь код, не меняя поведение | тесты остаются зелёными |

Смысл не в ритуале, а в **страховке**: на шаге 3 тебе не страшно трогать код, потому что у тебя есть автоматическая проверка. Без тестов рефакторинг — это лотерея.

> [!warning] Тест, который всегда зелёный, бесполезен
> Если тест не может упасть, он ничего не проверяет. Убедись, что он «краснеет»: сломай функцию нарочно и запусти тесты. Прошло — значит, тест написан неправильно.

# Как это делают в проекте

1. **Тесты лежат рядом с кодом** (папка `tests/`) и запускаются одной командой. В этом репозитории автотесты уже включены в редакторе: `"python.testing.pytestEnabled": true`.
2. **Тесты пишут на поведение**, а не на устройство: «при снятии больше остатка — ошибка», а не «внутри используется список операций».
3. **Тесты — часть правки.** Нашли баг — принесли тест на баг; добавили возможность — принесли тест на неё. Ревью без тестов задаёт вопрос: «как проверить, что не сломается?»
4. **Медленные вещи подменяют.** Файлы, сеть, время: вместо настоящего файла — временная папка, вместо сервиса — подделка. Это ровно то, о чём следующая лекция про зависимости.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Тесты писать дольше, чем код» | Первые тесты — да, потом они экономят часы отладки. Баг, найденный тестом, дешевле бага у пользователя |
| «Тесты нужны только в больших проектах» | Учебная задача с тестом делается быстрее: не надо каждый раз вводить данные руками |
| «100 % покрытия — цель» | Цель — покрыть **важные** случаи: границы, ошибки, разбор данных |
| «Тест можно написать после всего» | Можно, но тогда он повторяет код и повторяет его ошибки |
| «Тесты мешают менять код» | Мешают менять **поведение** — и это их работа |

# Проверь себя

1. Почему тест-функция лучше, чем набор `assert` в конце файла?
2. Как проверить, что функция падает с нужной ошибкой?
3. Что такое `parametrize` и зачем он нужен?
4. Какой тест вы напишете первым, если ищете ошибку в разборе файла?
5. Зачем убеждаться, что новый тест «краснеет»?
6. Почему чистая функция (считает и возвращает) тестируется легче?

> [!success]- Ответы
> 1. Видно, какая именно проверка упала, сколько их всего, и их можно запускать выборочно
>    (`uv run pytest тест_файл.py`).
> 2. `with pytest.raises(ТипОшибки):` вокруг вызова; при желании — с `match="часть текста"`.
> 3. Способ запустить один тест на нескольких наборах данных: меньше копий и видно,
>    на каком наборе упало.
> 4. На границе: пустой файл, строка без нужного разделителя, файл с одной записью.
> 5. Если тест не может упасть, он не проверяет ничего: зелёный результат ничего
>    не говорит о коде.
> 6. Ей не нужен ни ввод, ни файл, ни экран: передал данные — сравнил результат.
