# 07. Внедрение зависимостей

> [!abstract] О чём лекция
> Внедрение зависимостей (dependency injection, DI) звучит как что-то из больших фреймворков,
> но идея простая: **класс не создаёт то, чем пользуется, а получает это снаружи**.
>
> Зачем: класс, который сам создаёт файл, базу или «текущее время», невозможно проверить
> в тесте и невозможно переиспользовать. Как только зависимость приходит извне, всё
> становится подменяемым — и код превращается из «жёстко сшитого» в гибкий.

# Проблема: объект создаёт своих помощников

```python
from pathlib import Path


class Report:
    """Отчёт, который сам пишет себя в файл."""

    def __init__(self, title):
        self.title = title

    def publish(self, body):
        Path("report.txt").write_text(f"{self.title}\n{body}", encoding="utf-8")
        return "записано в report.txt"
```

Что здесь неудобно:

- **тест пишет настоящий файл.** Проверка меняет диск, а файлы между тестами мешают друг другу;
- **путь зашит внутрь.** Чтобы сохранять в другую папку или в память, нужно править класс;
- **нет подмены.** Проверить, «что именно сохранили», можно только прочитав файл целиком.

# Решение: зависимость приходит в конструктор

```python
from pathlib import Path


class FileStorage:
    """Настоящее хранилище: пишет в файл."""

    def __init__(self, path):
        self.path = Path(path)

    def save(self, text):
        self.path.write_text(text, encoding="utf-8")
        return f"записано в {self.path.name}"


class MemoryStorage:
    """Подделка для тестов: держит текст в памяти."""

    def __init__(self):
        self.saved = []

    def save(self, text):
        self.saved.append(text)
        return "записано в память"


class Report:
    """Отчёт не знает, куда его сохранят, — хранилище передали снаружи."""

    def __init__(self, title, storage):
        self.title = title
        self.storage = storage

    def publish(self, body):
        return self.storage.save(f"{self.title}\n{body}")


print(Report("Продажи", MemoryStorage()).publish("Аня 5\nБорис 4"))
print(Report("Продажи", FileStorage("/tmp/eng/report.txt")).publish("Аня 5\nБорис 4"))
print(Path("/tmp/eng/report.txt").read_text(encoding="utf-8"))
```

```text
записано в память
записано в report.txt
Продажи
Аня 5
Борис 4
```

Разбор:

| Кто | Что делает | Зависит от |
|---|---|---|
| `Report` | формирует текст и публикует | только от того, что у хранилища есть `save` |
| `FileStorage` | пишет в файл | от `pathlib` |
| `MemoryStorage` | хранит строки в списке | ни от чего |

`MemoryStorage` — не «игрушка», а рабочий инструмент: в тестах вместо настоящего хранилища
передают его, и тест становится быстрым и предсказуемым.

```python
def test_report_publishes_text():
    storage = MemoryStorage()
    Report("Продажи", storage).publish("Аня 5")
    assert storage.saved == ["Продажи\nАня 5"]
```

```text
1 passed in 0.00s
```

Тест проверяет **результат работы** отчёта, не касаясь диска. Это и есть главный выигрыш DI.

# Что считается зависимостью

Зависимость — всё, что класс или функция берут «из внешнего мира»:

| Зависимость | Почему её передают снаружи |
|---|---|
| файлы и папки | в тесте — временная папка, а не рабочие данные |
| сеть и API | в тесте — подделка, реальный запрос медленный и нестабильный |
| база данных | в тесте — база в памяти или заглушка |
| время и случайность | иначе результат каждый запуск разный |
| вывод (`print`) | в тесте перехватывают, в работе пишут в лог |
| другие классы проекта | подменяются на «упрощённые» версии |

Время выглядит безобидно, но именно оно делает тесты нестабильными:

```python
from datetime import datetime


class FixedClock:
    """Часы с фиксированным временем — для тестов."""

    def __init__(self, hour):
        self.hour = hour

    def now(self):
        return datetime(2026, 9, 26, self.hour, 0, 0)


class Timetable:
    """Расписание: зависит от часов, но не создаёт их."""

    def __init__(self, clock):
        self.clock = clock

    def greeting(self):
        hour = self.clock.now().hour
        if hour < 12:
            return "Доброе утро"
        if hour < 18:
            return "Добрый день"
        return "Добрый вечер"


for hour in (7, 12, 20):
    print(f"{hour}:00 → {Timetable(FixedClock(hour)).greeting()}")
```

```text
7:00 → Доброе утро
12:00 → Добрый день
20:00 → Добрый вечер
```

В работе в `Timetable` передают настоящие часы (`Clock` с `datetime.now()`), а в тестах —
`FixedClock` с любым часом. Тест на «Доброе утро» тогда проходит и утром, и вечером.

Тест с `FixedClock` даёт один и тот же результат и утром, и ночью. Без этого тест
«Доброе утро» проходил бы только до полудня — классический пример нестабильного теста.

> [!note] Как не усложнить
> Не нужно делать DI «везде». Передавать снаружи стоит **то, что мешает тестировать
> или меняется**: файлы, время, сеть, внешние сервисы. Простой класс с чистой логикой
> (`Rectangle`, `Triangle` из практик) ничего не создаёт — ему DI не нужен.

# Как это выглядит в больших проектах

| Подход | Как выглядит | Когда |
|---|---|---|
| Параметр конструктора | `Report(title, storage)` | самое частое в коде |
| Параметр функции | `def save(report, storage)` | для функций без класса |
| Протокол / интерфейс | `class Storage(Protocol): def save(...)` | когда подмен много и хочется типов |
| Контейнер зависимостей | библиотека (например, `dependency-injector`) | большие приложения; для учёбы рано |

В Django DI проявляется как «настройки и подключения»: `settings`, соединение с базой,
кэш — всё это подставляется фреймворком, а не создаётся внутри представления.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «DI — это библиотека» | Это приём: передавать зависимости параметром. Библиотеки лишь автоматизируют сборку |
| «DI усложняет код» | Один параметр вместо строки внутри класса. Сложнее становится **меньше** |
| «Наследование решает то же самое» | Наследник всё ещё создаёт зависимость сам; подмена через наследование — это подмена класса, а не поведения |
| «Нужно передавать вообще всё» | Только то, что мешает тестам и меняется в работе |
| «Подделки опасны: тест проверяет не то» | Опасны подделки, повторяющие логику. Подделка-«записная книжка» проверяет взаимодействие, а логику проверяют на настоящей реализации |

# Как это делают в проекте

1. **Зависимости передают в конструктор** — и почти всегда с значением по умолчанию нет:
   явный параметр виден в сигнатуре.
2. **В тестах — подделки, в работе — настоящие объекты.** Сборка («что с чем соединить»)
   живёт в одном месте: в точке входа программы.
3. **Зависимости не прячут в глобальных переменных.** Глобальное состояние — главный враг
   тестов: его нельзя подменить и трудно сбросить.
4. **Границы — по смыслу.** Класс с бизнес-логикой не знает про файлы и базы: этим занимаются
   те, кого ему передали.

# Проверь себя

1. Что такое зависимость класса, если говорить просто?
2. Что становится возможным, когда хранилище передают в конструктор?
3. Почему время — тоже зависимость?
4. Когда DI не нужен?
5. Чем подделка для тестов отличается от «второй реализации» логики?
6. Как в Django проявляется та же идея?

> [!success]- Ответы
> 1. То, чем класс пользуется, но не создаёт сам: файлы, время, сеть, другие объекты.
> 2. Подмена: в тестах — хранилище в памяти, в работе — файл; класс не меняется.
> 3. Потому что от него зависит результат: тесты с настоящим временем падают
>    в разное время суток.
> 4. Когда объект ничего не создаёт и не зависит от внешнего мира: чистая логика.
> 5. Подделка хранит или считает вызовы (проверяет взаимодействие), а не повторяет
>    правила предметной области.
> 6. Настройки, соединение с базой и кэш подставляет фреймворк: представление их не создаёт.
