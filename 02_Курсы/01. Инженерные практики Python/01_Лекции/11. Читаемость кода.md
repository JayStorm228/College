# 11. Читаемость кода

> [!abstract] О чём лекция
> Код читают в десятки раз чаще, чем пишут. Значит, важны не «украшения», а два простых
> правила: **стиль одинаковый у всей команды** и **всё, что можно проверить машиной,
> проверяет машина**.
>
> В лекции — соглашение PEP 8, форматтер `black`, линтер `ruff` и несколько приёмов
> читаемости на уровне кода: имена, ранние выходы, магические числа.

# PEP 8 в объёме, который нужен каждый день

PEP 8 — официальное соглашение о стиле Python. Запоминать целиком не нужно: большую часть
работы делают инструменты. Что стоит держать в голове:

| Что | Как |
|---|---|
| имена переменных и функций | `snake_case`: `total_sum`, `read_numbers` |
| имена классов | `CamelCase`: `MemoryStorage`, `ReportBuilder` |
| константы | `UPPER_CASE`: `MAX_RETRIES`, `TAX_RATE` |
| отступ | 4 пробела, не табуляция |
| длина строки | 88 символов (современная практика) или 79 (классический PEP 8) |
| пробелы | вокруг операторов и после запятой: `a + b`, `f(x, y)` |
| импорты | сверху, группами: стандартная библиотека, сторонние, свои |
| пустые строки | между функциями — пустая строка, вокруг классов — две |

Имена важнее причёсанных отступов: `d` и `data2` не спасут даже идеально
отформатированный код.

# black: формат делает машина

`black` приводит код к одному виду и не спрашивает мнения: стиль либо его, либо никакой.
Установка и запуск:

```bash
uv add --dev black ruff      # добавить инструменты в проект
uv run black .               # отформатировать весь проект
uv run black --check .       # проверить, не меняя файлы (для CI)
```

Посмотрим, что он делает с «грязным» файлом:

```python
import os
import json


def make_report(title,rows):
    '''Отчёт'''
    result=""
    for r in rows:
        if r[1]==None:
            continue
        result=result+str(r[0])+": "+str(r[1])+"\n"
    if title == None: return result
    return title.upper() + "\n" + result


print(make_report("Продажи",[["Аня",5],["Игорь",None]]))
```

```text
$ black --check report.py
would reformat report.py

Oh no! 💥 💔 💥
1 file would be reformatted.
```

Правки формата, которые он вносит (фрагмент `black --diff`):

```diff

-    '''Отчёт'''
-    result=""
+def make_report(title, rows):
+    """Отчёт"""
+    result = ""
     for r in rows:
-        if r[1]==None:
+        if r[1] == None:
             continue
-        result=result+str(r[0])+": "+str(r[1])+"\n"
-    if title == None: return result
+    if title == None:
+        return result
     return title.upper() + "\n" + result
```

`black` выровнял пробелы, разбил `if ...: return ...` на две строки, заменил кавычки
docstring на двойные. Обрати внимание: **смысл кода он не меняет.** `r[1] == None`
(сравнение с `None`) так и осталось — это работа линтера.

# ruff: линтер ищет проблемы

`ruff` проверяет не вид, а ошибки и подозрительные места:

```bash
uv run ruff check .          # проверить проект
uv run ruff check --fix .    # исправить то, что безопасно исправлять автоматически
```

```text
$ ruff check --select "E,F,I,UP" report.py
report.py:1:1: I001 [*] Import block is un-sorted or un-formatted
report.py:1:8: F401 [*] `os` imported but unused
report.py:2:8: F401 [*] `json` imported but unused
report.py:9:18: E711 Comparison to `None` should be `cond is None`
report.py:12:17: E711 Comparison to `None` should be `cond is None`
report.py:12:21: E701 Multiple statements on one line (colon)
Found 6 errors.
[*] 3 fixable with the `--fix` option (2 hidden fixes can be enabled with the `--unsafe-fixes` option).
```

Что здесь видно: неиспользуемые импорты, сравнение с `None` через `==` (нужно `is`),
два оператора в одной строке. Часть помечена `[*]` — исправимо автоматически.

Формат и смысл — разные обязанности, поэтому инструмента и два:

| Инструмент | Отвечает за | Ловит |
|---|---|---|
| `black` | вид кода | пробелы, переносы, кавычки |
| `ruff` | ошибки и подозрительные места | лишние импорты, сравнения, неиспользуемые имена |

# Как выглядит код после исправлений

```python
def make_report(title, rows):
    """Собирает отчёт: по строке на запись."""
    lines = []
    for name, mark in rows:
        if mark is None:
            continue
        lines.append(f"{name}: {mark}")
    body = "\n".join(lines)
    if title is None:
        return body
    return f"{title.upper()}\n{body}"


if __name__ == "__main__":
    print(make_report("Продажи", [["Аня", 5], ["Игорь", None]]))
```

```text
ПРОДАЖИ
Аня: 5
```

```text
$ black --check report_clean.py
(код возврата 0, без сообщений)
$ ruff check --select "E,F,I,UP,B" report_clean.py
All checks passed!
```

Что изменилось по существу, а не по виду:

| Было | Стало | Почему лучше |
|---|---|---|
| `for r in rows`, `r[0]`, `r[1]` | `for name, mark in rows` | имена объясняют, что где лежит |
| `result = result + str(...) + ...` | `f"{name}: {mark}"` | читается как фраза, без склеек |
| `if mark == None: continue` внутри большого тела | ранний выход `continue` наверху | основная логика не прячется в отступе |
| `print(...)` на верхнем уровне | вызов в `if __name__ == "__main__":` | модуль можно импортировать ([[09. Структура проекта и модули]]) |

# Читаемость сверх форматтера

Форматтеры не понимают смысла, поэтому часть работы за человеком:

1. **Имена — существительные для данных, глаголы для функций:** `total`, `report_lines`,
   `make_report`, `read_numbers`. Сокращения — только общепринятые (`idx`, `max`, `url`).
2. **Ранний выход вместо вложенности.** Чем меньше вложенных `if`, тем лучше видно
   главный путь: «отбросили неподходящие случаи — и работаем».
3. **Магические числа — в константы.** `TAX_RATE = 0.2` лучше, чем `* 0.2` в трёх местах:
   видно, что это одно и то же число, и правка делается в одном месте.
4. **Комментарий объясняет «зачем», а не «что».** `# если скидка больше 50%, проверяет руководитель` —
   полезно; `# прибавляю 1 к i` — шум.
5. **Функция делает одно.** Если из описания получается «…и…и…», функция делится.
6. **Мёртвый код убирают.** Закомментированные куски живут в git ([[08. Git и GitHub]]),
   а не в файле, где их читают через полгода.

# Как это делают в проекте

1. **Стиль настроен один раз.** В `pyproject.toml` лежат настройки `black` и `ruff`:
   таблица ниже. Никто не спорит о пробелах на ревью.
2. **Инструменты стоят в зависимостях разработки** (`dev`-группа) и запускаются одной командой.
3. **Проверка в CI и pre-commit.** Если `ruff` или `black --check` ругается, PR не проходит
   ([[08. Git и GitHub]]) — стиль не обсуждается в комментариях.
4. **Автосохранение делает VS Code.** При сохранении файла форматирование применяется
   само, и грязный код просто не успевает появиться.
5. **Правила можно расширять.** Набор `select` в `ruff` настраивается: проект описывает,
   какие правила считает важными, а не полагается на вкус каждого.

```toml
[tool.black]
line-length = 88

[tool.ruff]
line-length = 88

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]
```

- `E` — стилевые ошибки (в том числе сравнение с `None`),
- `F` — реальные ошибки: неиспользуемое имя, неопределённое имя,
- `I` — порядок импортов,
- `UP` — устаревшие конструкции, которые можно записать современно,
- `B` — «грабли»: подозрительные сравнения, изменяемые значения по умолчанию.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Форматирование — вопрос вкуса» | Вкус заканчивается там, где начинает работать машина: `black` не спорит |
| «Достаточно одного `black`» | `black` не видит неиспользуемые импорты и сравнения с `None` |
| «`ruff` — это только стиль» | Он ловит реальные ошибки: неопределённые имена, забытые импорты |
| «Линтер мешает писать» | Линтер убирает обсуждения на ревью и ловит опечатки до запуска |
| «Красивый код = понятный код» | Отформатированная каша остаётся кашей: имена и структура важнее пробелов |

# Проверь себя

1. Чем обязанности `black` отличаются от обязанностей `ruff`?
2. Что делает команда `black --check .` и зачем она в CI?
3. Почему `if mark is None` лучше, чем `if mark == None`?
4. Почему магические числа выносят в константы?
5. Когда комментарий полезен, а когда мешает?
6. Что означает `select = ["E", "F", "I", "UP", "B"]` в `pyproject.toml`?

> [!success]- Ответы
> 1. `black` приводит вид к одному стилю и не меняет смысл; `ruff` ищет ошибки
>    и подозрительные конструкции.
> 2. Проверяет формат, не изменяя файлов: если код не отформатирован, проверка падает
>    и PR не проходит.
> 3. `is` сравнивает «тот же объект», и для единственного экземпляра `None` это точнее
>    и быстрее; `==` может быть переопределён в классе.
> 4. Одно число в одном месте: видно, что это одна и та же величина, и правка не забудет
>    одно из использований.
> 5. Полезен, когда объясняет причину или неочевидное правило. Мешает, когда пересказывает код.
> 6. Набор правил `ruff`: стиль, ошибки, импорты, современные конструкции, «грабли».
