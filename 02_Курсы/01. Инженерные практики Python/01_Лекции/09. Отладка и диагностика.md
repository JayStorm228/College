# 09. Отладка и диагностика

> [!abstract] О чём лекция
> Программа сломалась — что делать? В курсе Python был один приём: поставить `print` и смотреть.
> Здесь — полный набор: чтение traceback в глубину, точки останова в VS Code, `breakpoint()`
> в терминале и `logging` вместо `print` в проекте.
>
> Главная мысль: отладка — не «угадай, где ошибка», а **сужение области поиска**. Точка
> останова, лог и тест — три способа сузить место быстрее, чем перечитывание всего кода.

# Читаем traceback правильно

```python
def read_numbers(text):
    numbers = []
    for part in text.split(","):
        numbers.append(int(part))
    return numbers


def average(numbers):
    return sum(numbers) / len(numbers)


print(average(read_numbers("1,2,три")))
```

```text
Traceback (most recent call last):
  File "/tmp/eng/crash.py", line 12, in <module>
    print(average(read_numbers("1,2,три")))
                  ^^^^^^^^^^^^^^^^^^^^^^^
  File "/tmp/eng/crash.py", line 4, in read_numbers
    numbers.append(int(part))
                   ^^^^^^^^^
ValueError: invalid literal for int() with base 10: 'три'
```

Как читать:

| Место | Что говорит |
|---|---|
| последняя строка | **тип ошибки и причина** — самое важное |
| последний блок `File ...` | где именно упало (внутри `read_numbers`) |
| блоки выше | как программа туда пришла: из `<module>` в `read_numbers` |
| строка `^^^^` | точное место внутри строки (подсказка Python 3.11 и новее) |

Обрати внимание: `average` в traceback не появился. Аргументы вычисляются раньше вызова,
поэтому до `average` дело не дошло. Ошибка внутри библиотеки тоже не означает, что
библиотека виновата: чаще всего не те данные передал вызывающий код. Ищи свой первый
блок в списке.

# Точки останова: остановиться и посмотреть

В VS Code: щёлкнуть слева от номера строки (`F9`) — появится красная точка, затем запустить
отладчик (`F5`). Программа остановится, и в панели **Variables** будет видно **все**
значения в этот момент. Дальше:

| Клавиша | Действие |
|---|---|
| `F5` | продолжить до следующей точки останова |
| `F10` | шаг через строку (вызовы выполняются целиком) |
| `F11` | шаг с заходом внутрь функции |
| `Shift+F5` | остановить отладку |

В терминале (без редактора) то же самое делает `breakpoint()`:

```python
def read_numbers(text):
    parts = text.split(",")
    breakpoint()          # остановка: тут можно посмотреть значения
    return [int(part) for part in parts]
```

При запуске откроется `(Pdb)` — мини-консоль отладчика:

| Команда | Что делает |
|---|---|
| `p parts` | напечатать значение переменной |
| `n` | следующая строка |
| `s` | шаг внутрь функции |
| `c` | продолжить выполнение |
| `q` | выйти |

Это и есть «посмотреть, что там на самом деле» — только без правки кода и повторных запусков.

# `print` — почему не в проекте

`print` не плох, но у него три проблемы: его забывают убрать, он не пишет время и уровень
важности, и его нельзя отключить без правки кода. Поэтому в проектах используют `logging`:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
    datefmt="%H:%M:%S",
)

logger = logging.getLogger(__name__)


def average(numbers):
    if len(numbers) == 0:
        logger.warning("пустой список: среднее не определено")
        return None
    logger.info("считаю среднее по %d числам", len(numbers))
    return sum(numbers) / len(numbers)


logger.info("среднее по [1, 2, 3] = %s", average([1, 2, 3]))
logger.warning("среднее по [] = %s", average([]))
```

```text
20:06:59 INFO считаю среднее по 3 числам
20:06:59 INFO среднее по [1, 2, 3] = 2.0
20:06:59 WARNING пустой список: среднее не определено
20:06:59 WARNING среднее по [] = None
```

Логи уходят в поток ошибок (`stderr`), поэтому `python prog.py > result.txt` их не заберёт:
в файле будет только результат, а сообщения останутся видны в терминале.

Уровни важности — это фильтр: в работе включают `INFO`, при разборе проблем — `DEBUG`,
а `WARNING` и `ERROR` видны всегда.

| Уровень | Когда использовать |
|---|---|
| `debug` | подробности для отладки: значения входов, ветки |
| `info` | нормальные события: «сохранил отчёт», «обработал 120 записей» |
| `warning` | подозрительное, но программа продолжает: пустой список, старое значение |
| `error` | операция не удалась: файл не найден, сервис недоступен |
| `critical` | программа не может продолжать |

Обрати внимание на `%d` и `%s` в тексте сообщения: значения передают **отдельными
аргументами**, а не склеивают f-строкой. Logging подставляет их сам, и только если
сообщение действительно будет записано (для `debug` при уровне `INFO` работа по
склейке не делается). `%d` — целое число, `%s` — любое значение как строка, `%r` — то же,
что `repr` (с кавычками у строк).

Ошибку, которую поймали и не пробросили дальше, записывают вместе с traceback —
методом `logger.exception` (его вызывают внутри `except`):

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger(__name__)


def read_number(text):
    try:
        return int(text)
    except ValueError:
        logger.exception("не удалось разобрать %r", text)
        return None


read_number("три")
```

```text
ERROR не удалось разобрать 'три'
Traceback (most recent call last):
  File "/home/user/project/read.py", line 9, in read_number
    return int(text)
           ^^^^^^^^^
ValueError: invalid literal for int() with base 10: 'три'
```

Так ошибка не «проглочена»: и сообщение, и полный traceback остались в логе
(формат вывода задан строкой `format=` в `basicConfig`; путь к файлу в traceback у тебя будет свой).

Почему `logger = logging.getLogger(__name__)`, а не `print`:

1. **Видно, откуда сообщение** — имя модуля попадает в лог.
2. **Уровни включаются настройкой**, а не правкой кода.
3. **Лог пишется в файл**, а не остаётся в чужом терминале.
4. **Формат одинаковый** — время, уровень, сообщение.

# Приёмы, которые сужают поиск

| Приём | Как выглядит | Когда помогает |
|---|---|---|
| сузить данные | маленький пример (3 числа вместо 3000) вместо большого | ошибка воспроизводится не всегда |
| деление пополам | проверить середину: данные правильные? тогда смотреть дальше | непонятно, где ломается |
| печатать вход и выход | `logger.debug("вход %r, выход %r", data, result)` | результат «не тот» |
| проверить границы | пусто, ноль, одно значение, максимум | падает «иногда» |
| изолировать | вызвать подозрительную функцию отдельно в консоли | сложная цепочка вызовов |

Отдельно стоит запомнить: **баг, который не воспроизводится, нельзя починить осознанно.**
Сначала его превращают в тест ([[08. Тесты]]), потом чинят.

# Как это делают в проекте

1. **`print` живёт только в черновиках.** В проекте — `logging`; сообщения с уровнем
   и контекстом.
2. **Логи не спамят.** `debug` — для подробностей, `info` — для ключевых событий.
   Тысяча строк «вошёл в функцию» мешает искать настоящую проблему.
3. **Ошибку логируют один раз.** Либо там, где поймали, либо на верхнем уровне —
   иначе в логе три копии одного сбоя.
4. **Отладка начинается с вопроса, а не с кода.** «Данные не те?», «не тот файл?»,
   «функция не вызывается?» — гипотеза, потом проверка.
5. **Точка останова дешевле `print`.** Она не требует правок, которые потом забывают убрать.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Ошибка в библиотеке — виновата библиотека» | Смотри первый свой вызов в цепочке: чаще всего данные не те |
| «Traceback читают снизу вверх — и всё» | Сначала последняя строка (что), потом свой первый блок в списке (откуда) |
| «Логи — это `print` с другим названием» | Уровни, имена модулей, запись в файл, отключение без правок |
| «Чем больше логов, тем лучше» | Лог читают люди: важное должно быть видно |
| «Отладчик нужен только профессионалам» | Точка останова — самый быстрый способ увидеть значения, доступный с первого дня |

# Проверь себя

1. Что в traceback читают первым?
2. Чем `F10` отличается от `F11`?
3. Что делает `breakpoint()` и какие две команды отладчика самые частые?
4. Чем `logging.warning` отличается от `logging.info` на практике?
5. Почему «одна ошибка — один лог»?
6. Почему невоспроизводимый баг сначала превращают в тест?

> [!success]- Ответы
> 1. Последнюю строку: тип ошибки и причину. Потом находят свой первый блок `File ...`.
> 2. `F10` выполняет вызов целиком (перешагнуть), `F11` заходит внутрь функции.
> 3. Останавливает выполнение и открывает отладчик. Чаще всего нужны `p переменная`
>    (посмотреть) и `n` (следующая строка).
> 4. Уровнем: `info` видно при обычной настройке, `warning` — заметен и там, где подробные
>    сообщения отключены; это сигнал «что-то не так, но работаем дальше».
> 5. Иначе один сбой превращается в несколько сообщений, и настоящее место ошибки
>    теряется в дублях.
> 6. Тест закрепляет условия сбоя: после правки он подтвердит, что баг не вернулся.
