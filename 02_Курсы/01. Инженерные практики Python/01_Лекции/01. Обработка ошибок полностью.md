# 01. Обработка ошибок полностью

> [!abstract] О чём лекция
> В курсе Python был базис: `try` / `except` с конкретным типом, чтобы программа не падала
> на неверном вводе. Здесь — вся конструкция целиком: `else`, `finally`, `raise`,
> `raise ... from`, свои классы исключений и `assert`. И главный вопрос: **какие ошибки
> нужно обрабатывать, а какие — дать упасть**.
>
> Ключевая мысль: ошибка — это информация. Плохо не то, что программа упала, а то, что она
> упала молча или не там, где проблему можно было увидеть.

# Конструкция целиком

```python
class BalanceError(Exception):
    """Своё исключение: понятное имя и данные внутри."""

    def __init__(self, amount, balance):
        super().__init__(f"не хватает {amount - balance:.2f} руб.")
        self.amount = amount
        self.balance = balance


def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("сумма должна быть положительной")
    if amount > balance:
        raise BalanceError(amount, balance)
    return balance - amount


for balance, amount in [(100, 30), (100, -5), (100, 250)]:
    try:
        result = withdraw(balance, amount)
    except ValueError as error:
        print(f"ValueError: {error}")
    except BalanceError as error:
        print(f"BalanceError: {error}; не хватило {error.amount - error.balance:.2f}")
    else:
        print(f"Успех: остаток {result}")
    finally:
        print("--- попытка обработана ---")
```

```text
Успех: остаток 70
--- попытка обработана ---
ValueError: сумма должна быть положительной
--- попытка обработана ---
BalanceError: не хватает 150.00 руб.; не хватило 150.00
--- попытка обработана ---
```

Четыре части конструкции:

| Часть | Когда выполняется | Зачем |
|---|---|---|
| `try` | всегда | код, который может сломаться |
| `except Тип` | если исключение этого типа | обработать **ожидаемую** проблему |
| `else` | если исключения **не** было | код, который не должен попасть под `except` |
| `finally` | **всегда**, даже при `return` или ошибке | закрыть файл, отпустить ресурс, записать факт |

`else` — не украшение. Всё, что в `try`, защищено от «случайного» перехвата: если положить
печать результата внутрь `try`, её ошибка тоже попадёт в `except`, и причина будет скрыта.

# Проверка вместо обработки

```python
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("сумма должна быть положительной")
    ...
```

Функция **проверяет аргументы сама** и падает с понятным сообщением — это называется
«упасть рано» (fail fast). Так делать лучше, чем надеяться, что вызывающий код помнит
про ограничения.

Правило, которое стоит запомнить: **обрабатывать нужно те ошибки, на которые можешь
отреагировать**. Пользователь ввёл буквы вместо числа — реагируем (спросить снова).
Файл конфигурации повреждён — падаем с ясным сообщением, чинить это должен человек.

# Свои исключения

Стандартные исключения (`ValueError`, `TypeError`, `KeyError`) покрывают общие случаи.
Когда у ошибки есть **свой смысл**, делают класс:

```python
class BalanceError(Exception):
    def __init__(self, amount, balance):
        super().__init__(f"не хватает {amount - balance:.2f} руб.")
        self.amount = amount
        self.balance = balance
```

Что это даёт:

- **имя говорит о смысле** — `BalanceError` понятнее, чем `ValueError: bad amount`;
- **внутри есть данные** — вызывающий код может показать «не хватило 150 руб.», не разбирая текст;
- **ловим точечно** — `except BalanceError` не поймает чужие ошибки.

Требования к своим исключениям простые: наследоваться от `Exception`, называться
с суффиксом `Error`, иметь понятное сообщение. Наследоваться от `BaseException` нельзя —
его ловят только системные механизмы (`KeyboardInterrupt`).

# `raise ... from`: сохраняем причину

```python
def load_count(text):
    try:
        return int(text)
    except ValueError as error:
        raise ValueError(f"не число: {text!r}") from error


try:
    load_count("abc")
except ValueError as error:
    print("ошибка:", error)
    print("причина:", repr(error.__cause__))
```

```text
ошибка: не число: 'abc'
причина: ValueError("invalid literal for int() with base 10: 'abc'")
```

Без `from` исходная причина теряется, и в логе остаётся только «не число: 'abc'» —
непонятно, что именно сломалось внутри. `from error` дописывает цепочку: «это упало
потому что вот это».

# `assert`: проверка того, во что веришь

```python
def average(numbers):
    assert len(numbers) > 0, "среднее пустого списка не определено"
    return sum(numbers) / len(numbers)
```

`assert` — это **утверждение о программе**, а не обработка ошибок пользователя:

- `assert` для того, что «никогда не должно случиться» (внутренняя договорённость);
- `raise ValueError` — для того, что может прийти снаружи и что нужно объяснить.

> [!warning] `assert` можно выключить
> Флаг `python -O` убирает все `assert` из кода. Поэтому ими не проверяют пользовательский
> ввод и не защищают данные: для этого есть обычные `if` + `raise`.

# Чего делать нельзя

| Плохо | Почему | Как правильно |
|---|---|---|
| `except Exception: pass` | ошибка исчезает: код идёт дальше сломанным | ловить конкретный тип или хотя бы записать ошибку в лог |
| ловить всё подряд вокруг всего кода | скрывает и опечатки, и настоящие сбои | `try` — вокруг **одного** подозрительного вызова |
| `except Exception as error: raise error` | теряется traceback и цепочка причин | `raise` без аргументов или `raise ... from` |
| разбирать текст ошибки строками | сообщение меняется между версиями Python | сравнивать тип и пользоваться атрибутами исключения |
| возвращать `None` вместо ошибки | вызывающий код не узнает о проблеме | `raise` или явный результат-объект |

# Как это делают в проекте

1. **Ошибки делят на ожидаемые и неожиданные.** Ожидаемые (нет файла, кривой ввод) —
   обрабатывают и пишут понятное сообщение. Неожиданные — дают упасть, но с полным
   traceback, чтобы в логе была причина.
2. **Свои исключения — часть интерфейса модуля.** Если библиотека может кинуть
   `BalanceError`, об этом пишут в docstring; вызывающий код ловит именно её.
3. **В `finally` — только освобождение ресурсов.** Логика в `finally` путает: он выполняется
   и при ошибке, и при `return`.
4. **Ошибку видно в логе.** Следующая лекция про отладку покажет `logging`; главное —
   «молча проглоченных» ошибок в проекте не бывает.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Чем больше `try`, тем надёжнее» | Лишний `try` скрывает ошибки. Надёжность — в проверках и тестах |
| «`except Exception` — универсальная защита» | Ловит и то, что чинить должен разработчик; ошибка всплывёт позже и в другом месте |
| «`finally` нужен только для файлов» | Для любых ресурсов: соединение, блокировка, временный файл |
| «`assert` — то же, что `raise`» | `assert` выключается флагом `-O` и не объясняет пользователю причину |

# Проверь себя

1. Чем `else` в конструкции `try` отличается от кода сразу после `except`?
2. Зачем `raise ... from error`, если сообщение и так понятное?
3. Почему `except Exception: pass` опаснее, чем отсутствие `try`?
4. Когда своё исключение лучше стандартного `ValueError`?
5. Почему `assert` не годится для проверки пользовательского ввода?
6. Что выполнится: `finally` или `return`, если `return` стоит в блоке `try`?

> [!success]- Ответы
> 1. Смыслом: `else` выполняется, только если исключения не было, и его ошибки **не**
>    попадают в `except`. Это способ отделить «защищённый вызов» от «работы с результатом».
> 2. Сохраняет исходную причину: в traceback и в логе видно и внешнюю ошибку, и то,
>    что упало внутри. Без `from` причина теряется.
> 3. Ошибка исчезает: программа идёт дальше с неправильными данными, а падение случится
>    позже и в другом месте — искать придётся дольше.
> 4. Когда у ошибки есть смысл и данные: `BalanceError` с суммой и остатком говорит больше,
>    чем `ValueError`, и его можно поймать точечно.
> 5. Потому что `python -O` их убирает: проверка исчезнет именно тогда, когда данные
>    придут «снаружи».
> 6. `finally` выполнится перед возвратом управления. Поэтому в нём не меняют результат
>    работы функции.
