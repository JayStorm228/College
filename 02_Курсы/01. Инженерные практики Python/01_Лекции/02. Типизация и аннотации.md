# 02. Типизация и аннотации

> [!abstract] О чём лекция
> В курсе Python типы разбирались как свойство **значения**: `type(5)` — это `int`.
> Здесь — второй слой: как записать **ожидаемый** тип в коде, чтобы редактор и внешний
> проверяльщик находили ошибки до запуска программы.
>
> Аннотации не меняют поведение программы. Они меняют то, как быстро ты узнаёшь,
> что перепутал `int` и `str`: сразу в редакторе или позже, на глазах у пользователя.

# Аннотации: что это

```python
def greet(name: str, times: int = 1) -> str:
    return ("Привет, " + name + "! ") * times


print(repr(greet("Аня")))
print(repr(greet("Аня", 2)))
print("аннотации живут в __annotations__:", greet.__annotations__)
```

```text
'Привет, Аня! '
'Привет, Аня! Привет, Аня! '
аннотации живут в __annotations__: {'name': <class 'str'>, 'times': <class 'int'>, 'return': <class 'str'>}
```

Аннотация — это **обещание**, а не проверка: Python положит её в `greet.__annotations__`
и выполнит функцию, даже если передать строку вместо числа. Проверяет не Python,
а инструменты: Pylance в VS Code и `mypy` в терминале.

# Что писать в аннотациях

| Что описываем                      | Как записать                                                   |
| ---------------------------------- | -------------------------------------------------------------- |
| переменная                         | `price: float = 199.90`                                        |
| параметр и возврат                 | `def rubles(amount: int) -> str:`                              |
| функция без результата             | `def log(text: str) -> None:`                                  |
| список, словарь, множество, кортеж | `list[int]`, `dict[str, float]`, `set[str]`, `tuple[int, str]` |
| значение «или ничего»              | `str \| None` (раньше писали `Optional[str]`)                  |
| псевдоним типа                     | `Number = int \| float`                                        |
| список словарей                    | `list[dict[str, int]]`                                         |

Полный пример:

```python
from typing import TypeVar

TNum = TypeVar("TNum", int, float)
Number = int | float          # псевдоним типа
Scores = list[int]            # список целых чисел


def average(numbers: list[TNum]) -> float:
    """Среднее арифметическое списка чисел."""
    if len(numbers) == 0:
        raise ValueError("пустой список")
    return sum(numbers) / len(numbers)


def find_longest(words: list[str]) -> str | None:
    """Самое длинное слово или None, если слов нет."""
    if not words:
        return None
    return max(words, key=len)


def describe(value: Number) -> str:
    """Строка про число: целое или дробное."""
    if isinstance(value, int):
        return f"{value} — целое"
    return f"{value} — дробное"


print(f"среднее: {average([1, 2, 3]):.2f}")
print(f"среднее: {average([1.5, 2.5])}")
print("самое длинное:", find_longest(["мама", "мыла", "раму"]))
print("пусто:", find_longest([]))
print(describe(5), "|", describe(2.5))
```

```text
среднее: 2.00
среднее: 2.0
самое длинное: мама
пусто: None
5 — целое | 2.5 — дробное
```

Разбор мест:

- `TypeVar("TNum", int, float)` — «один и тот же тип из двух возможных»: `average([1, 2, 3])`
  принимает `list[int]`, `average([1.5, 2.5])` — `list[float]`, а не «список чего попало».
- `str | None` — честный возврат: функция действительно может вернуть `None`, и вызывающий
  код обязан это учесть. Спрятать `None` за `str` — соврать.
- Псевдонимы (`Number`, `Scores`) убирают шум: смысл видно по имени, а не по «списку целых».

> [!note] Версии синтаксиса
> Запись `list[int]` вместо `List[int]` работает в Python 3.9+, `int | str` вместо
> `Union[int, str]` — с 3.10, а объявление псевдонима через `type Number = int | float` —
> с 3.12. В этом репозитории проект настроен на 3.12+ (`requires-python` в `pyproject.toml`),
> поэтому используется новый синтаксис; старые записи встречаются в чужом коде.

# Как проверяются типы

**В редакторе.** Pylance подчёркивает несоответствия, показывая вывод типов. Уровень
проверок задаётся в настройках, и в этом репозитории он максимальный:

```json
"python.analysis.typeCheckingMode": "strict"
```

**В терминале.** `mypy` проходит по файлам и печатает список несоответствий:

```python
def discounted(price: float, percent: int) -> float:
    """Цена со скидкой в процентах."""
    return price * (1 - percent / 100)


total: int = discounted(1000, 10)
print(total)
```

```text
mypy_demo.py:6: error: Incompatible types in assignment (expression has type "float", variable has type "int")  [assignment]
Found 1 error in 1 file (checked 1 source file)
```

Обрати внимание: программа при этом **запускается** и печатает `900.0`. Проверка типов —
отдельный шаг, и это главное, что нужно понять:

| Инструмент | Что делает | Когда срабатывает |
|---|---|---|
| Python | выполняет код | во время запуска |
| Pylance | подсказывает и предупреждает | во время набора текста |
| `mypy` | проверяет весь проект | по команде, например в тестах и CI |

Запуск: `uv add --dev mypy`, затем `uv run mypy src`. Настроить строгость можно
в `pyproject.toml`, но начинать достаточно с сообщений по умолчанию.

# Что даёт типизация на практике

1. **Ошибка вместо принта.** Вместо `print(type(value))` и догадок — подсказка в редакторе.
2. **Самодокументируемость.** `def total(rows: list[dict[str, int]]) -> int` понятнее,
   чем `def total(rows)` — не надо читать тело функции.
3. **Проверка до запуска.** Опечатку в имени поля вложенного словаря ловит Pylance.
4. **Безопасная работа с чужими библиотеками.** Видно, что принимает функция и что вернёт.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Аннотации ускоряют код» | Не влияют вообще: это данные для инструментов |
| «Если аннотировать, Python будет проверять» | Нет. Проверяют Pylance и `mypy`, а не интерпретатор |
| «`Any` — это универсальный тип» | `Any` отключает проверку в этом месте: он нужен для крайнего случая и заметен на ревью |
| «Аннотации нужны везде и всегда» | Обязательны на публичных функциях и на данных; локальные переменные аннотируют там, где это помогает читать |
| «`str \| None` — то же самое, что `str`» | Разница принципиальная: `None` придётся обработать, иначе упадёт |

# Как это делают в проекте

1. **Аннотируют границы модуля.** Все публичные функции и методы классов — с аннотациями;
   внутри многострочной функции — по необходимости.
2. **Строгость включают постепенно.** В старом проекте ставят `mypy` в щадящем режиме
   и закрывают ошибки по мере правок, а не «всё сразу».
3. **Строка — тоже договорённость.** Если функция возвращает `str | None`, вызывающий код
   обязан проверить `None`, а не надеяться.
4. **Аннотации не заменяют проверки.** Данные от пользователя и из файлов всё равно проверяются кодом: `int(input(...))`, `try` / `except`, а позже — Pydantic ([[00. Pydantic]]).

# Проверь себя

1. Что произойдёт, если передать в аннотированную функцию значение другого типа?
2. Чем `list[int]` отличается от `list` в аннотации?
3. Когда нужен `TypeVar`, а когда хватит `int | float`?
4. Почему `str | None` честнее, чем `str`, если функция иногда возвращает `None`?
5. Как проверить проект на ошибки типов из терминала?
6. Чем опасен `Any`?

> [!success]- Ответы
> 1. Ничего: код выполнится. Ошибку заметит редактор или `mypy`, если их запустить.
> 2. `list[int]` говорит, что внутри целые числа: проверяющий инструмент поймает
>    `["a", "b"]`. Просто `list` проверки элементов не даёт.
> 3. `TypeVar` нужен, когда тип входа и выхода связаны (возвращаем из того же набора).
>    Если связь не важна, хватит объединения `int | float`.
> 4. Потому что вызывающий код увидит, что результат может отсутствовать, и обработает это —
>    вместо падения на `None` в арифметике.
> 5. Поставить `mypy` как dev-зависимость и запустить: `uv add --dev mypy` и `uv run mypy src`.
> 6. Он выключает проверку: всё, что попало в `Any`, может быть чем угодно, и ошибки
>    дойдут до выполнения.
