# 12. Docstring

> [!abstract] О чём лекция
> Docstring — первая строка в тройных кавычках сразу после `def`, `class` или в начале файла.
> Она **не декорация**: из неё Python строит справку (`help()`), редактор показывает её
> при наведении мыши, а генераторы документации собирают сайт проекта.
>
> Лекция — про то, что писать в описании функции, чего не писать и как это проверить.

# Что показывает `help()`

```python
def rubles(amount, currency="руб."):
    """Форматирует сумму по-русски.

    Args:
        amount: сумма числом.
        currency: обозначение валюты, по умолчанию «руб.».

    Returns:
        Строка вида «1234.50 руб.».

    Raises:
        ValueError: если сумма отрицательная.
    """
    if amount < 0:
        raise ValueError("сумма не может быть отрицательной")
    return f"{amount:.2f} {currency}"
```

```text
>>> from money import rubles
>>> help(rubles)
Help on function rubles in module money:

rubles(amount, currency='руб.')
    Форматирует сумму по-русски.

    Args:
        amount: сумма числом.
        currency: обозначение валюты, по умолчанию «руб.».

    Returns:
        Строка вида «1234.50 руб.».

    Raises:
        ValueError: если сумма отрицательная.
```

Заметь: `help()` показал не только текст, но и **сигнатуру** со значением по умолчанию —
поэтому в docstring не нужно повторять «currency — по умолчанию руб.», это видно из кода.
Но раз в тексте это уже написано, ничего страшного: главное — не превращать docstring
в пересказ сигнатуры.

Модуль тоже может иметь docstring — он попадает в начало справки:

```text
$ python3 -m pydoc docs2
Help on module docs2:

NAME
    docs2 - Работа с деньгами: форматирование сумм.

FUNCTIONS
    rubles(amount, currency='руб.')
        Форматирует сумму по-русски.
        ...
```

# Одной строкой или блоками

| Случай | Формат |
|---|---|
| функция простая, смысл ясен из имени | одна строка: `"""Среднее арифметическое; None для пустого списка."""` |
| несколько параметров, результат неочевиден, есть исключения | блоки `Args / Returns / Raises` |
| класс | что описывает объект и как им пользоваться |
| модуль | зачем этот модуль нужен |

```python
def average(numbers):
    """Среднее арифметическое; None для пустого списка."""
    if not numbers:
        return None
    return sum(numbers) / len(numbers)
```

```text
4.0 None
```

Правило выбора простое: **чем больше вопросов возникает у читателя, тем подробнее описание.**
Описание из трёх абзацев у функции из пяти строк — такой же дефект, как его отсутствие.

# Что писать и что не писать

| Не писать | Почему | Вместо этого |
|---|---|---|
| «Функция складывает два числа» | пересказ кода | «Считает итоговый балл курса с учётом бонуса» |
| «Args: x (int) — число» | тип виден из аннотации ([[02. Типизация и аннотации]]) | описывать смысл: «количество попыток» |
| «Возвращает: результат» | ничего не сообщает | «Возвращает `None`, если список пуст» |
| подробности реализации | они изменятся, а docstring останется | описывать поведение и контракт |
| устаревшие примеры | вводят в заблуждение | примеры запускать (или использовать doctest) |

Хороший docstring отвечает на три вопроса: **что делает, что принимает по смыслу,
что возвращает и при каких условиях падает**. Всё остальное — в коде.

# Стили оформления

Единого стандарта нет, есть три распространённых:

| Стиль | Как выглядит | Где встречается |
|---|---|---|
| Google | `Args:`, `Returns:`, `Raises:` | большинство современных проектов |
| NumPy | `Parameters`, `Returns` с подчёркиваниями | научные библиотеки (NumPy, pandas) |
| reStructuredText | `:param x:`, `:return:` | документация на Sphinx, старые проекты |

Главное правило: **в проекте придерживаются одного стиля**. Смешивать нельзя — генераторы
документации начинают спотыкаться, а читатель не понимает, где что искать.

Проверить оформление может линтер: у `ruff` есть правила группы `D` (pydocstyle).
Например, `D103` — «нет docstring у публичной функции», `D200` — «docstring в одну строку
не помещается в одну строку». Включают, когда команда договорилась о строгости:

```toml
[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "D"]
```

# Docstring — контракт, а не украшение

Самое полезное свойство: docstring описывает **что обещает функция**, независимо от того,
как она это делает. Поэтому при рефакторинге:

- если описание осталось верным, менять нечего;
- если описание перестало быть верным — это сигнал: поведение функции изменилось,
  и это заметят все, кто её использует.

К docstring примыкают **doctest** — примеры прямо в описании:

```python
def average(numbers):
    """Среднее арифметическое.

    >>> average([2, 4, 6])
    4.0
    >>> average([]) is None
    True
    """
```

Такие примеры можно запускать как тесты (`python -m doctest`): документация, которая
проверяется машиной. Подробнее — в практике по тестам и в [[03. Тесты]].

# Как это делают в проекте

1. **Описывают публичное, не описывают очевидное.** Внутренние хелперы с говорящими именами
   могут остаться без docstring.
2. **Пишут «что и зачем», не «как».** Реализация меняется, обещание — редко.
3. **Один стиль на проект**, заданный в настройках линтера.
4. **Примеры в docstring запускают.** Иначе они тихо устаревают.
5. **Docstring для модулей — короткие.** Зачем файл: этого часто достаточно.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Комментарии и docstring — одно и то же» | Комментарий — заметка в коде для того, кто читает реализацию; docstring — справка для того, кто пользуется функцией |
| «Хороший код не нуждается в docstring» | Нуждается в меньшей, но контракт (исключения, `None`, границы) не виден из имени |
| «Docstring пишут один раз» | Его правят вместе с поведением функции; устаревший docstring хуже отсутствующего |
| «Чем длиннее, тем лучше» | Длина — по потребности читателя, а не по объёму текста |
| «Docstring заменит тесты» | Docstring описывает обещание, тесты проверяют, что оно выполняется |

# Проверь себя

1. Что Python делает с docstring, кроме хранения текста?
2. Когда docstring можно ограничить одной строкой?
3. Что не нужно указывать в docstring, потому что это и так видно из кода?
4. Зачем в проекте один стиль описаний?
5. Что произойдёт с описанием при рефакторинге, если оно описывает реализацию?
6. Что такое doctest?

> [!success]- Ответы
> 1. Строит из неё справку `help()` и `pydoc`; редакторы показывают её в подсказках.
> 2. Когда функция простая и её смысл понятен из имени и сигнатуры; сложные случаи
>    (несколько параметров, исключения) описывают блоками.
> 3. Типы (они уже в аннотациях) и всё, что буквально повторяет тело функции.
> 4. Чтобы читатель и генератор документации не гадали, где `Args:`, а где `:param x:`;
>    кроме того, это правило можно проверять линтером.
> 5. Оно устареет и начнёт вводить в заблуждение — поэтому описывают контракт, а не устройство.
> 6. Пример работы функции прямо в docstring, который можно запускать как тест.
