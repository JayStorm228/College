# 13. Сложность и производительность

> [!abstract] О чём лекция
> «Программа тормозит» — не повод переписывать всё. Здесь о том, как **измерить**,
> где именно теряется время, и почему `99 999 in numbers` может занимать в тысячи раз
> больше времени, чем `99 999 in numbers_set`.
>
> Лекция даёт словарь (сколько времени занимают типовые операции), инструмент (`timeit`,
> `cProfile`) и правило: сначала замер, потом оптимизация.

# Порядок роста: словарь, а не теория

Сложность отвечает на вопрос: **как растёт время работы, когда данных становится больше**.
Обозначение `O(...)` читается как «примерно столько операций на каждый элемент»:

| Обозначение | Название | Пример в Python | Данных в 10 раз больше — время… |
|---|---|---|---|
| `O(1)` | константа | `d[key]`, `x in set` | не изменилось |
| `O(log n)` | логарифм | `bisect`, поиск в сбалансированном дереве | выросло чуть-чуть |
| `O(n)` | линейная | `sum(list)`, `x in list` | выросло в 10 раз |
| `O(n log n)` | почти линейная | `sorted(list)` | выросло в ~10 раз |
| `O(n²)` | квадратичная | вложенный цикл по тем же данным | выросло в **100 раз** |

В Python особенно важно помнить две операции:

- `x in список` — просматривает элементы по одному: `O(n)`;
- `x in множество`, `x in словарь` — использует хеш: `O(1)`.

На маленьких данных разницы не заметно, на больших — она огромна. Проверим.

# Измеряем: `timeit`

```python
import timeit

data_list = list(range(100_000))
data_set = set(data_list)


def measure(stmt, setup, repeat=5):
    return min(timeit.repeat(stmt, setup=setup, repeat=repeat, number=1))


search_list = measure("99999 in data_list", "from __main__ import data_list")
search_set = measure("99999 in data_set", "from __main__ import data_set")
print(f"поиск в списке:    {search_list * 1e6:8.1f} мкс")
print(f"поиск в множестве: {search_set * 1e6:8.1f} мкс")
```

```text
поиск в списке:       359.5 мкс
поиск в множестве:      0.1 мкс
```

Одна и та же проверка: в 3595 раз быстрее в множестве. И это на 100 000 элементов:
с ростом данных разрыв только увеличится.

Тот же инструмент показывает остальные закономерности:

```text
конкатенация 20k:     0.52 мс
join 20k:             0.066 мс
уникальные (список):  4.22 мс
уникальные (dict):    0.046 мс
```

| Задача | Медленный способ | Быстрый способ | Разница |
|---|---|---|---|
| поиск элемента | `x in list` | `x in set` | ~3600 раз |
| построение строки | `s += part` в цикле | `"".join(parts)` | ~8 раз |
| уникальные значения | список + `not in` | `dict.fromkeys(...)` | ~90 раз |

> [!note] Числа зависят от машины и версии Python
> Замеры выше сделаны на учебной машине с Python 3.11. Важен **порядок различий**,
> а не точные значения: на вашем компьютере числа будут другими, а вывод «множество
> против списка — тысячи раз» останется тем же.
>
> Отдельно про строки: CPython умеет ускорять `s += part`, когда на строку ссылается одна
> переменная, поэтому разрыв с `join` невелик. Однако `join` предсказуемее: он не зависит
> от оптимизации внутри интерпретатора.

# Профилирование: где именно время

Если программа тормозит целиком, `timeit` не поможет: нужно знать, **какая функция**
съедает время. Для этого — `cProfile`:

```python
import cProfile
import pstats


def unique_slow(numbers):
    seen = []
    result = []
    for n in numbers:
        if n not in seen:
            seen.append(n)
            result.append(n)
    return result


cProfile.run("unique_slow(nums)", "prof.out")
pstats.Stats("prof.out").sort_stats("tottime").print_stats(4)
```

```text
         2604 function calls in 0.006 seconds

   Ordered by: internal time
   List reduced from 5 to 4 due to restriction <4>

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.006    0.006    0.006    0.006 /tmp/eng/prof.py:6(unique_slow)
     2600    0.000    0.000    0.000    0.000 {method 'append' of 'list' objects}
```

Как читать таблицу:

| Колонка | Значение |
|---|---|
| `ncalls` | сколько раз вызвана функция |
| `tottime` | сколько времени **внутри неё самой** (без вложенных вызовов) |
| `cumtime` | время вместе со всеми вложенными вызовами |
| первая строка | то, что нужно оптимизировать |

Обрати внимание: `append` вызывался 2600 раз, но виноват не он, а `unique_slow`:
именно там цикл `n not in seen` перебирает список. Профилирование показывает **место**,
а не «виноватую строку» — думать всё равно нужно.

# Типичные источники медленного кода

1. **Поиск в списке внутри цикла.** `if item in seen` для списка из тысяч элементов — `O(n²)`.
   Лечится множеством (`seen = set()`), если порядок не важен.
2. **Вложенные циклы по одним и тем же данным.** Часто заменяются словарём: сначала один проход
   собирает данные, второй — использует.
3. **Повторные вычисления в цикле.** `len(data)`, `data.upper()` или сложный расчёт внутри цикла
   считаются каждый раз — их выносят наружу.
4. **Лишние копии.** `sorted(data)` там, где достаточно `data.sort()`; создание нового списка
   на каждой итерации.
5. **Медленный ввод-вывод.** Запись в файл в цикле по строкам — медленнее, чем накопить
   и записать один раз; лишние `print` в больших циклах тоже стоят времени.
6. **Не тот инструмент.** Ручной поиск в списке там, где данные изначально стоит хранить
   в словаре; `list` там, где нужен `set`.

# Порядок действий при оптимизации

```text
1. Убедиться, что код правильный (тесты зелёные)
2. Замерить: timeit для операции, cProfile для программы
3. Найти узкое место — самое дорогое место, а не «подозрительное»
4. Исправить алгоритм или структуру данных
5. Замерить снова и сравнить
6. Прогнать тесты: быстрее не значит правильнее
```

Оптимизация без замера — это угадывание. Обычно «самое медленное место» в коде оказывается
не тем, о чём думал автор: медленным бывает ввод-вывод, а не вычисления.

# Как это делают в проекте

1. **Сначала понятный код.** Оптимизируют по замеру, а не заранее: преждевременная
   оптимизация усложняет код без пользы.
2. **Правильная структура данных вместо хитрых трюков.** Множество вместо списка
   или словарь вместо двойного поиска часто дают больше, чем любой микротрюк.
3. **Замер — с данными, похожими на реальные.** На трёх элементах любая разница не видна.
4. **Производительность тоже проверяют.** В больших проектах есть замеры, которые падают,
   если время выросло (регрессионные тесты производительности).
5. **Не жертвуют читаемостью ради микросекунд.** Если нужно объяснить трюк комментарием
   на пять строк, возможно, он того не стоит.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Медленно — значит надо переписать всё» | Обычно тормозит одно место, которое видно после профилирования |
| «`list` и `set` — почти одно и то же» | Для поиска разница в тысячи раз на 100 000 элементах |
| «Списковые включения всегда быстрее» | Они быстрее цикла с `append` на ту же работу, но алгоритм важнее синтаксиса |
| «Оптимизация всегда полезна» | Неизмеренная оптимизация тратит время и ухудшает читаемость |
| «`cProfile` покажет виноватую строку» | Он покажет функцию и время; выводы делает человек |

# Проверь себя

1. Чем `O(1)` отличается от `O(n)` на практике: что происходит при росте данных?
2. Почему `x in set` быстрее, чем `x in list`?
3. Зачем `timeit.repeat` и почему берут минимум из повторов?
4. Что показывает колонка `tottime` в `cProfile`?
5. Что делают перед оптимизацией и что — после неё?
6. Почему тесты обязательно прогоняют после оптимизации?

> [!success]- Ответы
> 1. `O(1)` не зависит от размера данных, `O(n)` растёт вместе с ним: в 10 раз больше данных —
>    примерно в 10 раз больше времени.
> 2. Множество использует хеш-таблицу: проверка почти не зависит от размера; список
>    просматривается по одному элементу.
> 3. Повторы отсеивают случайные помехи (другие процессы, кэш процессора); минимум ближе
>    всего к «чистому» времени работы.
> 4. Время внутри самой функции, без вложенных вызовов: сразу видно, где основная работа.
> 5. Перед — убедиться, что код верный, и замерить, чтобы найти узкое место. После — замерить
>    снова и сравнить.
> 6. Оптимизация меняет алгоритм, и легко сломать поведение. Тесты подтверждают, что
>    результат остался правильным.
