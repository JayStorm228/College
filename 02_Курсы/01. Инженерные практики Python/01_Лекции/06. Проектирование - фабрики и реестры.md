# 06. Проектирование: фабрики и реестры

> [!abstract] О чём лекция
> Программа растёт — и в одном месте появляется длинная лестница `if` / `elif`, которая
> решает, какой объект создать. Добавить новый вариант становится страшно: нужно найти
> это место, вспомнить про порядок условий, ничего не сломать.
>
> Здесь разбирается приём, который убирает такую лестницу: **реестр** — словарь, где
> по имени лежит функция-создатель. Это первый шаг к проектированию, о котором говорят
> «расширять, не меняя существующий код».

# Проблема: длинный `if` при создании

Так пишут в начале — и это нормально, пока вариантов два:

```python
def build_report(fmt, rows):
    if fmt == "text":
        return "\n".join(" | ".join(str(cell) for cell in row) for row in rows)
    elif fmt == "csv":
        return "\n".join(";".join(str(cell) for cell in row) for row in rows)
    elif fmt == "json":
        import json

        return json.dumps(rows, ensure_ascii=False)
    else:
        return None
```

Что плохо при росте: чтобы добавить `xml`, нужно править функцию; чтобы узнать список
поддерживаемых форматов — прочитать все ветки; чтобы протестировать один формат —
придумывать, как добраться до нужной ветки.

# Реестр: словарь «имя → создатель»

```python
def make_text_report(rows):
    return "\n".join(" | ".join(str(cell) for cell in row) for row in rows)


def make_csv_report(rows):
    return "\n".join(";".join(str(cell) for cell in row) for row in rows)


def make_json_report(rows):
    import json

    return json.dumps(rows, ensure_ascii=False)


BUILDERS = {
    "text": make_text_report,
    "csv": make_csv_report,
    "json": make_json_report,
}


def build_report(fmt, rows):
    """Создаёт отчёт нужного формата; None — если формат не поддерживается."""
    builder = BUILDERS.get(fmt)
    if builder is None:
        return None
    return builder(rows)


rows = [["Аня", 5], ["Борис", 4]]
for fmt in ["text", "csv", "json", "xml"]:
    print(f"--- {fmt} ---")
    print(build_report(fmt, rows))
print("поддерживаются:", ", ".join(BUILDERS))
```

```text
--- text ---
Аня | 5
Борис | 4
--- csv ---
Аня;5
Борис;4
--- json ---
[["Аня", 5], ["Борис", 4]]
--- xml ---
None
поддерживаются: text, csv, json
```

Что изменилось:

| Было | Стало |
|---|---|
| один большой `if` | три маленькие функции, каждая — один формат |
| добавить формат = править `build_report` | добавить формат = дописать функцию и строку в `BUILDERS` |
| список форматов не видно | `", ".join(BUILDERS)` печатает список |
| неизвестный формат | `None` или сообщение — решает вызывающий код |

В функции на **функции** ссылаются по имени, без вызова: `make_csv_report`, а не
`make_csv_report(rows)`. Это важный момент: в словаре лежит сама функция, вызов
происходит позже — `builder(rows)`.

# Фабрика: создание объектов

Тот же приём для классов. Пусть есть фигуры, и по имени нужно создавать объект:

```python
import math
from dataclasses import dataclass


@dataclass
class Circle:
    radius: float

    @property
    def area(self):
        return math.pi * self.radius**2


@dataclass
class Rectangle:
    width: float
    height: float

    @property
    def area(self):
        return self.width * self.height


SHAPES = {
    "circle": lambda radius: Circle(radius),
    "square": lambda side: Rectangle(side, side),
    "rectangle": lambda width, height: Rectangle(width, height),
}

shape = SHAPES["square"](3)
print(f"{shape}: площадь {shape.area}")
circle = SHAPES["circle"](1)
print(f"{circle}: площадь {circle.area:.4f}")
```

```text
Rectangle(width=3, height=3): площадь 9
Circle(radius=1): площадь 3.1416
```

`SHAPES["square"]` — это **фабрика**: функция, которая по данным создаёт объект. Класс
`SHAPES` не нужен, словарь справляется. Такой словарь удобно дополнять: новый тип фигуры —
одна строка, старая логика не переписывается.

> [!note] Функция-фабрика читается лучше `lambda`, если в ней есть проверки
> `lambda radius: Circle(radius)` хороша, пока создание — одна строка. Если нужны проверки
> («радиус положительный»), пишут обычную функцию `def make_circle(radius): ...` и кладут
> её в словарь. Это ровно тот случай, когда короткая запись мешает.

# Зачем это нужно: расширение без правки

Приём с реестром даёт три выгоды:

1. **Открыт для расширения, закрыт для правки.** Новый формат не меняет существующие
   функции — значит, ничего не сломается.
2. **Проверяется по частям.** `make_json_report(rows)` тестируется отдельно, без разбора
   всего `if`.
3. **Список возможностей видно.** `BUILDERS` читается как оглавление: что умеет программа.

Такой же приём встречается в реальных библиотеках: реестр загрузчиков, реестр команд,
реестр парсеров. В Django, например, реестр — это таблица маршрутов URL: имя → функция.

# Как это делают в проекте

1. **Сначала `if`, потом реестр.** Пока вариантов два-три — лестница условий нормальна
   и понятнее словаря. Переделывают, когда вариантов становится больше или когда
   добавление варианта задевает чужой код.
2. **Имя реестра говорит о содержимом:** `BUILDERS`, `PARSERS`, `HANDLERS` — во множественном
   числе, значение — функция или класс.
3. **Отсутствие варианта — не молчание.** Вернуть `None`, `raise ValueError` или
   сообщение по умолчанию — но явно, а не «как-нибудь».
4. **Реестр — данные, а не код.** Его можно собрать в одном месте и импортировать, можно
   дополнить из другого модуля (например, плагин регистрирует свой формат).

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Словарь медленнее `if`» | Разница ничтожна, а читаемость и расширяемость важнее |
| «Если есть реестр, все условия исчезнут» | Останутся: проверка наличия ключа, валидация данных |
| «Фабрика — это обязательно класс с методом» | В Python фабрика — обычная функция; класс нужен реже |
| «Реестр нужно делать сразу» | Сначала простое решение, реестр — когда простое перестало работать |

# Проверь себя

1. Почему в словаре `BUILDERS` стоят функции без вызова?
2. Как добавить новый формат отчёта, не трогая `build_report`?
3. Как реестр показывает список поддерживаемых вариантов?
4. Когда длинная лестница `if` уместнее реестра?
5. Чем фабрика-функция лучше `lambda`, если при создании нужны проверки?
6. Почему в реестре значений (`SHAPES`) допустимы `lambda`, а в реестре отчётов — нет?

> [!success]- Ответы
> 1. В словаре хранится сама функция как значение; вызов происходит позже — `builder(rows)`.
> 2. Дописать функцию-создатель и одну строку в `BUILDERS`.
> 3. `", ".join(BUILDERS)` печатает ключи — видно, что умеет программа.
> 4. Пока вариантов мало и они не будут расширяться: лестница `if` читается проще.
> 5. В обычной функции помещаются несколько строк с проверками и docstring;
>    в `lambda` — только одно выражение.
> 6. В `SHAPES` создание каждой фигуры — одна строка, поэтому `lambda` читается.
>    Создание отчёта — несколько строк, поэтому это именованные функции.
