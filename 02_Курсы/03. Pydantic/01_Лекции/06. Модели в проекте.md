# 06. Модели в проекте

> [!abstract] О чём лекция
> В реальном проекте модели редко бывают плоскими: у выписки есть список операций, у заказа —
> список товаров, у настроек — вложенная настройка базы. Здесь — вложенные модели, списки
> моделей, проверка больших структур данных и вопрос «когда Pydantic, а когда `dataclass`».

# Вложенные модели

```python
from datetime import date
from typing import Literal

from pydantic import BaseModel, Field, ValidationError


class Operation(BaseModel):
    """Одна операция по счёту."""

    date: date
    kind: Literal["доход", "расход"]
    amount: float = Field(gt=0)


class Statement(BaseModel):
    """Выписка: владелец и список операций."""

    owner: str = Field(min_length=1)
    operations: list[Operation] = Field(default_factory=list)

    @property
    def balance(self) -> float:
        """Баланс: доходы минус расходы."""
        income = sum(op.amount for op in self.operations if op.kind == "доход")
        outcome = sum(op.amount for op in self.operations if op.kind == "расход")
        return round(income - outcome, 2)
```

`Statement` содержит список `Operation`. Pydantic проверяет структуру **рекурсивно**:
каждый элемент списка превращается в модель `Operation`, а ошибка указывает полный путь.

```python
raw = {
    "owner": "Аня",
    "operations": [
        {"date": "2026-09-01", "kind": "доход", "amount": 5000},
        {"date": "2026-09-02", "kind": "расход", "amount": "1200.5"},
    ],
}
statement = Statement.model_validate(raw)
print(statement.owner, "| операций:", len(statement.operations), "| баланс:", statement.balance)
print(statement.model_dump_json())
```

```text
Аня | операций: 2 | баланс: 3799.5
{"owner":"Аня","operations":[{"date":"2026-09-01","kind":"доход","amount":5000.0},{"date":"2026-09-02","kind":"расход","amount":1200.5}]}
```

Строка `"1200.5"` внутри вложенного словаря превратилась в число — вложенность не мешает
приведению типов. А свойство `balance` считается по уже проверенным данным: в нём нет
ни одного `if`, который проверял бы типы.

# Ошибка говорит, где именно

```python
try:
    Statement.model_validate(
        {"owner": "Вика", "operations": [{"date": "2026-09-04", "kind": "подарок", "amount": 100}]}
    )
except ValidationError as exc:
    error = exc.errors()[0]
    print("поле:", error["loc"], "→", error["msg"])
```

```text
поле: ('operations', 0, 'kind') → Input should be 'доход' or 'расход'
```

Путь `('operations', 0, 'kind')` читается как «операции → первая → вид». В больших данных
такой путь экономит часы: сразу видно, какой именно элемент списка испорчен.

# Списки моделей без контейнера

Иногда нужен список моделей сам по себе — без «обёртки». Для этого есть `TypeAdapter`:

```python
from pydantic import TypeAdapter

adapter = TypeAdapter(list[Operation])
operations = adapter.validate_python(
    [{"date": "2026-09-03", "kind": "расход", "amount": 90}]
)
print("из списка словарей:", operations, "| баланс:", sum(-op.amount for op in operations))
```

```text
из списка словарей: [Operation(date=datetime.date(2026, 9, 3), kind='расход', amount=90.0)] | баланс: -90.0
```

`TypeAdapter` пригодится, когда данные — это «просто массив объектов» и создавать лишний
класс-контейнер не хочется. В проекте мини-валидатора он используется для проверки
`list[Application]` из файла.

# Копия и частичное обновление

```python
copy = statement.model_copy(update={"owner": "Борис"})
print("копия владельца:", copy.owner, "| исходный:", statement.owner)
```

```text
копия владельца: Борис | исходный: Аня
```

Помни предупреждение из [[04. Сериализация и JSON]]: `model_copy` **не валидирует**
обновление. Если данные приходят извне, собирай модель заново через `model_validate`.

# Когда Pydantic, а когда `dataclass`

| Вопрос | `dataclass` | Pydantic `BaseModel` |
|---|---|---|
| данные извне, нужна проверка | нет встроенной валидации | да, автоматически |
| приведение типов (`"17"` → `17`) | нет | да |
| скорость создания | быстрее | немного медленнее |
| структура очевидна | да | да |
| сериализация в JSON | вручную (`asdict`) | `model_dump_json` |
| ошибки с путём до поля | нет | `ValidationError` с `loc` |
| настройки приложения | нет | `BaseSettings` |

Практическое правило: **`dataclass` для внутренних структур, которым доверяем**
(например, точка на плоскости), **Pydantic — для данных на границе** (файлы, сети, настройки,
запросы). В одном проекте они спокойно живут вместе.

# Как это делают в проекте

Модели — это словарь домена. Чем точнее они отражают предметную область, тем меньше
логики в сервисах.

**1. Модели на границе, `dataclass` внутри.**

```python
# src/domain/geometry.py — внутренние расчёты, доверяем данным
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float

def distance(a: Point, b: Point) -> float:
    return ((a.x - b.x) ** 2 + (a.y - b.y) ** 2) ** 0.5

# src/api/models.py — граница, проверяем
from pydantic import BaseModel, Field
class PointIn(BaseModel):
    x: float = Field(ge=-1000, le=1000)
    y: float = Field(ge=-1000, le=1000)

# использование: входящие данные → Pydantic, внутри — dataclass
raw = {"x": "1.5", "y": 2}
point_in = PointIn.model_validate(raw)
point = Point(x=point_in.x, y=point_in.y)  # дальше — быстро и без валидации
```

Мотивация — скорость и шум: валидация каждого `Point` внутри цикла из 100 000 точек
замедляет в ~6 раз (см. лекцию 08), а пользы нет — данные уже проверены.

**2. Разделяют «вход» и «выход».**

```python
# пароль обязателен на входе, но никогда не уходит наружу
class UserIn(BaseModel):
    name: str
    password: str = Field(min_length=8)

class UserOut(BaseModel):
    name: str
    # пароля нет — его нельзя случайно сериализовать в response
```

С `dataclass` так не сделаешь: разные правила для одного класса не описать.

**3. Вложенные сущности — отдельные модели с именем домена.**

```python
# плохо: «список словарей»
# good: Operation — имя из банковской выписки, её можно переиспользовать
class Statement(BaseModel):
    owner: str
    operations: list[Operation]  # читается как «выписка состоит из операций»
```

Так модель читается как фраза предметной области, а не как «массив объектов».

**4. Вычисляемое — свойством, а не полем.**

```python
# плохо: хранить и операции, и баланс — кто-то забудет обновить
class StatementBad(BaseModel):
    operations: list[Operation]
    balance: float  # может разъехаться с операциями

# хорошо: баланс всегда считается из источника правды
class Statement(BaseModel):
    operations: list[Operation]
    @property
    def balance(self) -> float:
        return sum(op.amount for op in self.operations if op.kind == "доход") - \
               sum(op.amount for op in self.operations if op.kind == "расход")
```

То же правило, что в дисциплине 02 для `@property` в классе `Rectangle` —
«Сторона → площадь», только теперь гарантия типов идёт от Pydantic.

**5. Модель тестируется вместе с доменом.**

```python
# tests/test_statement.py
from pydantic import ValidationError
import pytest
from domain.statement import Statement

def test_balance_ok() -> None:
    s = Statement(owner="Аня", operations=[
        {"date": "2026-09-01", "kind": "доход", "amount": 100},
        {"date": "2026-09-02", "kind": "расход", "amount": 30},
    ])
    assert s.balance == 70

def test_bad_kind_has_path() -> None:
    with pytest.raises(ValidationError) as info:
        Statement.model_validate({"owner":"Аня","operations":[{"date":"2026-09-01","kind":"подарок","amount":10}]})
    assert info.value.errors()[0]["loc"] == ("operations", 0, "kind")
```

Тест проверяет и happy path, и путь в ошибке — это документация договора.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Вложенные модели надо приводить вручную» | Pydantic разбирает вложенность сам |
| «`loc` всегда просто имя поля» | Для вложенных данных это путь: `('operations', 0, 'kind')` |
| «Pydantic заменит `dataclass` всюду» | Внутренние структуры проще и быстрее как `dataclass` |
| «Модель должна содержать логику» | Хорошая модель — данные плюс минимальные свойства; логика живёт в сервисах |
| «Проверка замедлит программу» | Замедление заметно только на очень больших объёмах, а надёжность важнее |

# Проверь себя

1. Как объявить список моделей внутри модели?
2. Как читается путь `('operations', 0, 'kind')`?
3. Что такое `TypeAdapter` и когда он нужен?
4. Когда лучше `dataclass`, а когда Pydantic?
5. Почему `balance` — свойство, а не поле?

> [!success]- Ответы
> 1. `operations: list[Operation] = Field(default_factory=list)`.
> 2. «Поле `operations` → элемент с индексом 0 → поле `kind`».
> 3. Адаптер для типов без модели-контейнера: например, чтобы провалидировать `list[Operation]`.
> 4. `dataclass` — для внутренних структур, Pydantic — для данных снаружи, где нужна проверка.
> 5. Потому что баланс вычисляется из операций: как поле он мог бы «разъехаться» с данными.
