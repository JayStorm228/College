# 07. Ошибки валидации в приложении

> [!abstract] О чём лекция
> `ValidationError` — обычное исключение Python: его можно ловить, логировать и превращать
> в понятный отчёт. Важно только решить **где**: на границе приложения (ввод, файл, запрос),
> а не в каждой внутренней функции.
>
> Здесь — как из списка ошибок Pydantic собрать сообщение для человека, куда писать
> технические подробности и как проверить всё это тестами.

# Где ловить ошибку

```text
            ┌────────────────────────────────────────────┐
ввод/файл → │ граница: валидация и разбор ошибок         │ → дальше идут готовые модели
            └────────────────────────────────────────────┘
```

Внутри программы типы уже проверены, поэтому повторять `try/except` в каждой функции
не нужно: это тот же принцип «валидация — на границе», что в [[01. Зачем валидировать данные]].
Если функция принимает модель (`Order`), а не словарь, ей не нужно проверять данные вовсе —
это видно по аннотации.

```python
def save_order(order: Order) -> None:
    """Сохраняет уже проверенную заявку."""
```

Такую функцию невозможно случайно вызвать с «сырыми» данными: тип говорит, что заявку
сначала нужно провалидировать.

Анти-пример — ловить везде:

```python
# плохо: каждая функция сама валидирует
def total(orders: list[dict]) -> float:
    for raw in orders:
        try:
            Order.model_validate(raw)
        except ValidationError:
            continue  # ошибка растворилась
        ...
```

Правильно — проверить один раз и дальше работать с `list[Order]`.

# Отчёт для человека из списка ошибок

```python
import logging
import sys

from pydantic import BaseModel, Field, ValidationError

logging.basicConfig(
    level=logging.INFO,
    format="%(levelname)s %(message)s",
    stream=sys.stderr,
)
logger = logging.getLogger("orders")

FIELD_NAMES = {"client": "клиент", "email": "почта", "items": "позиции"}


class Order(BaseModel):
    """Заявка: клиент, почта и хотя бы одна позиция."""

    client: str = Field(min_length=2)
    email: str
    items: list[str] = Field(min_length=1)


def validate_order(raw: dict) -> Order | None:
    """Проверяет заявку: возвращает модель или None, записав причины в лог."""
    try:
        return Order.model_validate(raw)
    except ValidationError as exc:
        for error in exc.errors():
            field = ".".join(str(part) for part in error["loc"])
            logger.warning("заявка отклонена: %s — %s", FIELD_NAMES.get(field, field), error["msg"])
        return None
```

```python
print("плохая заявка →", validate_order({"client": "А", "email": "a@b", "items": []}))
good = validate_order({"client": "Аня", "email": "a@b", "items": ["ручка"]})
print("хорошая заявка →", good, "| позиций:", len(good.items))
```

```text
WARNING заявка отклонена: клиент — String should have at least 2 characters
WARNING заявка отклонена: позиции — List should have at least 1 item after validation, not 0
плохая заявка → None
хорошая заявка → client='Аня' email='a@b' items=['ручка'] | позиций: 1
```

Что здесь сделано:

1. **`loc` соединён в путь** (`"items.0"`, если ошибка во вложенном элементе) — так видно
   точное место.
2. **Техническое имя поля заменено на понятное** через словарь `FIELD_NAMES`. Словарь
   стоит держать рядом с моделью: он часть интерфейса.
3. **Логи идут в отдельный поток** (`stream=sys.stderr`) и содержат все ошибки сразу —
   это техническая запись для разработчика.
4. **Пользователю** в настоящем приложении показывают не лог, а человеческие фразы:
   «Клиент: минимум 2 символа». Англоязычный `msg` Pydantic — не текст для интерфейса,
   а основа для перевода.

> [!note] Русские тексты ошибок
> В валидаторах (`raise ValueError("оценка должна быть от 1 до 5")`) текст свой — он
> и показывается пользователю. Для встроенных проверок либо переводят `msg` по типу ошибки
> (`error["type"]`), либо задают своё сообщение в `Field(..., description=...)`, либо
> проверяют всё валидатором. Самый предсказуемый путь — **свой валидатор со своим текстом**.

# Не глотать ошибку

`return None` без следа — плохой вариант: вызывающий код может не заметить отказ.
Так лучше:

```python
def read_order(raw: dict) -> Order:
    """Возвращает заявку или поднимает исключение с понятными причинами."""
    try:
        return Order.model_validate(raw)
    except ValidationError as exc:
        reasons = "; ".join(
            f"{FIELD_NAMES.get(str(err['loc'][0]), err['loc'][0])}: {err['msg']}"
            for err in exc.errors()
        )
        raise ValueError(f"заявка не прошла проверку — {reasons}") from exc
```

- ошибка **всегда видна** (нет молчаливого `None`);
- исходная `ValidationError` сохранена в `__cause__` (`from exc`) — виден технический след;
- текст объясняет, что именно не так ([[01. Обработка ошибок полностью]]).

В мини-проекте выбран третий путь — деление на два списка:

```python
def check_all(items: list[dict]) -> tuple[list[Order], list[str]]:
    """Возвращает (принятые, причины отказов) — отказ не теряется и не роняет программу."""
    accepted: list[Order] = []
    rejected: list[str] = []
    for idx, raw in enumerate(items, start=1):
        try:
            accepted.append(Order.model_validate(raw))
        except ValidationError as exc:
            reasons = "; ".join(
                f"{'.'.join(str(p) for p in e['loc']) or 'строка'}: {e['msg'].removeprefix('Value error, ')}"
                for e in exc.errors()
            )
            logger.warning("заявка %d: %s", idx, reasons)
            rejected.append(f"заявка {idx}: {reasons}")
    return accepted, rejected
```

Пустой `loc` (ошибка модели из `model_validator`) заменяется словом `строка`, а
служебное `Value error, ` отрезается — пользователь видит `заявка 3: на продвинутый уровень нужен балл не ниже 4`.

# Тесты на ошибки

Проверяют и удачный путь, и отказ:

```python
import pytest
from pydantic import ValidationError

from orders import Order


def test_order_ok() -> None:
    """Правильная заявка проходит."""
    order = Order(client="Аня", email="a@b", items=["ручка"])
    assert order.client == "Аня"


def test_empty_items() -> None:
    """Заявка без позиций отклоняется."""
    with pytest.raises(ValidationError) as info:
        Order(client="Аня", email="a@b", items=[])
    assert info.value.errors()[0]["loc"] == ("items",)


def test_bad_email_has_path() -> None:
    """Неверная почта — путь указывает на поле."""
    with pytest.raises(ValidationError) as info:
        Order(client="Аня", email="непочта", items=["ручка"])
    # зависит от валидатора почты, но структура та же
    assert "email" in str(info.value.errors()[0]["loc"])
```

В `pytest.raises` можно получить само исключение и проверить **структуру** ошибки: какое поле,
какой тип. Это надёжнее, чем сверять весь текст сообщения — он может измениться при
обновлении Pydantic.

Граничные тесты тоже нужны:

```python
def test_client_boundary() -> None:
    """Ровно 2 символа — уже можно, 1 — нельзя."""
    assert Order(client="Ан", email="a@b", items=["р"]).client == "Ан"
    with pytest.raises(ValidationError):
        Order(client="А", email="a@b", items=["р"])
```

# Как это делают в проекте

Обработка ошибок валидации — архитектура, а не «попробовать/поймать».

**1. Ловят один раз, на границе.**

```text
CLI / HTTP-handler  →  try: model_validate  →  except ValidationError → отчёт + лог
                     ↓ (успех)
                   сервис(модель) — без try
```

CLI-команда, обработчик файла, эндпоинт FastAPI — единственные места с `except ValidationError`.
Сервис `save_order(order: Order)` их не содержит.

**2. Логи — для разработчика, отчёт — для пользователя.**

```python
# лог — технический, со всеми полями и значениями
logger.warning("отклонена заявка 4: applicant.email: Value error, почта должна быть вида имя@домен | вход: %r", raw)

# отчёт — короткий
# заявка 4: applicant.email: почта должна быть вида имя@домен
```

Разница — как между `logging` и `print` в [[10. Отладка и диагностика]]: лог остаётся в файле,
отчёт идёт на экран.

**3. Свои тексты в валидаторах — чтобы не переводить `msg`.**

```python
@field_validator("email")
@classmethod
def check_email(cls, v: str) -> str:
    if "@" not in v:
        raise ValueError("почта должна быть вида имя@домен")  # русский — сразу для отчёта
    return v.lower()
```

Для встроенных `Field` текст остаётся английским — его либо мапят по `type` (`string_too_short`),
либо заменяют валидатором, если текст должен быть русским.

**4. Тесты на каждое правило, включая границу.**

Как в [[03. Тесты]]: минимальный, максимальный и ошибочный случай. Модель — часть кода,
а не «описание», и без теста она ломается тихо.

**5. Отказ не теряется.** Три варианта по ситуации:

| Ситуация | Что возвращать |
|---|---|
| CLI проверяет файл | `(принятые, отклонённые)` + `print` отчёта + `logger.warning` |
| API принимает запрос | `HTTP 422` с телом `{"detail": exc.errors()}` |
| Фоновая задача | `raise ValueError(...) from exc` — пусть упадёт с причиной |

Выбор зависит от канала, но общее правило — **отказ заметен и содержит путь до поля**.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Ошибку надо ловить в каждой функции» | Достаточно границы: внутри работают проверенные модели |
| «`msg` из Pydantic можно показать пользователю» | Это технический текст на английском; нужен свой |
| «`return None` — нормальная реакция на плохие данные» | Отказ должен быть заметен: исключение или явный результат-отчёт |
| «Логировать нужно только факт ошибки» | Логируют все ошибки с путями и значениями — иначе не отладить |
| «Текст ошибки можно проверять целиком в тесте» | Лучше проверять `loc` и `type`: тексты меняются |

# Проверь себя

1. Почему валидацию ловят на границе, а не везде?
2. Что даёт соединение `loc` через точку?
3. Чем запись для лога отличается от текста для пользователя?
4. Почему `return None` — плохая реакция на ошибку данных?
5. Что проверять в тесте, кроме самого факта `ValidationError`?

> [!success]- Ответы
> 1. Внутрь программы попадают уже проверенные модели, поэтому повторные проверки — лишний код.
> 2. Точный путь до проблемного места, включая индекс элемента списка.
> 3. Лог — технический, со всеми ошибками и значениями; текст для пользователя — короткий и понятный.
> 4. Отказ можно не заметить; лучше явное исключение или отчёт о причинах.
> 5. Поле (`loc`) и тип ошибки (`type`) — они стабильнее формулировок.

Материалы курса Python, на которые опирается лекция, и то, что она к ним добавляет:

- [[05. Язык Python - идентификаторы, операторы, типы данных]] — `try/except ValidationError as exc`, `raise ... from exc`: базис `try/except` из 05 теперь с цепочкой причин.
- [[15. Работа с файлами]] — `Path.read_text()` и `json.loads()`: чтение файла как источник `ValidationError`.
- [[07. Линейный алгоритм]] — `".".join(str(p) for p in loc)`: та же конкатенация строк, что в линейном алгоритме.

Что добавляет лекция: `try/except` получает предмет — `ValidationError` с **структурой** (`loc`, `type`, `msg`, `input`), а не просто текст. Лог и пользовательский отчёт разводятся, как `logging` vs `print` в дисциплине 02.
