# 08. Альтернативы и место Pydantic

> [!abstract] О чём лекция
> Pydantic — не единственный способ описать данные в Python. Есть `dataclass` из стандартной
> библиотеки, есть `TypedDict` для словарей, есть формы Django. Они решают разные задачи,
> и понимать разницу важнее, чем знать «правильный» инструмент.
>
> В конце — цена валидации в скорости и куда идти дальше после курса.

# Одна задача — три инструмента

Задача: точка на плоскости с координатами от −1000 до 1000.

```python
import timeit
from dataclasses import asdict, dataclass
from typing import TypedDict

from pydantic import BaseModel, Field, ValidationError


@dataclass
class PointDataclass:
    """Точка на плоскости (dataclass)."""

    x: float
    y: float


class PointModel(BaseModel):
    """Точка на плоскости (Pydantic)."""

    x: float = Field(ge=-1000, le=1000)
    y: float = Field(ge=-1000, le=1000)
```

# `dataclass`: структура без проверки

```python
loose = PointDataclass(x=1, y="2")
print("dataclass принимает строку:", loose, "| тип y:", type(loose).__name__)
print("asdict:", asdict(loose))
```

```text
dataclass принимает строку: PointDataclass(x=1, y='2') | тип y: str
asdict: {'x': 1, 'y': '2'}
```

Строка `"2"` осталась строкой, ограничения не проверялись. `dataclass` — это **соглашение
о структуре**: он удобен для внутренних объектов, которым доверяем, и почти бесплатен
по скорости. Но данные «снаружи» он не защищает.

# `TypedDict`: словарь с подсказкой

```python
class RawPoint(TypedDict):
    """Словарь-точка: только подсказка для редактора."""

    x: float
    y: float


raw: RawPoint = {"x": "один", "y": 2}
print("TypedDict не проверяет:", raw)
```

```text
TypedDict не проверяет: {'x': 'один', 'y': 2}
```

`TypedDict` существует для `mypy` и автодополнения: **во время выполнения** проверок нет
вовсе. Это полезно внутри программы, где типы уже гарантированы, и опасно на границе.

# Pydantic: проверка данных

Здесь то же создание, но правило уже встроено в модель:

```python
try:
    PointModel(x=-5000, y=2)
except ValidationError as exc:
    print("Pydantic отклоняет:", exc.errors()[0]["msg"])
```

```text
Pydantic отклоняет: Input should be greater than or equal to -1000
```

# Сравнение

|  | `dataclass` | `TypedDict` | Pydantic |
|---|---|---|---|
| проверка во время работы | нет | нет | да |
| приведение типов (`"2"` → `2`) | нет | нет | да |
| сериализация | `asdict` | вручную | `model_dump`, `model_dump_json` |
| ошибки с путём до поля | нет | нет | `ValidationError` с `loc` |
| настройки из окружения | нет | нет | `BaseSettings` |
| скорость создания | выше всех | выше всех | ниже (см. замер) |
| где уместен | внутренние структуры | тип словаря для mypy | данные на границе |

Замер на учебной машине (100 000 созданий):

```python
n = 100_000
dataclass_time = timeit.timeit("PointDataclass(1.0, 2.0)", globals=globals(), number=n)
model_time = timeit.timeit("PointModel(x=1.0, y=2.0)", globals=globals(), number=n)
print(f"dataclass: {dataclass_time / n * 1e6:.2f} мкс | Pydantic: {model_time / n * 1e6:.2f} мкс"
      f" | в {model_time / dataclass_time:.1f} раза медленнее")
```

```text
dataclass: 0.08 мкс | Pydantic: 0.53 мкс | в 6.4 раза медленнее
```

Разница «в 6 раз» выглядит внушительно, но речь о **половине микросекунды** на объект:
сто тысяч объектов — это 0.05 секунды. Показательно другое: превращать каждый внутренний
объект в модель Pydantic не нужно, потому что выигрыша нет, а шум в коде появляется.

# Pydantic и Django

В Django за проверку данных отвечают формы и модели (`Form`, `ModelForm`, `full_clean`):

| Задача | Инструмент Django | Pydantic |
|---|---|---|
| HTML-форма в браузере | форма с полями и виджетами | не подходит: нет отрисовки и привязки к запросу |
| проверка модели перед сохранением | `full_clean()`, валидаторы полей | можно, но обычно хватает Django |
| данные из API, JSON, CSV | писать вручную | Pydantic |
| настройки приложения | `settings.py` | `BaseSettings` ([[05. Настройки приложения]]) |

Практический вывод: в проекте на Django Pydantic **не заменяет формы**, а закрывает то,
что вне форм: импорт данных, ответы внешних сервисов, конфигурацию, обмен с другими
сервисами. Это разные слои, и они спокойно живут вместе.

> [!note] FastAPI
> FastAPI построен на Pydantic: те же модели описывают тело запроса, параметры и ответ,
> а документация API строится из схемы JSON ([[04. Сериализация и JSON]]). Если после
> Django захочется попробовать FastAPI, модели уже будут знакомы.

# Как это делают в проекте

Инструмент выбирают по источнику данных, а не по моде.

**1. Граница — Pydantic, внутри — `dataclass`.**

```python
# src/warehouse/service.py
from dataclasses import dataclass
from pydantic import BaseModel, Field, ValidationError

# внешнее: файл накладных — проверяем
class SupplyIn(BaseModel):
    title: str = Field(min_length=2)
    quantity: int = Field(gt=0)
    price: float = Field(gt=0)

# внутреннее: расчёт стоимости — доверяем
@dataclass
class Supply:
    title: str
    quantity: int
    price: float
    @property
    def cost(self) -> float:
        return self.quantity * self.price

def load_supplies(raw_list: list[dict]) -> list[Supply]:
    supplies: list[Supply] = []
    for raw in raw_list:
        try:
            validated = SupplyIn.model_validate(raw)
            supplies.append(Supply(**validated.model_dump()))
        except ValidationError as exc:
            print("пропущена:", exc.errors()[0]["msg"])
    return supplies

# дальше по коду — только Supply (dataclass), без проверок
def total_cost(supplies: list[Supply]) -> float:
    return sum(s.cost for s in supplies)
```

**2. `TypedDict` — для словарей, которые нельзя убрать.**

```python
# данные для шаблона Jinja/Django: словарь неизбежен, но тип подскажет
from typing import TypedDict

class TemplateContext(TypedDict):
    title: str
    rows: list[list[str]]

def render(ctx: TemplateContext) -> str:
    return f"<h1>{ctx['title']}</h1>"

# Pydantic здесь лишний — это не граница, а внутренняя передача
```

`TypedDict` не защищает во время работы, но `mypy` подсветит `ctx['titl']` как опечатку.

**3. Django-формы и Pydantic не смешивают на одном слое.**

```python
# forms.py — для браузера
from django import forms
class OrderForm(forms.Form):
    name = forms.CharField(min_length=2)
    email = forms.EmailField()

# import.py — для CSV вне браузера
from pydantic import BaseModel, field_validator
class OrderImport(BaseModel):
    name: str
    email: str
    @field_validator("email")
    @classmethod
    def check_email(cls, v: str) -> str:
        if "@" not in v: raise ValueError("почта вида имя@домен")
        return v.lower()
```

Формы — для `request.POST`, Pydantic — для `csv.DictReader` и `json.load`.

**4. Не оптимизируют заранее.** Сначала правильность, потом замер:

```python
import timeit
# замерили 6.4× — решили, что на 100 объектах это неважно
# а на 1 000 000 — уже перешли на dataclass внутри цикла
```

Это правило из [[13. Сложность и производительность]]: `timeit`/`cProfile` после,
а не вместо, чистого кода.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Pydantic лучше `dataclass` во всём» | Он медленнее и строже; для внутренних структур `dataclass` удобнее |
| «`TypedDict` проверяет данные» | Только подсказывает типам редактору и `mypy` |
| «Pydantic заменяет формы Django» | Формы работают с браузером и моделями Django; у Pydantic другая роль |
| «Валидация всё замедлит» | Цена — доли микросекунды; важно не проверять одно и то же дважды |
| «Модели нужны для каждого класса» | Модель — инструмент границы, а не обязательный элемент каждого класса |

> 3. Примерно в 6 раз на создание (0.08 против 0.53 мкс) — на практике это доли секунды.
> 4. Формы — HTML-формы и модели Django; Pydantic — данные из API, файлов и настройки.
