# 03. Валидаторы и проверки

> [!abstract] О чём лекция
> Типы и `Field` покрывают многое, но не всё: «имя с большой буквы», «оценка от 1 до 5»,
> «если баллов меньше 60, то `passed` должен быть `False`». Такие правила записывают
> **валидаторами** — функциями внутри модели.
>
> Здесь — два вида валидаторов: `field_validator` (проверяет одно поле) и `model_validator`
> (смотрит на модель целиком) — и главное правило: сообщение об ошибке пишут так, чтобы
> оно объясняло, **что именно не так**.

# `field_validator`: проверка одного поля

```python
from pydantic import BaseModel, ValidationError, field_validator


class Grade(BaseModel):
    """Оценка ученика."""

    student: str
    value: int

    @field_validator("student")
    @classmethod
    def check_student(cls, value: str) -> str:
        """Имя не пустое и с большой буквы."""
        cleaned = value.strip()
        if not cleaned:
            raise ValueError("имя не может быть пустым")
        return cleaned[0].upper() + cleaned[1:]

    @field_validator("value")
    @classmethod
    def check_value(cls, value: int) -> int:
        """Оценка от 1 до 5."""
        if not 1 <= value <= 5:
            raise ValueError("оценка должна быть от 1 до 5")
        return value
```

Что здесь важно:

1. **Декоратор указывает имя поля** — валидатор вызовется только для него.
2. **Под `@field_validator` ставят `@classmethod`** — так рекомендует документация Pydantic 2: первым параметром идёт `cls` (класс), а не `self`, потому что валидатор вызывается до создания экземпляра.
3. **Возвращаемое значение идёт в модель** — можно не только проверять, но и исправлять
   (`value.strip()` и первая заглавная буква).
4. **Ошибку поднимают через `ValueError`** с текстом, который увидит пользователь.

```python
print(Grade(student="  аня ", value=5))
```

```text
student='Аня' value=5
```

# Что видно при ошибке

```python
try:
    Grade(student="  ", value=7)
except ValidationError as exc:
    for error in exc.errors():
        print(error["loc"][0], "→", error["msg"])
    print()
    print(exc)
```

```text
student → Value error, имя не может быть пустым
value → Value error, оценка должна быть от 1 до 5

2 validation errors for Grade
student
  Value error, имя не может быть пустым [type=value_error, input_value='  ', input_type=str]
    For further information visit https://errors.pydantic.dev/2.13/v/value_error
value
  Value error, оценка должна быть от 1 до 5 [type=value_error, input_value=7, input_type=int]
    For further information visit https://errors.pydantic.dev/2.13/v/value_error
```

Печатать `exc` целиком полезно при отладке: видно и сообщение, и **какое значение** пришло.
В интерфейсе пользователю такие строки не показывают — из них берут `msg` и `loc`.

# `model_validator`: проверка связей между полями

Правило «сдано, если баллов не меньше 60» нельзя проверить по одному полю: нужно знать оба.
Для этого есть валидатор модели:

```python
from pydantic import Field, model_validator


class Exam(BaseModel):
    """Экзамен: баллы и оценка, согласованные между собой."""

    points: int = Field(ge=0, le=100)
    passed: bool

    @model_validator(mode="after")
    def check_pass(self) -> "Exam":
        """Оценка «сдано» должна соответствовать баллам."""
        if self.passed != (self.points >= 60):
            raise ValueError(f"при {self.points} баллах «сдано» = {self.points >= 60}")
        return self
```

```python
print(Exam(points=75, passed=True))
try:
    Exam(points=30, passed=True)
except ValidationError as exc:
    print(exc.errors()[0]["msg"])
```

```text
points=75 passed=True
Value error, при 30 баллах «сдано» = False
```

Режим `mode="after"` означает: валидатор выполняется **после** того, как все поля уже
приведены к своим типам, и получает готовую модель (`self`). Возвращать нужно её же.

> [!note] `mode="after"` vs `mode="before"`
> В курсе используется только `after` — проверка уже типизированных данных. `before`
> нужен редко (например, переименование ключа из API) и в базовый курс не входит.

# Когда что использовать

| Ситуация | Инструмент |
|---|---|
| значение должно быть в диапазоне | `Field(gt=..., le=...)` |
| строка определённой длины | `Field(min_length=..., max_length=...)` |
| значение из списка | `Literal[...]` |
| нормализация значения (обрезать пробелы, привести к нижнему регистру) | `field_validator` |
| сложное правило для одного поля (проверка контрольной суммы) | `field_validator` |
| связь между полями | `model_validator(mode="after")` |
| проверка, что значение есть в базе или файле | внешняя функция после валидации |

Правило простое: **сначала пробуют `Field`, потом `field_validator`, и только потом
`model_validator`.** Чем меньше кода в валидаторах, тем проще читать модель.

# Как это делают в проекте

Валидатор — место для **правила данных**, а не для бизнес-логики. Он быстрый, чистый и
говорит по-человечески.

**1. Сообщения — как в интерфейсе.** Текст из `raise ValueError` попадает в отчёт и в лог:

```python
# src/applications/models.py — реальный кусок из мини-проекта
from pydantic import BaseModel, field_validator

class Applicant(BaseModel):
    name: str
    email: str

    @field_validator("name")
    @classmethod
    def normalize_name(cls, value: str) -> str:
        """Убирает лишние пробелы и делает вид 'Аня Петрова'."""
        cleaned = " ".join(value.split())
        if len(cleaned) < 2:
            raise ValueError("имя должно содержать хотя бы 2 символа")
        return cleaned.title()  # "аня  петрова" → "Аня Петрова"

    @field_validator("email")
    @classmethod
    def check_email(cls, value: str) -> str:
        if "@" not in value or value.count("@") != 1:
            raise ValueError("почта должна быть вида имя@домен")
        local, domain = value.split("@")
        if not local or not domain or "." not in domain:
            raise ValueError("почта должна быть вида имя@домен")
        return value.lower()  # нормализация тоже здесь
```

Почему так: `normalize_name` и `check_email` — чистые функции без IO. Они не лезут в
базу («есть ли такой пользователь?»), не читают файл — только проверяют и нормализуют
строку. Проверка в базе — отдельный шаг после валидации.

**2. Нормализация — в валидаторе, правило — в `Field`.**

```python
class Comment(BaseModel):
    text: str = Field(min_length=1, max_length=500)  # правило — в Field

    @field_validator("text")
    @classmethod
    def normalize(cls, value: str) -> str:
        return " ".join(value.split())  # нормализация — в валидаторе
```

Разделение помогает читать модель: `Field` — что должно быть, валидатор — как привести.

**3. Один валидатор — одно правило.**

```python
# плохо: пять проверок в одной функции
@field_validator("name")
@classmethod
def check_all(cls, v: str) -> str:
    if not v.strip(): raise ValueError(...)
    if len(v) < 2: raise ValueError(...)
    if v.isdigit(): raise ValueError(...)
    return v.title()

# хорошо: одна функция — одна мысль (если правил много — их видно)
@field_validator("name")
@classmethod
def not_empty(cls, v: str) -> str:
    if not v.strip(): raise ValueError("имя не может быть пустым")
    return v
# следующее правило — либо второй валидатор, либо Field(min_length=2)
```

**4. Валидатор тестируется как функция.**

```python
# tests/test_models.py
import pytest
from pydantic import ValidationError
from applications.models import Applicant

def test_normalizes_name() -> None:
    assert Applicant(name="  аня  петрова ", email="a@b.ru").name == "Аня Петрова"

def test_empty_name_rejected() -> None:
    with pytest.raises(ValidationError) as info:
        Applicant(name="  ", email="a@b.ru")
    assert info.value.errors()[0]["loc"] == ("name",)
```

Тест ловит `ValidationError` и проверяет `loc` и текст — это надёжнее падения
«на плохих данных» в продакшене через неделю.

# Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Валидатор должен быть обычным методом с `self`» | Полевой валидатор — метод класса: `@field_validator(...)` и под ним `@classmethod` с параметром `cls` |
| «`raise ValueError` внутри валидатора ломает программу» | Pydantic перехватывает его и превращает в ошибку валидации |
| «Проверки можно делать в `__init__`» | Тогда ошибки будут обычными исключениями без структуры `loc`/`msg` |
| «Валидатор — место для бизнес-логики» | Только проверка и нормализация данных |
| «Одного валидатора на всё хватит» | Один валидатор — одно правило; вместе их собирает модель |

# Проверь себя

1. Чем `field_validator` отличается от `model_validator`?
2. Почему валидатор помечают `@classmethod`?
3. Что происходит с `ValueError`, поднятым внутри валидатора?
4. Где заканчиваются обязанности валидатора?
5. Как проверить, что валидатор работает и после правок не сломался?

> [!success]- Ответы
> 1. Первый проверяет одно поле, второй — всю модель (связи между полями).
> 2. Так рекомендует Pydantic 2: значение проверяется до создания экземпляра, поэтому первым параметром идёт класс `cls`, а не `self`.
> 3. Он превращается в элемент списка ошибок `ValidationError` с типом, сообщением и путём.
> 4. На проверке и нормализации данных: без базы, сети, чтения файлов.
> 5. Тестами: отдельно на правильные данные, отдельно на каждое нарушение.
