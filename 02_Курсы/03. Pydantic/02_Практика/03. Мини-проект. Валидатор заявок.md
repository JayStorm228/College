# 03. Мини-проект. Валидатор заявок

> [!abstract] Что это за проект
> Программа читает заявки на учебные курсы из JSON-файла, проверяет каждую моделью Pydantic
> и печатает отчёт: сколько заявок принято, какие отклонены и почему. Плохая заявка
> **не роняет программу** — она попадает в отчёт с путём до проблемного поля.
>
> Это итог курса: здесь соединяются модели и валидаторы
> ([[02. Модели и типы]], [[03. Валидаторы и проверки]]), настройки
> ([[05. Настройки приложения]]), вложенные данные ([[06. Модели в проекте]]) и работа
> с ошибками ([[07. Ошибки валидации в приложении]]).
>
> **Перед началом** пройди практики [[01. Практика. Модели и валидация]] и
> [[02. Практика. Настройки и JSON]], а также курс 1 — в проекте используются реестр,
> внедрение зависимостей, тесты и структура пакета
> ([[06. Проектирование - фабрики и реестры]], [[07. Внедрение зависимостей]],
> [[09. Структура проекта и модули]]).

# Что должно получиться

Программа запускается из корня проекта и печатает выбранный отчёт:

```text
$ PYTHONPATH=src CAMPAIGN="Осень 2026" python3 main.py
INFO кампания Осень 2026, отчёт: summary
Принято: 4
Отклонено: 4
Лучший балл: 5.0 (Жанна Крылова)
```

Отчёт по принятым заявкам:

```text
$ PYTHONPATH=src CAMPAIGN="Осень 2026" REPORT=text python3 main.py
INFO кампания Осень 2026, отчёт: text
Аня Петрова — Инженерные практики (Продвинутый), балл 4.5
Борис — NumPy (Базовый), балл 3.8
Жанна Крылова — Инженерные практики (Базовый), балл 5.0
Игорь — NumPy (Продвинутый), балл 4.8
```

Причины отказов:

```text
$ PYTHONPATH=src CAMPAIGN="Осень 2026" REPORT=rejected python3 main.py
INFO кампания Осень 2026, отчёт: rejected
заявка 3: на продвинутый уровень нужен средний балл не ниже 4
заявка 4: applicant.email: почта должна быть вида имя@домен
заявка 5: average: Input should be greater than or equal to 2
заявка 6: level: Input should be 'Базовый' or 'Продвинутый'
```

В лог (не в отчёт) уходит предупреждение на каждую отклонённую заявку:

```text
WARNING отклонена заявка 3: на продвинутый уровень нужен средний балл не ниже 4
```

Настройка `LIMIT` ограничивает длину отчёта:

```text
$ PYTHONPATH=src CAMPAIGN="Осень 2026" REPORT=rejected LIMIT=2 python3 main.py
заявка 3: на продвинутый уровень нужен средний балл не ниже 4
заявка 4: applicant.email: почта должна быть вида имя@домен
… ещё 2 строк
```

Если обязательной настройки нет — понятное сообщение вместо трейсбека:

```text
$ PYTHONPATH=src python3 main.py
не заданы настройки: campaign (смотри .env.example)
```

# Как идти

1. **Подготовь проект.** Стартовых заготовок нет — создай файлы сам:

   ```text
   applications-check/
   ├── src/applications/__init__.py
   ├── src/applications/models.py
   ├── src/applications/sources.py
   ├── src/applications/reports.py
   ├── src/applications/config.py
   ├── main.py
   ├── tests/test_applications.py
   ├── data/applications.json
   ├── pyproject.toml
   ├── .gitignore
   ├── .env.example
   └── README.md
   ```

2. **Настрой `pyproject.toml`** — в нём зависимости и правила инструментов:

   ```toml
   [project]
   name = "applications"
   version = "0.1.0"
   requires-python = ">=3.11"
   dependencies = ["pydantic>=2.13", "pydantic-settings>=2.15"]

   [dependency-groups]
   dev = ["pytest>=9.1", "mypy>=2.3", "black>=26.5", "ruff>=0.16"]

   [tool.black]
   line-length = 88

   [tool.ruff]
   line-length = 88

   [tool.ruff.lint]
   select = ["E", "F", "I", "UP", "B"]

   [tool.mypy]
   plugins = ["pydantic.mypy"]
   python_version = "3.11"
   ```

   Плагин `pydantic.mypy` учит `mypy` понимать поля моделей. Отдельных исключений для
   `Settings` не нужно: `BaseSettings` принимает поля через `**values`, и вызов
   `Settings()` без аргументов `mypy` пропускает (проверено на mypy 2.3.1 и
   pydantic-settings 2.15.0).

3. **Сделай первый коммит** до кода: `.gitignore` (`.venv/`, `__pycache__/`, `.env`),
   `pyproject.toml`, `README.md` и пустые модули с docstring.

4. **Начни с моделей.** `Applicant` с двумя валидаторами, затем `Application`
   с вложенным `applicant` и валидатором модели. Сразу пиши тесты: правильная заявка,
   нормализация имени, плохая почта, балл вне диапазона, неизвестный уровень,
   «Продвинутый» с баллом 3.5.

5. **Добавь источники.** `MemorySource` для тестов, `JsonSource` для файла. Проверь,
   что `load()` возвращает «сырые» словари: валидацией занимается не источник,
   а сервис проверки.

6. **Собери проверку.** `CheckResult` с двумя списками, `check_all` с `try/except
   ValidationError`, `format_error` для причины. Проверь на своём файле: должно получиться
   **4 принятых и 4 отклонённых** заявки.

7. **Добавь отчёты и настройки.** Три отчёта в реестре `REPORTS`, `cut` для настройки
   `LIMIT`, `Settings` с `CAMPAIGN`, `REPORT`, `LIMIT`. В `main()` — чтение настроек
   с понятной ошибкой и логирование.

8. **Прогони проверки:** `pytest`, `mypy`, `black --check`, `ruff check`. Затем сверь
   выводы со списком ниже — числа должны совпасть.

9. **Закоммить по шагам.** Хорошая история: «Структура и модели заявок», «Источники
   и проверка заявок», «Отчёты, настройки и точка входа», «Тесты и проверки».

# Пример-аналог

> [!example]- Склад: проверка накладных (другая задача, то же устройство)
> Это **не решение** твоего проекта, а маленькая программа, собранная похожим образом:
> другая предметная область, но те же приёмы — вложенная валидация, нормализация,
> валидатор модели, разделение на принятые и отклонённые, причины отказов.
>
> ```python
> """Склад: проверка накладных."""
>
> import logging
> from datetime import date
>
> from pydantic import BaseModel, Field, ValidationError, field_validator, model_validator
>
> logger = logging.getLogger("warehouse")
>
>
> class Supply(BaseModel):
>     """Поставка: товар, количество, цена и скидка."""
>
>     title: str = Field(min_length=2, max_length=40)
>     quantity: int = Field(gt=0, le=1000)
>     price: float = Field(gt=0)
>     discount: float = Field(default=0, ge=0, le=50)
>     delivered: date | None = None
>
>     @field_validator("title")
>     @classmethod
>     def normalize_title(cls, value: str) -> str:
>         """Убирает лишние пробелы и пишет каждое слово с большой буквы."""
>         return " ".join(value.split()).title()
>
>     @model_validator(mode="after")
>     def check_discount(self) -> "Supply":
>         """Скидка положена только от 10 штук."""
>         if self.discount > 0 and self.quantity < 10:
>             raise ValueError("скидка только при количестве от 10 штук")
>         return self
>
>
> def check_supplies(items: list[dict]) -> tuple[list[Supply], list[str]]:
>     """Делит накладные на принятые и отклонённые с причинами."""
>     accepted: list[Supply] = []
>     rejected: list[str] = []
>     for number, raw in enumerate(items, start=1):
>         try:
>             accepted.append(Supply.model_validate(raw))
>         except ValidationError as exc:
>             reasons = "; ".join(
>                 f"{'.'.join(str(part) for part in err['loc']) or 'строка'}: "
>                 f"{err['msg'].removeprefix('Value error, ')}"
>                 for err in exc.errors()
>             )
>             message = f"накладная {number}: {reasons}"
>             logger.warning("%s", message)
>             rejected.append(message)
>     return accepted, rejected
>
>
> if __name__ == "__main__":
>     logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
>     items = [
>         {"title": "  ручка   гелевая ", "quantity": 100, "price": 50, "discount": 10},
>         {"title": "тетрадь", "quantity": 5, "price": 40, "discount": 5},
>         {"title": "папка", "quantity": 20, "price": 610},
>         {"title": "я", "quantity": 3, "price": -1},
>     ]
>     accepted, rejected = check_supplies(items)
>     print("принято:", len(accepted), "| отклонено:", len(rejected))
>     total = sum(item.quantity * item.price * (1 - item.discount / 100) for item in accepted)
>     print("итог:", total)
> ```
>
> Запуск (`python3 -u warehouse.py 2>&1` — сообщения лога идут в поток ошибок, поэтому их
> направляют в тот же поток, что и `print`):
>
> ```text
> WARNING накладная 2: строка: скидка только при количестве от 10 штук
> WARNING накладная 4: title: String should have at least 2 characters; price: Input should be greater than 0
> принято: 2 | отклонено: 2
> итог: 16700.0
> ```
>
> Посмотри, **что здесь общее** с твоим проектом: путь до поля собирается через точку
> («applicant.email»), пустой путь заменяется словом, из сообщения убирается служебное
> «Value error,», а отказ не прерывает проверку остальных записей. Разница — в предметной
> области, а она у тебя другая.

# Если застрял

| Симптом | Куда смотреть |
|---|---|
| `ModuleNotFoundError: No module named 'applications'` | [[09. Структура проекта и модули]]: запуск из корня с `PYTHONPATH=src` |
| В отчёте пустой путь: `заявка 3: : Value error, …` | [[07. Ошибки валидации в приложении]]: у ошибки модели `loc` пуст — обработай это в `format_error` |
| Вместо понятного сообщения — длинный `ValidationError` при `Settings()` | [[05. Настройки приложения]]: поймай `ValidationError` в `main()` и напечатай имена пропущенных полей |
| Тест читает настоящий `data/applications.json` | [[07. Внедрение зависимостей]]: подмени источник на `MemorySource` |
| `KeyError: 'html'` вместо понятной ошибки | [[01. Обработка ошибок полностью]]: неизвестный отчёт должен давать сообщение со списком доступных |
| Правило «Продвинутый» не срабатывает | [[03. Валидаторы и проверки]]: проверь, что это `model_validator`, а не `field_validator` |
| `ruff` ругается на строку длиннее 88 | [[11. Читаемость кода]]: перенеси строку, а не увеличивай `line-length` |

# Типичные ошибки

| Ошибка | Чем плоха |
|---|---|
| Читать файл прямо в модели | модель перестаёт быть описанием данных и становится сервисом |
| `except ValidationError: continue` без записи причины | отказы исчезают: отчёт «правильный», но неполный |
| Проверка почты внешней библиотекой | лишняя зависимость для учебного проекта; начни с простого правила |
| Настройки зашиты в код | нельзя сменить отчёт или лимит без правки программы |
| Трейсбек при отсутствии `CAMPAIGN` | пользователь видит внутренности Pydantic вместо подсказки |
| Тесты, читающие рабочий файл заявок | тест зависит от данных, которые кто-то поменяет |
| `print` вместо логирования | сообщения попадают в вывод отчёта и ломают его разбор |
