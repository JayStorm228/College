# 01. Практика. Модели и валидация

> [!abstract] О чём эта практика
> Три задачи по лекциям [[01. Зачем валидировать данные]], [[02. Модели и типы]] и
> [[03. Валидаторы и проверки]]. Сначала простая модель с приведением типов, затем модель
> с ограничениями и значениями по умолчанию, в конце — свои валидаторы: нормализация имени
> и согласованность полей.

> [!important] Как работать с задачей
> 1. Прочитай условие и **не открывай разбор**.
> 2. Запусти код и посмотри, какие типы получились у полей.
> 3. Проверь границы: минимальные и максимальные значения, пустые строки, `None`.
> 4. Сверься с разбором, особенно в том, какие тексты ошибок приходят.

## Задача 1. Первая модель

★☆☆ · `BaseModel`, приведение типов, `ValidationError`

**Условие.** Данные приходят из CSV, поэтому всё в них — строки:

```python
raw = {"name": "Аня", "grade": "9", "average": "4.5"}
```

**Задание.** 1) Опиши модель `Student` с полями `name`, `grade`, `average`.
2) Создай ученика из этих данных и напечатай его. 3) Выведи типы `grade` и `average`.
4) Посчитай «класс после года учёбы» (`grade + 1`) и удвоенный балл. 5) Попробуй создать
модель с `grade="девятый"` и объясни, что произойдёт.

> [!example]- Разбор
> **Идея.** Модель объявляет ожидаемые типы, а Pydantic приводит данные к ним. Строка `"9"`
> становится числом, и с ним можно считать — без `int(...)` в каждом месте программы.
>
> **Код.**
>
> ```python
> from pydantic import BaseModel, ValidationError
>
>
> class Student(BaseModel):
>     """Ученик: имя, класс и средний балл."""
>
>     name: str
>     grade: int
>     average: float
>
>
> anna = Student(name="Аня", grade="9", average="4.5")
> print(anna)
> print("типы:", type(anna.grade).__name__, type(anna.average).__name__)
> print("после года учёбы:", anna.grade + 1, "| удвоенный балл:", anna.average * 2)
>
> try:
>     Student(name="Борис", grade="девятый", average=3.8)
> except ValidationError as exc:
>     error = exc.errors()[0]
>     print("ошибок:", exc.error_count())
>     print("поле:", error["loc"][0], "|", error["msg"])
> ```
>
> **Вывод:**
>
> ```text
> name='Аня' grade=9 average=4.5
> типы: int float
> после года учёбы: 10 | удвоенный балл: 9.0
> ошибок: 1
> поле: grade | Input should be a valid integer, unable to parse string as an integer
> ```
>
> **Что здесь важно.** Печать модели (`name='Аня' grade=9 average=4.5`) показывает значения
> и типы — это удобно для отладки. Ошибка содержит и поле (`grade`), и понятное сообщение:
> из такой структуры можно собрать и подсказку пользователю, и текст в лог.
>
> **Типичная ошибка.** Писать `average = float(raw["average"])` вручную «на всякий случай» —
> тогда модель теряет смысл: она уже это делает. Вторая ошибка — ловить `ValueError` вместо
> `ValidationError`: Pydantic поднимает именно свой тип исключения.
>
> **Граница.** Если данных нет вовсе (`{}`), каждая ошибка будет `Field required` — по одной
> на каждое обязательное поле. А `None` в `average` даст другую ошибку: «Input should be
> a valid number». Различай «поле отсутствует» и «поле есть, но пустое».

## Задача 2. Ограничения и значения по умолчанию

★★☆ · `Field`, `Literal`, `default_factory`, `date | None`

**Условие.** Курс описывается так: название (от 3 до 60 символов), часы (больше 0
и не больше 200), уровень — «базовый» или «продвинутый» (по умолчанию базовый, если не указан),
теги (список строк, по умолчанию пустой), дата старта (может быть неизвестна).

**Задание.** 1) Опиши модель `Course` со всеми ограничениями. 2) Создай курс
`{"title": "NumPy", "hours": "40", "tags": ["массивы"]}` и напечатай его. 3) Убедись,
что теги двух разных курсов **не связаны** между собой: измени теги одного — у второго
ничего не поменялось. 4) Создай три ошибки сразу: название «ИИ», 500 часов
и уровень «экспертный» — и посмотри, сколько ошибок вернёт Pydantic. 5) Разбери строку
даты `"2026-10-01"` в поле `started`.

> [!example]- Разбор
> **Идея.** `Field` превращает тип в правило, `Literal` — в список допустимых значений,
> `default_factory` создаёт **новый** список каждому экземпляру, а `date | None`
> позволяет не указывать дату. Pydantic собирает **все** ошибки, поэтому пользователю
> не нужно исправлять их по одной.
>
> **Код.**
>
> ```python
> from datetime import date
> from typing import Literal
>
> from pydantic import BaseModel, Field, ValidationError
>
>
> class Course(BaseModel):
>     """Курс: название, часы, уровень, теги, дата старта."""
>
>     title: str = Field(min_length=3, max_length=60)
>     hours: int = Field(gt=0, le=200)
>     level: Literal["базовый", "продвинутый"] = "базовый"
>     tags: list[str] = Field(default_factory=list)
>     started: date | None = None
>
>
> numpy_course = Course(title="NumPy", hours="40", tags=["массивы"])
> print(numpy_course)
>
> another = Course(title="Matplotlib", hours=30)
> print("теги разных курсов:", another.tags, numpy_course.tags)
> another.tags.append("графики")
> print("после правки тегов первого:", another.tags)
> print("у второго теги не изменились:", numpy_course.tags)
>
> try:
>     Course(title="ИИ", hours=500, level="экспертный")
> except ValidationError as exc:
>     for error in exc.errors():
>         print(error["loc"][0], "→", error["msg"])
>
> started_course = Course(title="Pydantic", hours=20, started="2026-10-01")
> print("дата разобрана:", started_course.started, type(started_course.started).__name__)
> ```
>
> **Вывод:**
>
> ```text
> title='NumPy' hours=40 level='базовый' tags=['массивы'] started=None
> теги разных курсов: [] ['массивы']
> после правки тегов первого: ['графики']
> у второго теги не изменились: ['массивы']
> title → String should have at least 3 characters
> hours → Input should be less than or equal to 200
> level → Input should be 'базовый' or 'продвинутый'
> дата разобрана: 2026-10-01 date
> ```
>
> **Что здесь важно.** Про «ИИ»: название из двух букв короче минимальной длины — это
> **третья** ошибка, хотя в условии она не упоминалась. Так и должно быть: ограничение
> работает независимо от того, помним мы о нём или нет. Строка даты стала объектом `date`.
>
> **Типичная ошибка.** Написать `tags: list[str] = []` по привычке: в Pydantic это работает
> (значение копируется), но тот же код в `dataclass` даст `ValueError`, а в обычной функции —
> общий список. Поэтому список по умолчанию пишут через `default_factory`. Второй случай — написать `hours: int` без ограничений
> и потом проверять «а не слишком ли много» вручную.
>
> **Граница.** `hours=200` разрешено (`le=200`), `hours=200.5` — уже нет. `hours="40"`
> принимается: Pydantic приводит строку к числу. А `hours="сорок"` — нет, будет ошибка
> `int_parsing`.

## Задача 3. Свои валидаторы

★★★ · `field_validator`, `model_validator`, нормализация и связи

**Условие.** Нужны две проверки, которые не выразить типами:

1. Имя ученика нужно **нормализовать**: убрать лишние пробелы и сделать каждое слово
   с большой буквы; пустое имя — ошибка.
2. У экзамена есть баллы (0–100) и признак «сдано». Признак должен соответствовать баллам:
   сдано тогда и только тогда, когда баллов не меньше 60.

**Задание.** 1) Опиши `Grade` с валидаторами поля: нормализация имени и проверка оценки
от 1 до 5. 2) Проверь, что `Grade(student="  аня   петрова ", value=5)` даёт «Аня Петрова».
3) Проверь, что пустое имя и оценка 6 дают **две** ошибки. 4) Опиши `Exam` с валидатором
модели и проверь, что `Exam(points=30, passed=True)` отклоняется, а `points=75, passed=True` —
принимается.

> [!example]- Разбор
> **Идея.** Валидатор поля отвечает за одно значение (и может его изменить), валидатор
> модели — за согласованность. Нормализация на входе удобна: дальше по программе имя уже
> в едином виде, и не нужно «приводить к красивому виду» в трёх местах.
>
> **Код.**
>
> ```python
> from pydantic import BaseModel, Field, ValidationError, field_validator, model_validator
>
>
> class Grade(BaseModel):
>     """Оценка: имя нормализуется, значение ограничено."""
>
>     student: str
>     value: int
>
>     @field_validator("student")
>     @classmethod
>     def normalize_student(cls, value: str) -> str:
>         """Убирает лишние пробелы и делает первую букву заглавной."""
>         cleaned = " ".join(value.split())
>         if not cleaned:
>             raise ValueError("имя не может быть пустым")
>         return cleaned.title()
>
>     @field_validator("value")
>     @classmethod
>     def check_value(cls, value: int) -> int:
>         """Оценка от 1 до 5."""
>         if not 1 <= value <= 5:
>             raise ValueError("оценка должна быть от 1 до 5")
>         return value
>
>
> print(Grade(student="  аня   петрова ", value=5))
>
> try:
>     Grade(student="   ", value=6)
> except ValidationError as exc:
>     for error in exc.errors():
>         print(error["loc"][0], "→", error["msg"])
>
> print(Grade(student="борис", value="4"))
> ```
>
> ```text
> student='Аня Петрова' value=5
> student → Value error, имя не может быть пустым
> value → Value error, оценка должна быть от 1 до 5
> student='Борис' value=4
> ```
>
> ```python
> class Exam(BaseModel):
>     """Экзамен: баллы и признак сдачи должны совпадать."""
>
>     points: int = Field(ge=0, le=100)
>     passed: bool
>
>     @model_validator(mode="after")
>     def check_consistency(self) -> "Exam":
>         """«Сдано» тогда и только тогда, когда баллов не меньше 60."""
>         expected = self.points >= 60
>         if self.passed != expected:
>             raise ValueError(f"при {self.points} баллах «сдано» должно быть {expected}")
>         return self
>
>
> print(Exam(points=75, passed=True))
>
> try:
>     Exam(points=30, passed=True)
> except ValidationError as exc:
>     print(exc.errors()[0]["msg"])
> ```
>
> ```text
> points=75 passed=True
> Value error, при 30 баллах «сдано» должно быть False
> ```
>
> **Что здесь важно.** `" ".join(value.split())` — простой способ убрать любые лишние
> пробелы, а `.title()` делает слова заглавными; вместе это нормализация. Валидатор модели
> получает уже готовый объект (`self.points` — число), поэтому в нём нет проверок типов.
>
> **Типичная ошибка.** Забыть `@classmethod` — Pydantic выдаст ошибку при определении
> класса. Вторая ошибка — «починить» данные вместо ошибки (например, обрезать 120 баллов
> до 100): тихая правка хуже честного отказа.
>
> **Граница.** Валидатор срабатывает и когда поля задаются по отдельности, и при чтении
> из JSON — правило одно на все пути. Но `model_copy(update=...)` его **не вызовет**
> ([[04. Сериализация и JSON]]): обновлять данные можно только через `model_validate`,
> если важна проверка.

# Что запомнить из практики

| Приём | Когда |
|---|---|
| `BaseModel` и типы полей | данные приходят строками, нужны числа |
| `Field(gt=..., le=..., min_length=...)` | числовые и строковые ограничения |
| `Literal[...]` | выбор из перечисленных значений |
| `Field(default_factory=list)` | изменяемое значение по умолчанию |
| `X \| None = None` | необязательное поле |
| `field_validator` | нормализация и сложная проверка одного поля |
| `model_validator(mode="after")` | согласованность между полями |
