# 17. Решение сложных задач — структуры данных и проектирование

> [!abstract] О чём лекция
> Сложная программа начинается не с набора ключевых слов, а с понимания задачи. Соберём
> переносимый инженерный метод: требования, входы и границы, модель данных, алгоритм, оценка
> затрат, доказательство ключевого свойства, тесты, модульный дизайн и улучшение по измерениям.
>
> **Зачем это нужно.** Одно решение может быть правильным для десяти строк и непригодным для
> миллиона. Подбор структуры данных и алгоритма должен учитывать требуемые операции и ограничения,
> а не только количество строк кода.
>
> **После лекции ты сможешь:** превратить текст задачи в спецификацию, выбрать между основными
> контейнерами STL, оценить время и память, обосновать корректность через инвариант, подобрать
> систематические тесты и оформить решение как поддерживаемую программу.

## Сложная задача — несколько вопросов, а не одна загадка

До кода выпиши:

1. **Цель и пользователь:** кто запускает программу и какое решение/отчёт ему нужен?
2. **Вход:** формат, диапазоны, единицы, возможны ли пустые/повторяющиеся/неверные данные?
3. **Выход:** точный формат и порядок результатов.
4. **Ограничения:** сколько данных, какой объём памяти/время допустимы, какие компиляторы/ОС?
5. **Правила предметной области:** какие допущения и запреты должны быть сохранены?
6. **Ошибочные условия:** как программа должна сообщить о проблеме?

Если чего-то не хватает, сформулируй открытый вопрос, а не выдумывай требование. В учебной
задаче явно запиши допущение, если условие намеренно оставляет деталь неопределённой.

## От формулировки к алгоритму

Используй цикл проектирования:

```text
условие → вход/выход → примеры и границы → модель состояния → простой алгоритм →
обоснование → сложность → код → тесты → профилирование/улучшение
```

### 1. Сначала простой корректный алгоритм

Набросай шаги словами или псевдокодом. Например: «для каждого идентификатора увеличить
счётчик именно этого идентификатора; затем вывести пары идентификатор/количество в требуемом
порядке». Не оптимизируй до того, как ясны данные и ограничения.

### 2. Выбери структуру по нужным операциям

| Структура | Основное назначение | Типичная стоимость/особенность |
|---|---|---|
| `std::array<T, N>` | Фиксированное число элементов | Индекс `O(1)`; размер задан в типе. |
| `std::vector<T>` | Последовательность с быстрым индексом и проходом | Индекс `O(1)`; добавление в конец амортизированно `O(1)`; середина требует сдвигов. |
| `std::deque<T>` | Последовательность с добавлением на обоих концах | Удобен, если часто работают с передним и задним концом. |
| `std::map<K, V>` | Ключи с упорядоченным обходом | Поиск/вставка обычно `O(log n)`; отчёт естественно получается в порядке ключа. |
| `std::unordered_map<K, V>` | Быстрый поиск по хешируемому ключу | Среднее `O(1)`, худшее `O(n)`; порядок обхода не гарантирован. |
| `std::set<T>` / `unordered_set<T>` | Уникальные значения | Проверка наличия; упорядоченное дерево или хеш-таблица. |
| `std::queue<T>` | Обработка в порядке поступления | FIFO: first in, first out. |
| `std::stack<T>` | Последним пришёл — первым обработан | LIFO: last in, first out. |
| `std::priority_queue<T>` | Каждый раз брать элемент с наивысшим приоритетом | Полезна для очереди событий/задач; не хранит полный отсортированный порядок. |

Это типичные оценки, не обещание конкретной скорости на каждом входе. `std::list` тоже есть,
но он редко нужен по умолчанию: выбери его лишь если требуемые операции/стабильность ссылок
оправдывают дополнительные расходы и ты сравнил с вектором.

### 3. Обоснуй корректность

Для цикла сформулируй инвариант: «после обработки первых `i` входных записей структура
содержит точное число появлений каждого уже встреченного ключа». Затем проверь:

- **Инициализация:** до первого элемента счётчик пуст; утверждение верно для нуля записей.
- **Сохранение:** обработка следующего ключа увеличивает только его число на один.
- **Завершение:** после последней записи инвариант охватывает весь вход.

Это короткое рассуждение сильнее, чем «на нескольких примерах вышло правильно».

## Пример: частоты идентификаторов

Требование: дан набор строковых идентификаторов, вывести число появлений каждого идентификатора
в алфавитно-лексикографическом порядке ключа `std::string`.

```cpp
#include <cstddef>
#include <iostream>
#include <map>
#include <string>
#include <vector>

int main() {
    const std::vector<std::string> ids{
        "room-a", "room-b", "room-a", "room-c", "room-b", "room-a"
    };

    std::map<std::string, std::size_t> frequencies;
    for (const std::string& id : ids) {
        ++frequencies[id];
    }

    for (const auto& [id, count] : frequencies) {
        std::cout << id << ": " << count << '\n';
    }
    return 0;
}
```

Здесь используется **structured binding** C++17 (значит, он доступен в C++20):
`[id, count]` получает имена пары ключ/значение. `std::map` автоматически упорядочивает
ключи по своему правилу сравнения. У `std::string` это не обязательно культурно-языковая
сортировка русских/локализованных имён; для технических ASCII-идентификаторов порядок подходит.

Почему `map`?

- `std::map` делает число каждого ключа доступным через `frequencies[id]`.
- Вставка/обновление стоит `O(log k)`, где `k` — число разных ключей.
- Весь проход по `n` входным элементам даёт примерно `O(n log k)` времени и `O(k)` дополнительной
  памяти.
- Вывод уже упорядочен, что прямо соответствует условию.

Если порядок не нужен и ключи корректно хешируются, `unordered_map` обычно даёт среднее
`O(n)` на обновления, но для стабильного отчёта тогда пришлось бы отдельно сортировать ключи.
Выбор зависит от полного требования, включая формат вывода.

## Тесты: не только счастливый путь

Для частотного подсчёта подбери небольшую матрицу:

| Вход | Что проверить |
|---|---|
| Пустой набор | Вывод пустой; ошибки и выдуманной строки нет. |
| Один идентификатор | Частота равна `1`. |
| Один ключ повторён `n` раз | Значение равно `n`. |
| Несколько разных ключей | Каждый выведен ровно один раз. |
| Ключи в обратном порядке | Результат `map` всё равно упорядочен. |
| Строки отличаются регистром | Поведение совпадает с явно выбранным сравнением; `Room-A` и `room-a` обычно разные ключи. |
| Ошибка чтения файла/ввода | Программа сообщает о сбое и не выдаёт неполный отчёт как успешный. |

Для границ используй допустимый максимум из требований, а не произвольные «огромные числа».
Подумай о пустом значении, повторениях, максимальной длине строки и нечитаемом файле.

## Сложность — инструмент принятия решения

Сначала оцени алгоритм по входному размеру:

- Один проход по данным — обычно `O(n)`.
- Вложенный полный проход по парам — обычно `O(n²)`.
- Сортировка перед единственным поиском может добавить `O(n log n)`, а для многих запросов
  окупиться.
- Хеш-таблица обычно обменивает дополнительную память на среднюю скорость доступа.
- Упорядоченная map дороже по асимптотике, но сохраняет порядок и предсказуемое логарифмическое
  поведение.

Сложность не измеряет всё: константные факторы, локальность данных, выделение памяти и читаемость
важны. Если данные малы, простой линейный алгоритм может быть лучшим. Для производительности
сначала сделай корректно, затем измерь на представительных данных.

## От задачи до структуры программы

В большом решении раздели ответственности:

- **ввод/парсинг** превращает внешний текст в проверенные данные;
- **предметная логика** обрабатывает типы/контейнеры без консольных деталей;
- **представление результата** формирует отчёт;
- **тесты** проверяют предметные функции без реального файла и клавиатуры.

Выноси чистые вычисления в функции, типы — в классы/структуры, публичные объявления — в
заголовки там, где модуль действительно переиспользуется. Не дроби задачу на файлы ради числа
файлов: граница модуля должна иметь понятный смысл.

## Проверка и измерение производительности

1. Сначала включи предупреждения и отладочную информацию.
2. Проведи функциональные тесты, включая ошибки ввода и границы.
3. Проверь корректность под AddressSanitizer/UndefinedBehaviorSanitizer, если используемый GCC
   это поддерживает.
4. Сравни результаты на репрезентативных данных.
5. Только затем измеряй время или профилируй горячие места.
6. После каждого улучшения снова запускай весь набор тестов.

Один замер на ноутбуке не становится переносимой гарантией. Оптимизируй по требованиям проекта,
а не по красивому совету из случайного обсуждения.

## Рабочий чек-лист решения

Перед завершением задачи ответь:

- Правильно ли я понял вход, выход и ограничения?
- Определены ли единицы измерения и допустимые диапазоны?
- Обрабатываются ли пустые данные и ошибки чтения?
- Выбран ли контейнер по операциям, которые действительно нужны?
- Обосновал ли я, почему цикл/алгоритм даёт правильный результат?
- Проверил ли тестом обе границы каждого существенного условия?
- Оценил ли время и память при максимальном `n`?
- Можно ли прочитать имена функций/переменных без догадки?
- Сохраняет ли проект и интерфейсы понятные границы?
- Если заявляю, что решение быстрее, измерил ли это на тех же данных?

## Без олимпиадного обязательства

Алгоритмы и структуры данных важны и в прикладной разработке, но этот курс не требует
соревновательной математики, специальных трюков или обязательного олимпиадного маршрута.
Цель — распознавать форму задачи, выбирать разумные стандартные средства, оценивать затраты,
обосновывать корректность и самостоятельно читать документацию, когда встречается новая область.
Специализированный трек можно добавить позже под учебную или рабочую потребность.

## Как это делают в проекте

Не начинай с вопроса «какое слово C++ применить?». Начни с того, что должен получить пользователь
и что известно о данных. Затем выбери представление, сформулируй алгоритм и его инвариант,
оцени сложность, запиши тесты и только потом реализуй. Когда тесты проходят, отдели ввод/вывод
от предметного расчёта и проверь, можно ли объяснить каждую часть другому разработчику.

## Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «У сложной задачи обязательно должен быть сложный алгоритм» | Иногда стандартная структура/один проход решают её лучше. |
| «Хеш-таблица гарантирует O(1)» | Обычно это средняя оценка; худший случай хуже, а порядок не задан. |
| «Меньшая Big-O всегда быстрее на любых данных» | Постоянные расходы, размер входа и локальность тоже важны; нужно измерение. |
| «Примеры доказали алгоритм» | Они проверяют случаи; для обоснования сформулируй инвариант/аргумент корректности. |
| «Пустой ввод не важен, потому что в задании есть данные» | Реальный файл/пользователь может принести пустые данные или ошибку чтения. |
| «Надо оптимизировать до первого запуска» | Сначала простое корректное решение и тесты; оптимизация должна отвечать измеренной проблеме. |
| «Профессиональный C++ требует ручной памяти и собственных структур» | Стандартные контейнеры и RAII — нормальная отправная точка; ручной низкоуровневый контроль нужен по особой причине. |

## Ключевые термины

| Термин | Объяснение |
|---|---|
| Требование | Проверяемое ожидание о поведении/ограничениях программы. |
| Спецификация | Точное описание входов, выходов, ошибок и допустимого поведения. |
| Структура данных | Способ представить и организовать данные для нужных операций. |
| Инвариант алгоритма | Свойство состояния, которое сохраняется на каждом шаге и обосновывает корректность. |
| `std::map` | Упорядоченное ассоциативное отображение ключей в значения. |
| `std::unordered_map` | Ассоциативное отображение на хеш-таблице без гарантированного порядка обхода. |
| Асимптотическая сложность | Описание роста времени/памяти при увеличении входа. |
| Профилирование | Измерение выполнения, показывающее фактические горячие места. |
| Регрессионный тест | Проверка, которая не даёт уже исправленной ошибке незаметно вернуться. |
| Локальность данных | Насколько часто соседние данные находятся близко в памяти; влияет на реальную скорость. |
