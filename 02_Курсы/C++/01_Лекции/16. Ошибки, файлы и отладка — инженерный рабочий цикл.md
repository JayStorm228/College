# 16. Ошибки, файлы и отладка — инженерный рабочий цикл

> [!abstract] О чём лекция
> Надёжная программа — это не код без ошибок на удачном примере, а код, который обнаруживает
> неправильные условия, показывает причину сбоя и проверяется повторяемым способом. Соберём
> рабочий процесс диагностики, познакомимся с gdb и Visual Studio Debugger, научимся читать
> строки/файлы и выбирать уместный способ сообщать об ошибке.
>
> **Зачем это нужно.** У программы есть разные классы сбоев — синтаксис, компоновка, неверный
> ввод, ошибка алгоритма и неопределённое поведение. У них разные источники и разные способы
> исправления.
>
> **После лекции ты сможешь:** классифицировать диагностику, локализовать сбой минимальным тестом,
> поставить breakpoint и проследить состояние, проверить текстовый ввод/файл, написать простые
> автоматические проверки, использовать исключение для нарушения контракта и распознать UB.

## Пять разных видов проблемы

| Вид | Пример | Когда обнаруживается | Первый шаг |
|---|---|---|---|
| Ошибка препроцессора | Не найден нужный заголовок | До компиляции единицы | Проверить `#include`, путь и установку инструментов. |
| Ошибка компиляции | Неверный тип, пропущенная `;` | Компиляция `.cpp` | Прочитать первое сообщение и контекст строки. |
| Ошибка компоновки | `undefined reference` | После компиляции объектов | Сверить определения и список файлов/библиотек. |
| Ошибка времени выполнения | Открыт неверный файл, программа получила сбой | При запуске | Сохранить точный вход/сообщение и локализовать операцию. |
| Логическая ошибка | Для валидного ввода выведен неверный ответ | Может пройти незамеченной | Сравнить с ожидаемым результатом и трассировать данные. |

Дополнительно есть **неопределённое поведение** (UB): стандарт C++ не задаёт, что должна
сделать программа, например при выходе за границы `vector`, чтении недопустимо используемого
неинициализированного значения, use-after-free или signed integer overflow. Не рассчитывай на
то, что UB «всегда даст мусор» или «сработает одинаково в Debug и Release».

## Диагностический цикл

1. **Зафиксируй точный симптом.** Сохрани сообщение, команду сборки, ОС/компилятор и входные данные.
2. **Установи этап.** Препроцессор, компилятор, компоновщик, запуск, предметная логика?
3. **Прочитай первое сообщение.** Поздние могут быть следствием первой ошибки.
4. **Сделай минимальный пример.** Убери нерелевантный код, сохрани вход, на котором дефект виден.
5. **Сформулируй ожидаемое и фактическое поведение.** Какая переменная впервые стала неверной?
6. **Измени одну причину за раз.** После исправления повтори тот же тест.
7. **Добавь регрессионный тест.** Исправленная ошибка не должна возвращаться незаметно.

Не переписывай программу целиком до того, как понял причину: так легко скрыть дефект, но не
устранить его.

## Предупреждения компилятора

В команде курса включены `-Wall -Wextra -Wpedantic`. Предупреждение — не всегда ошибка, но
часто полезный сигнал: неиспользованная переменная, подозрительное преобразование, отсутствие
возврата по пути выполнения. Прочитай его и исправь первопричину, если это возможно.

Не делай сборку «чистой», выключая предупреждения проекта. В MSVC учебный проект настраивается
на высокий разумный уровень предупреждений. Предупреждение можно обоснованно подавить только
локально и с документированной причиной.

## Отладчик: увидеть состояние, а не угадывать

Отладчик позволяет остановиться на строке, посмотреть значения и пройти выполнение пошагово.
Для начала собери с отладочной информацией (`-g`, уже есть в команде курса).

### gdb в WSL Ubuntu

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -g app.cpp -o app
gdb ./app
```

В gdb введи:

```text
break main    # поставить точку останова на входе в main
run           # запустить
next          # выполнить текущую строку, не входя в вызываемую функцию
step          # выполнить строку, входя в вызываемую функцию
print value   # показать текущее значение переменной value
backtrace     # показать цепочку вызовов, если программа остановилась/упала
continue      # продолжить до следующей точки останова
quit          # выйти из gdb
```

Имена локальных переменных доступны только в их области жизни/видимости. Если gdb не находит
символ, проверь, что собрал текущий исходник с `-g` и не запускаешь старый исполняемый файл.

### Visual Studio Debugger

- Щёлкни слева от строки кода, чтобы поставить breakpoint (часто клавиша `F9`).
- `F5` запускает/продолжает отладку.
- `F10` выполняет следующую строку без входа в функцию; `F11` заходит внутрь вызова.
- Посмотри `Locals` и добавь выражение в `Watch`.
- `Shift+F5` останавливает сеанс отладки.

Названия окон и клавиш могут измениться в конкретной версии Visual Studio; смысл один: breakpoint,
step over, step into, просмотр переменных и стека вызовов.

## Ввод целой строки и строгий разбор числа

`std::cin >> number` удобен для простого учебного ввода, но надёжное приложение должно решить,
принимает ли оно пробелы, лишний текст, пустую строку и значения вне допустимого диапазона.
Для контроля формата полезно прочитать целую строку, затем разобрать её отдельно:

```cpp
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::string line;
    std::cout << "Enter one whole number: ";
    if (!std::getline(std::cin, line)) {
        std::cerr << "No input line.\n";
        return 1;
    }

    std::istringstream parser{line};
    int value{};
    char extra{};
    if (!(parser >> value) || (parser >> extra)) {
        std::cerr << "Expected one integer and nothing else.\n";
        return 1;
    }

    std::cout << "Accepted: " << value << '\n';
    return 0;
}
```

`std::istringstream` читает текст как поток. Второе чтение в `extra` проверяет, не остался ли
после числа ещё непробельный символ. Например, `42` и ` 42 ` принимаются, а `42abc` и пустая
строка отвергаются. Это всё ещё не предметная проверка диапазона: если задача допускает только
числа от 1 до 100, добавь отдельное условие `value >= 1 && value <= 100`.

Чтение одной строкой также избегает неожиданного остаточного `\n` после форматированного
`std::cin >>`. Если всё же смешиваешь методы, нужно сознательно очистить состояние/остаток потока.

## Текстовый файл: `ifstream` и RAII

```cpp
#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream input{"notes.txt"};
    if (!input) {
        std::cerr << "Cannot open notes.txt\n";
        return 1;
    }

    std::string line;
    while (std::getline(input, line)) {
        std::cout << line << '\n';
    }

    if (input.bad()) {
        std::cerr << "I/O error while reading notes.txt\n";
        return 1;
    }
    return 0;
}
```

`std::ifstream` объявлен в `<fstream>`; его объект владеет файловым ресурсом и закрывает файл
при завершении жизни (RAII). Путь `notes.txt` считается относительно текущего каталога
процесса, а не автоматически относительно места, где лежит `.cpp`. В IDE рабочий каталог
задаётся настройками запуска; в терминале он обычно тот, из которого ты вызвал программу.

Если файл пустой, цикл просто не выполнит тело. Если открыть его не удалось, проверка
`if (!input)` отрабатывает до чтения. Не пиши `while (!input.eof())`: `eof()` становится
истинным только после попытки чтения за концом файла, поэтому такая схема часто дублирует
последнюю строку или обрабатывает невалидные данные.

Для записи применяют `std::ofstream`; тоже проверь открытие и результат записи. Если приложение
обязано сохранять отчёт, не сообщай «готово», пока не убедился, что запись прошла успешно.

## Ошибки ввода и исключения

Выбирай способ сообщения по типу ситуации:

- **Обычный неверный пользовательский ввод** — ожидаемая ситуация. Проверь его и покажи
  понятное сообщение/предложи повторить.
- **Отсутствующий необязательный результат** — интерфейс может вернуть `std::optional<T>`.
- **Нарушение контракта** или неожиданная невозможность выполнить операцию может сообщаться
  исключением, например `std::invalid_argument` или `std::runtime_error`.
- **Системный/файловый сбой** можно обрабатывать проверкой потока или исключениями, если они
  включены и согласованы в проекте.

Исключение можно перехватить и сообщить об ошибке:

```cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        // Вставь сюда вызов, который может выбросить std::invalid_argument.
    } catch (const std::invalid_argument& error) {
        std::cerr << "Invalid argument: " << error.what() << '\n';
        return 1;
    } catch (const std::exception& error) {
        std::cerr << "Unexpected failure: " << error.what() << '\n';
        return 1;
    }
    return 0;
}
```

Исключения перехватывают по `const&`, не по значению: так избегают копирования базового
объекта и сохраняют динамический тип. Не ловить `...` без причины: так можно скрыть ошибку,
которую ты не умеешь восстановить. Благодаря RAII файлы и `unique_ptr` освобождают ресурсы и
при раскрутке стека исключением.

Исключения не должны заменять обычный `if` для ожидаемых вариантов вроде «элемент не найден»,
если в интерфейсе естественно вернуть `bool`/`optional`. Обсуди политику ошибки на границе
модуля и не оставляй исключение без обработчика там, где программа обязана продолжить работу.

## Утверждения: `assert` для внутренних предположений

```cpp
#include <cassert>

int divide_exactly(int numerator, int denominator) {
    assert(denominator != 0);  // условие разработчика, а не проверка пользователя
    return numerator / denominator;
}
```

`assert` помогает поймать нарушенный внутренний инвариант во время разработки. В сборках с
`NDEBUG` проверки могут быть отключены, поэтому `assert` **не заменяет** валидацию внешнего ввода
и не должен содержать выражений с обязательными побочными эффектами.

Для пользовательского делителя напиши явную проверку и выбери результат/сообщение ошибки.
Не рассчитывай, что `assert` всегда включён на компьютере пользователя.

## Тесты: проверять контракт, не одну строку вывода

Для каждой важной функции зафиксируй ожидаемые входы/выходы. Минимальный набор:

1. Обычный случай.
2. Ноль или пустые данные.
3. Нижняя и верхняя границы допустимого диапазона.
4. Соседнее недопустимое значение.
5. Повторяющиеся значения/пустой файл/неверная строка — если они возможны.

Можно временно написать маленький тестовый драйвер и сравнить результат с ожидаемым. В этом
курсе часть задач использует `assert` для упражнений; для настоящего проекта лучше подключить
тестовый фреймворк и запускать тесты автоматически при изменении кода.

Тесты проверяют выбранные случаи, а не доказывают корректность для всех возможных входов.
Дополняй их рассуждением об инварианте и границах из блока
[[17. Решение сложных задач — структуры данных и проектирование]].

## Санитайзеры GCC: подсказка о части UB

В WSL можно дополнительно собрать программу так:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -g \\
    -fsanitize=address,undefined -fno-omit-frame-pointer app.cpp -o app_checked
./app_checked
```

AddressSanitizer и UndefinedBehaviorSanitizer помогают найти некоторые ошибки памяти и
неопределённое поведение во время конкретного запуска. Их доступность зависит от toolchain;
они не заменяют тесты, не доказывают отсутствие всех дефектов и обычно не являются настройкой
производительной сборки.

## Как читать stack trace

Если программа упала, **backtrace/stack trace** показывает цепочку функций: от текущего места
до вызовов, которые привели к нему. Начни с первого кадра в своём коде, проверь аргументы и
состояние объекта, затем отступи к вызывающему коду. Самый глубокий кадр может быть внутри
стандартной библиотеки, потому что ошибка была передана ей через неверный индекс/состояние.

## Как это делают в проекте

Надёжный инженерный цикл — часть решения, а не работа «после готового кода»:

1. Сохрани воспроизводимый вход.
2. Раздели разбор/валидацию входа и предметный расчёт.
3. Обрабатывай ошибки файла до того, как выдаёшь успешный результат.
4. Проверяй чистые функции независимыми тестами.
5. Используй отладчик для ответа на конкретный вопрос о состоянии.
6. Включай предупреждения; при необходимости — санитайзеры.
7. После исправления добавляй регрессионную проверку.
8. Не подавляй предупреждения и не маскируй ошибку общим `catch` без решения, как восстановиться.

## Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Компилятор не выдал ошибку — программа верна» | Логика, ввод, границы и UB проверяются отдельно. |
| «`assert` проверит ввод пользователя и в Release» | Он может быть отключён через `NDEBUG`; внешние данные валидируют обычным кодом. |
| «Ненулевой адрес и завершившаяся сборка гарантируют безопасность памяти» | Указатель может быть висячим; часть дефектов проявляется только при выполнении. |
| «Надо каждый раз смотреть на последнюю строку компилятора» | Первое сообщение часто объясняет каскад последующих ошибок. |
| «`while (!file.eof())` — правильный файловый цикл» | Читай потоком через `while (std::getline(...))`, затем проверяй I/O-сбой. |
| «Любую ошибку надо бросать исключением» | Обычный отказ и отсутствие результата часто удобнее представить явно; политика зависит от контракта. |
| «Отладчик исправит причину за меня» | Он показывает состояние; разработчик формулирует гипотезу, проверяет и исправляет алгоритм. |
| «Санитайзер подтвердил безопасность навсегда» | Он обнаруживает часть ошибок в запущенных путях, но не анализирует все входы и исполнения. |

## Ключевые термины

| Термин | Объяснение |
|---|---|
| Компиляционная ошибка | Диагностика, из-за которой исходная единица не превращается в объектный код. |
| Ошибка компоновки | Проблема связывания объектных файлов, символов или библиотек. |
| Ошибка времени выполнения | Сбой или некорректная операция после запуска программы. |
| Логическая ошибка | Программа выполняется, но не соблюдает требуемый смысл/результат. |
| Неопределённое поведение (UB) | Случай, когда стандарт C++ не задаёт поведение программы. |
| Отладчик | Инструмент остановки и пошагового исследования состояния. |
| Breakpoint | Точка, в которой отладчик приостанавливает выполнение. |
| Регрессионный тест | Тест, который закрепляет исправление известной ошибки. |
| `assert` | Проверка предположения разработчика; может отсутствовать в release-сборке. |
| Исключение | Механизм передачи ошибочного/исключительного состояния к обработчику. |
| RAII | Управление ресурсом через время жизни объекта; работает и при выходе из-за исключения. |
| Address/UndefinedBehaviorSanitizer | Инструменты GCC/Clang, находящие часть ошибок памяти/UB при запуске. |
| Stack trace / backtrace | Цепочка активных вызовов, ведущая к текущей точке исполнения. |
