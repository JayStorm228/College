# 14. Наследование и полиморфизм — когда нужны интерфейсы

> [!abstract] О чём лекция
> Наследование позволяет описать специализацию типа, а виртуальные функции — вызывать
> переопределённое поведение через интерфейс базового класса. Разберём abstract class,
> `override`, виртуальный деструктор, объектное срезание и важное правило: сначала проверить,
> нужна ли здесь композиция вместо наследования.
>
> **Зачем это нужно.** Полиморфизм позволяет работать с разными реализациями через общий контракт.
> Но неуместная иерархия усложняет изменение программы; наследование — инструмент, а не способ
> переиспользовать любое похожее поле.
>
> **После лекции ты сможешь:** объяснить динамический полиморфизм, объявить чисто виртуальную
> функцию, корректно переопределить её, хранить разные реализации за `unique_ptr<Base>` и
> назвать ситуации, в которых лучше выбрать композицию.

## Отношение «является», а не просто «похоже»

Если круг **является** фигурой, его можно подставить в код, которому нужна фигура. Это естественная
основа наследования. Если автомобиль **содержит** двигатель, двигатель не становится видом
автомобиля — здесь естественнее поле-компонент и композиция.

Наследование уместно, когда специализированный тип действительно выполняет контракт базового
типа во всех предусмотренных ситуациях. Если часть наследника нарушает ожидания базового
интерфейса, иерархия неверно выражает предметную область.

## Интерфейс базового класса

```cpp
class Shape {
public:
    virtual ~Shape() = default;

    virtual double area() const = 0;
};
```

- `virtual` сообщает, что функция может иметь переопределённую реализацию в производном классе.
- `= 0` — чисто виртуальная функция: базовый класс задаёт требование, но не реализацию.
- Класс с чисто виртуальной функцией **абстрактный**: нельзя создать объект `Shape` напрямую.
- `virtual ~Shape() = default` — виртуальный деструктор. Он нужен, если объекты-наследники
  уничтожают через указатель на базовый класс.

`Shape` определяет публичный контракт: любая конкретная фигура сообщает площадь.

> [!note] Примеры зависят друг от друга
> Блок реализации ниже использует `Shape`, определённый выше. Следующие блоки с функциями и
> контейнером также являются фрагментами того же файла: для запуска соедини определения типов
> и добавь `<iostream>`, `<numbers>`, `<memory>` и `<vector>`; инструкции контейнера помести в
> `main`. Заголовки `Shape` и производных классов не нужно объявлять повторно.

## Реализации: `Circle` и `Rectangle`

```cpp
#include <numbers>

class Circle final : public Shape {
public:
    explicit Circle(double radius) : radius_{radius} {}

    double area() const override {
        return std::numbers::pi * radius_ * radius_;
    }

private:
    double radius_{};  // предусловие примера: radius >= 0
};

class Rectangle final : public Shape {
public:
    Rectangle(double width, double height)
        : width_{width}, height_{height} {}

    double area() const override {
        return width_ * height_;
    }

private:
    double width_{};   // предусловие примера: размеры >= 0
    double height_{};
};
```

- `: public Shape` означает публичное наследование: публичный интерфейс `Shape` остаётся
  публичным для пользователей производного типа.
- `override` просит компилятор проверить, что функция действительно переопределяет виртуальный
  метод базового класса. Опечатка в параметре/`const` не пройдёт незамеченной.
- `final` запрещает наследоваться дальше от этих конкретных классов. Это необязательно, но
  полезно, если специализация завершена.

Для полноценных типов следует валидировать радиус/размеры и поддерживать инварианты, как показано
в [[11. Свои типы и классы — данные с правилами]]. Здесь код сфокусирован на интерфейсе
полиморфизма; предусловия указаны прямо.

## Динамический вызов

```cpp
#include <iostream>

void print_area(const Shape& shape) {
    std::cout << shape.area() << '\n';
}
```

`print_area` принимает ссылку на базовый интерфейс и не знает, круг это или прямоугольник.
Виртуальный вызов выбирает реализацию фактического объекта **во время выполнения**.

Можно хранить набор разнотипных фигур за одним интерфейсом:

```cpp
#include <memory>
#include <vector>

std::vector<std::unique_ptr<Shape>> shapes;
shapes.push_back(std::make_unique<Circle>(2.0));
shapes.push_back(std::make_unique<Rectangle>(3.0, 4.0));

for (const auto& shape : shapes) {
    std::cout << shape->area() << '\n';
}
```

`unique_ptr<Shape>` владеет объектом-наследником; виртуальный деструктор обеспечивает корректное
уничтожение через базовый указатель. `->` вызывает метод на объекте, на который указывает
умный указатель. `shape` в цикле — ссылка на smart pointer, чтобы не копировать владельца.

Для очень простой программы можно хранить `Circle` и `Rectangle` отдельными векторами, а
посчитать значение при создании. Полиморфная иерархия полезна, когда общий интерфейс должен
обрабатывать набор сменяемых реализаций.

## Динамический и статический полиморфизм

- **Динамический полиморфизм** (`virtual`) выбирает реализацию во время выполнения по фактическому
  типу объекта.
- **Статический полиморфизм** (перегрузки и шаблоны) разрешается компилятором для конкретного
  типа. Шаблоны разберём в [[15. Шаблоны и concepts — общий код с ограничениями]].

Выбор зависит от потребности: нужен ли единый набор объектов разных конкретных типов, меняющийся
во время выполнения, или алгоритм может сгенерироваться отдельно для типа при компиляции.

## Объектное срезание

Если копировать производный объект **по значению** в переменную базового типа, копируется только
базовая часть объекта — специфическое состояние и поведение наследника теряются. Это называется
**object slicing** (срезание объекта).

Абстрактный `Shape` выше нельзя скопировать в объект `Shape`, но та же проблема появляется
у не-абстрактных базовых классов. Для полиморфного поведения используй ссылки/указатели на
базовый интерфейс и ясное владение, а не контейнер объектов базового типа.

## Когда выбрать композицию

| Ситуация | Обычно яснее |
|---|---|
| Один объект использует/содержит другой | Композиция: `Car` содержит `Engine`. |
| Тип — корректная специализация общего понятия | Наследование: `Circle` реализует `Shape`. |
| Нужно добавить необязательную возможность/настройку | Компонент, стратегия/функция или отдельный интерфейс — зависит от требований. |
| Иерархия строится только ради повторного использования пары полей | Пересмотреть дизайн; возможно, помощник-компонент или обычная функция. |

Начинай с композиции; переходи к наследованию, когда общий контракт и отношение замещения
обоснованы. Это не запрет на наследование, а способ не создавать жёсткую связь без необходимости.

## Интерфейс и реализация по нескольким файлам

В больших проектах базовый класс и его реализации обычно размещают в заголовках/исходниках,
используя правила блока [[09. Заголовки и несколько файлов — объявления и сборка]]. Для
простого интерфейса с чисто виртуальной функцией объявление можно хранить в заголовке;
определения методов наследников — в их `.cpp`.

При виртуальных методах не забывай:

1. публичные операции базового класса описывают обещания для всех реализаций;
2. деструктор базового класса должен быть публичным виртуальным, если удаление через base-указатель допустимо;
3. на каждом переопределённом методе ставь `override`;
4. не передавай полиморфный объект по значению;
5. не заставляй вызывающую сторону проверять тип и перечислять всех наследников, если базовый контракт уже решает задачу.

## Ограничения и затраты

Виртуальный вызов добавляет механизм динамической диспетчеризации, а динамическое хранение
объектов может потребовать выделения памяти. Для многих приложений цена мала, но полиморфизм
выбирают ради ясной архитектуры, а не автоматически. Если набор типов известен и алгоритм
короткий, шаблон или `std::variant` могут быть подходящими альтернативами; их применение зависит
от требований.

## Как это делают в проекте

Перед созданием базового класса сформулируй общую операцию, которую должны поддерживать все
реализации. Затем попробуй написать функцию, принимающую ссылку на базовый тип. Если для каждого
наследника внутри функции всё равно нужны отдельные `if` и приведение типа, абстракция может
быть неполной.

## Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Наследование нужно, чтобы переиспользовать любой код» | Оно должно выражать корректное отношение подстановки и общий контракт. |
| «Публичное наследование — это просто скопировать поля базового класса» | Оно формирует отношение между интерфейсами и влияет на диспетчеризацию. |
| «`virtual` не нужен, если вызов сделан через `Base&`» | Без виртуальности вызывается выбранная по статическому типу функция; динамического выбора нет. |
| «`override` — украшение» | Оно позволяет компилятору обнаружить неверную сигнатуру переопределения. |
| «Объект наследника можно спокойно копировать в `Base`» | При передаче по значению теряется производная часть — объектное срезание. |
| «`unique_ptr<Base>` удалит наследника некорректно» | Виртуальный деструктор базового класса обеспечивает правильную цепочку уничтожения. |

## Ключевые термины

| Термин | Объяснение |
|---|---|
| Базовый класс | Тип, который задаёт общий интерфейс/основу наследников. |
| Производный класс | Специализированный тип, публично или иначе наследующий базовый. |
| Виртуальная функция | Функция, реализация которой может выбираться динамически. |
| Абстрактный класс | Класс с хотя бы одной чисто виртуальной функцией; напрямую не создаётся. |
| Чисто виртуальная функция | Виртуальная функция с `= 0`, задающая обязательный интерфейс. |
| `override` | Проверяемая компилятором пометка переопределения виртуальной функции. |
| Динамический полиморфизм | Выбор реализации в момент выполнения по динамическому типу объекта. |
| Объектное срезание | Потеря производной части при копировании объекта по значению в базовый тип. |
| Композиция | Связь «содержит», когда объект собран из других объектов. |
| Деструктор | Специальная функция, автоматически вызываемая при завершении времени жизни объекта. |
