# 15. Шаблоны и concepts — общий код с ограничениями

> [!abstract] О чём лекция
> Шаблон позволяет написать один алгоритм для нескольких типов. Но слишком свободный шаблон
> может принимать неподходящие данные и выдавать длинные непонятные ошибки. Разберём вывод типа,
> шаблоны функций и классов, ограничения concepts C++20 и связь шаблонов с заголовочными файлами.
>
> **Зачем это нужно.** `std::vector<int>` и `std::vector<std::string>` — примеры одного шаблонного
> контейнера с разными типами элементов. Понимание шаблонов помогает переиспользовать обобщённый
> код библиотеки и создавать собственные функции без копирования алгоритма для каждого типа.
>
> **После лекции ты сможешь:** написать шаблонную функцию, объяснить вывод параметра типа,
> ограничить его концептом, различить обобщение во время компиляции и runtime-полиморфизм и
> объяснить, почему определение шаблона обычно должно быть видно в месте использования.

## Один алгоритм — несколько типов

Предположим, есть функция, которая возвращает большее из двух значений. Для `int`, `double`
и `std::string` можно было бы написать три почти одинаковых перегруженных функции. Шаблон
описывает общий алгоритм один раз:

```cpp
template <typename T>
T larger(T left, T right) {
    return left < right ? right : left;
}
```

> [!note] Контекст коротких примеров
> Вызовы ниже используют этот шаблон и являются фрагментами тела `main`. Для примеров с
> `std::string` добавь `<string>`. Блоки с концептами далее показывают альтернативные объявления;
> не помещай два определения одной и той же `larger` в один файл.

`T` — параметр типа, который будет заменён конкретным типом при использовании. Например:

```cpp
int bigger_score{larger(80, 92)};
double longer_distance{larger(2.5, 4.0)};
```

Компилятор выводит `T` из аргументов: `int` для первого вызова, `double` для второго.

**Шаблон — не готовая машинная функция, которая умеет всё.** При компиляции компилятор
подставляет конкретный тип и проверяет, поддерживает ли он операции, использованные телом.
Если тип не подходит, вызов не скомпилируется.

## Шаблон функции с подходящим типом

```cpp
template <typename T>
T square(T value) {
    return value * value;
}
```

`T` должен поддерживать умножение `T * T`, а результат должен быть пригоден как `T`. `int`
и `double` подходят. Строка не имеет умножения строка-на-строку, поэтому `square(std::string{...})`
будет отвергнут компилятором.

Можно передать тип явно, хотя для простого `larger(80, 92)` он выводится автоматически:

```cpp
const int result{larger<int>(80, 92)};
```

Вывод типа не означает динамическое «угадывание» во время исполнения: конкретная специализация
создаётся при компиляции.

## Concepts C++20: документировать требования

В предыдущем шаблоне набор допустимых операций существовал только внутри тела. **Concept**
позволяет назвать ограничения и потребовать их у параметра типа.

```cpp
#include <concepts>

template <std::totally_ordered T>
T larger(T left, T right) {
    return left < right ? right : left;
}
```

`std::totally_ordered` — стандартный концепт C++20 из `<concepts>`. Он задаёт требования
согласованного полного порядка для типа, нужного операции `larger`. Ошибка неподходящего типа
возникает при вызове с более содержательной диагностикой, а контракт функции виден в заголовке.

Эквивалентный более развёрнутый синтаксис — **альтернатива** предыдущему объявлению `larger`
с `std::totally_ordered`, а не второе определение для копирования в тот же файл:

```cpp
template <typename T>
requires std::totally_ordered<T>
T larger(T left, T right) {
    return left < right ? right : left;
}
```

Концепт выражает требования к синтаксическим операциям и свойствам типа, но не доказывает,
что выбранное понятие предметной области подходит задаче. Тип может синтаксически сравниваться,
но сравнение может не иметь ожидаемого бизнес-смысла.

## Собственный concept на выражении `requires`

Если стандартного концепта нет, проверку нужного выражения можно описать так:

```cpp
#include <concepts>

template <typename T>
concept Multipliable = requires(T left, T right) {
    { left * right } -> std::convertible_to<T>;
};

template <Multipliable T>
constexpr T square(T value) {
    return value * value;
}

static_assert(square(4) == 16);
```

`requires`-выражение проверяет, что `left * right` допустимо и результат можно преобразовать
к `T`. `static_assert` проверяет утверждение при компиляции; если выражение ложно, сборка
останавливается с диагностикой.

Это учебный концепт, а не универсальная математическая теория умножения. Для production-кода
требования должны точно соответствовать операциям алгоритма; слишком слабые ограничения лишь
переносят ошибку дальше, а слишком сильные без нужды отсекают полезные типы.

## Шаблоны классов уже знакомы

В программе встречались следующие объявления. Это фрагмент тела функции; для отдельной сборки
нужны `<vector>`, `<string>` и `<array>`:

```cpp
std::vector<int> scores;
std::vector<std::string> names;
std::array<double, 3> point;
```

`std::vector<T>` — шаблон класса с параметром типа `T`; `std::array<T, N>` добавляет параметр
размера `N`, который является значением, а не типом. Одно определение контейнера применяется
к множеству типов и размеров.

## Полная короткая программа C++20

```cpp
#include <concepts>
#include <iostream>
#include <string>

template <std::totally_ordered T>
T larger(T left, T right) {
    return left < right ? right : left;
}

template <typename T>
concept Multipliable = requires(T left, T right) {
    { left * right } -> std::convertible_to<T>;
};

template <Multipliable T>
constexpr T square(T value) {
    return value * value;
}

int main() {
    std::cout << larger(12, 7) << '\n';
    std::cout << larger(std::string{"Ada"}, std::string{"Grace"}) << '\n';
    std::cout << square(5) << '\n';
    static_assert(square(4) == 16);
    return 0;
}
```

Строки сравниваются по определённому `std::string` порядку, который не обязательно совпадает
с человеческой сортировкой русских слов. Числовое `larger` соответствует обычному смыслу.
Собирай C++20-командой курса; C++17-компилятор не обязан знать `std::totally_ordered`.

## Шаблонная функция — не виртуальный метод

| Шаблон/concept | Виртуальная функция |
|---|---|
| Конкретный тип известен компилятору в месте создания специализации | Фактический тип выбирается во время выполнения |
| Часто приводит к коду, специализированному для типов | Даёт единый runtime-интерфейс для разных объектов |
| Ошибка несоответствия ограничению — при компиляции | Отсутствующая реализация может обнаружиться при дизайне/создании типа |
| Удобен для алгоритмов и операций над типами | Удобен для набора сменяемых реализаций через `Base&`/`Base*` |

Это два разных инструмента. Их можно сочетать, но не заменять друг другом автоматически.

## Почему определения шаблонов часто в заголовке

Компилятор должен увидеть тело шаблона, когда для конкретного типа создаёт его специализацию.
Поэтому обычный шаблон функции часто определяется целиком в `.h`/`.hpp` и подключается туда,
где его вызывают. В отличие от обычной функции из блока 09, скрыть единственное тело шаблона
только в несвязанном `.cpp` обычно недостаточно.

Правила ODR допускают одинаковые шаблонные определения в нескольких единицах трансляции при
выполнении специальных условий стандарта. Это не означает, что можно включать произвольные
`.cpp` или создавать разные тела под одним именем. Include guard по-прежнему полезен внутри
каждой единицы трансляции.

## Когда шаблон полезен

Шаблон оправдан, если один алгоритм действительно одинаков для разных типов, а различаются
данные и доступные операции. Например, `std::sort` не копирует свою реализацию под каждый тип
вручную.

Не превращай в шаблон каждую функцию: обычный конкретный тип часто проще читать, диагностировать
и сопровождать. Писать шаблон ради «более профессионального» вида бессмысленно.

## Как это делают в проекте

Перед шаблоном перечисли требования алгоритма простыми словами: «тип можно упорядочить»,
«диапазон можно пройти вперёд», «элементы можно сложить и результат сохранить». Затем:

1. Проверь, есть ли готовый концепт в `<concepts>`/`<ranges>`.
2. Ограничь параметр как можно точнее, но не строже, чем нужно.
3. Проверь полезные типы: встроенный, стандартный класс и собственный тип, если он реализует контракт.
4. Оставь определение доступным в месте инстанцирования.
5. Не создавай public generic API, пока не понял требования реального использования.

## Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Шаблон выполняется с любым типом» | Тип должен поддерживать каждую требуемую операцию и соответствовать ограничениям. |
| «Вывод типа происходит во время работы программы» | Для обычной инстанциации тип разрешается компилятором. |
| «Concept проверяет, что алгоритм имеет правильный смысл» | Он проверяет заявленные формальные требования; предметный смысл проектирует автор. |
| «Шаблоны и `virtual` решают одну задачу» | Первый обычно статически обобщает алгоритм, второй выбирает реализацию динамически. |
| «Тело шаблона можно убрать в `.cpp`, как у любой функции» | В месте инстанцирования тело обычно должно быть доступно. |
| «Чем больше шаблонов, тем лучше дизайн» | Необоснованное обобщение усложняет интерфейс и диагностику. |

## Ключевые термины

| Термин | Объяснение |
|---|---|
| Шаблон функции | Описание семейства функций с параметрами типа/значения. |
| Шаблон класса | Описание семейства типов, например `std::vector<T>`. |
| Параметр шаблона | Заполнитель типа или значения в объявлении шаблона. |
| Инстанцирование | Создание конкретной специализации шаблона для выбранных параметров. |
| Вывод типа | Определение параметра шаблона по аргументам вызова. |
| Concept | Именованный набор требований к параметрам шаблона. |
| `requires`-выражение | Синтаксическое описание выражений/ограничений, которые должен поддерживать тип. |
| Специализация | Конкретный вариант шаблона для заданного типа/значения. |
| Статический полиморфизм | Выбор и специализация поведения на этапе компиляции. |
| `static_assert` | Проверка логического условия во время компиляции. |
