# 09. Заголовки и несколько файлов — объявления и сборка

> [!abstract] О чём лекция
> Когда программа вырастает из одного файла, её полезно разделить на интерфейсы и реализации.
> Разберём, что помещают в заголовок, что — в `.cpp`, зачем нужны include guards, как компилятор
> собирает несколько единиц трансляции и как читать типичные ошибки компоновщика.
>
> **Зачем это нужно.** `#include` не «подключает библиотеку магическим образом»: исходные файлы
> компилируются отдельно, а затем их результаты связываются. Если объявление, определение и
> команда сборки не согласованы, программа не скомпонуется.
>
> **После лекции ты сможешь:** разделить программу на `.h` и `.cpp`, объяснить объявление и
> определение, защитить заголовок от повторного включения, собрать проект из двух `.cpp` и
> отличить ошибку компиляции от ошибки компоновки.

## Зачем разделять программу на файлы

Один файл подходит для маленького примера. В приложении могут работать несколько человек,
части должны быть переиспользуемыми, а изменения математической реализации не должны заставлять
читателя листать весь `main`.

Типичный подход:

- **заголовок** описывает публичный интерфейс: какие функции доступны и как их вызывать;
- **исходный `.cpp`** содержит определения/реализации функций;
- **главный `.cpp`** использует интерфейс и связывает действия программы.

Это не единственная архитектура, но полезный следующий шаг от программы в одном файле.

## Объявление и определение: повторение

Объявление сообщает компилятору, что функция существует и как выглядит её интерфейс:

```cpp
double sphere_volume(double radius);
```

Определение содержит тело:

```cpp
double sphere_volume(double radius) {
    return (4.0 / 3.0) * std::numbers::pi * radius * radius * radius;
}
```

Это фрагменты для уровня файла; перед таким определением подключи `<numbers>`, потому что
используется `std::numbers::pi`. Полная версия `sphere.cpp` с нужными заголовками приведена ниже.

Имя, тип результата и типы параметров должны соответствовать. Имя параметра в объявлении
можно опустить, но обычно имя делает контракт понятнее.

## Структура файлов

Создай одну папку проекта и три текстовых файла:

```text
sphere-project/
├── sphere.h
├── sphere.cpp
└── main.cpp
```

### `sphere.h`: интерфейс и include guard

```cpp
#ifndef COLLEGE_CPP_SPHERE_H
#define COLLEGE_CPP_SPHERE_H

// Вычисляет площадь поверхности сферы.
// Предусловие: radius >= 0.
double sphere_surface_area(double radius);

// Вычисляет объём сферы.
// Предусловие: radius >= 0.
double sphere_volume(double radius);

#endif  // COLLEGE_CPP_SPHERE_H
```

Guard (защитный макрос) не даёт телу заголовка обработаться дважды **в одной единице
трансляции**. Схема:

1. Если `COLLEGE_CPP_SPHERE_H` ещё не определён — выполнить содержимое.
2. Определить макрос.
3. На повторном `#include` условие ложно, и объявления второй раз не попадают в эту единицу.

Имя макроса делай уникальным для проекта и заголовка. В нём обычно используют заглавные буквы,
цифры и `_`.

### `sphere.cpp`: реализация

```cpp
#include "sphere.h"

#include <numbers>

// Определения функций из публичного интерфейса.
double sphere_surface_area(double radius) {
    return 4.0 * std::numbers::pi * radius * radius;
}

double sphere_volume(double radius) {
    return (4.0 / 3.0) * std::numbers::pi * radius * radius * radius;
}
```

Исходный файл подключает **свой заголовок**. Тогда компилятор сверяет определения с
объявленным интерфейсом. Заголовок `<numbers>` подключён явно, потому что этот `.cpp` использует
`std::numbers::pi`. Используем квадрат/куб умножением — отдельный `<cmath>` не требуется.

### `main.cpp`: использование интерфейса

```cpp
#include "sphere.h"

#include <iostream>

int main() {
    double radius{};
    std::cout << "Radius (non-negative): ";

    if (!(std::cin >> radius) || radius < 0.0) {
        std::cerr << "Enter a non-negative number.\n";
        return 1;
    }

    std::cout << "Area: " << sphere_surface_area(radius) << '\n';
    std::cout << "Volume: " << sphere_volume(radius) << '\n';
    return 0;
}
```

`main.cpp` видит объявления через `sphere.h`, а определения появятся на стадии компоновки из
`sphere.cpp`. `std::cerr` — поток диагностического вывода; код `1` отмечает ошибочный ввод.

## Угловые скобки и кавычки

В обычном стиле стандартный заголовок включают так:

```cpp
#include <iostream>
```

Свой файл проекта — кавычками:

```cpp
#include "sphere.h"
```

Это распространённое соглашение. Точный поиск по каталогам задаётся компилятором и ключами
поиска заголовков; не полагайся на непонятные абсолютные пути и не копируй файл стандартной
библиотеки в проект.

## Собираем вместе одной командой

Из каталога проекта выполни:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -g main.cpp sphere.cpp -o sphere_app
```

g++ компилирует `main.cpp` и `sphere.cpp`, затем передаёт полученные объектные файлы компоновщику.
Header-файлы в команду **не передают как самостоятельные исходники**: они попадают в каждую
единицу трансляции через `#include`.

Запуск:

```bash
./sphere_app
```

Ожидаемо: для радиуса `1` площадь близка к `12.5664`, объём — к `4.18879`.

## Раздельная компиляция и компоновка

Можно остановиться после компиляции каждого `.cpp`, затем скомпоновать объекты:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -g -c main.cpp -o main.o
g++ -std=c++20 -Wall -Wextra -Wpedantic -g -c sphere.cpp -o sphere.o
g++ main.o sphere.o -o sphere_app
```

Ключ `-c` означает: «скомпилировать/ассемблировать этот исходный файл в объектный, не
компоновать конечную программу». Последняя команда объединяет объектные файлы. Если поменялся
только `sphere.cpp`, достаточно пересобрать его и снова выполнить компоновку; крупные проекты
делают это автоматизированно системой сборки.

В Visual Studio/MSBuild те же роли скрыты за проектом: добавь оба `.cpp` в проект, сохрани
заголовок в папке проекта и убедись, что конфигурация использует C++20. Конкретная кнопка
сборки вызывает систему сборки, а не отменяет нужду определить все исходные файлы.

## Include guard — чего он не делает

Защитный макрос предотвращает повторное включение заголовка внутри одной единицы трансляции,
но **не** заменяет компоновку и не исправляет все ошибки повторных определений.

Например, если поместить обычное определение `sphere_volume` в заголовок и включить его в два
разных `.cpp`, каждый `.cpp` создаст свою копию определения. Guards сработают отдельно в каждом
файле, поэтому на стадии компоновки всё ещё может появиться `multiple definition`.

Для первой программы правило простое: в `.h` — объявления; обычное определение функции — в одном
`.cpp`. Исключения, например `inline` и шаблоны, имеют отдельные правила и будут объяснены позже.

`#pragma once` — широко поддерживаемая альтернатива в популярных компиляторах, но это не
директива, гарантированная стандартом C++. В базовом переносимом примере используем классические
include guards.

## Что такое единица трансляции и ODR

После препроцессинга каждый `.cpp` вместе со всеми включёнными объявлениями образует единицу
трансляции (translation unit). Каждая единица компилируется отдельно. Одна и та же функция
может быть **объявлена** в нескольких единицах, если декларации согласованы; обычное
не-inline-определение должно иметь единственное определение во всей программе. Общее правило
об этом называется **One Definition Rule (ODR)**.

Мы пока не рассматриваем все исключения ODR. Практический вывод: интерфейс можно включать
многократно, а реализацию размести ровно в одном `.cpp` и передай этот файл сборщику.

## Компилятор сообщил ошибку? Найди стадию

| Сообщение/симптом | Этап | Что проверить |
|---|---|---|
| `sphere.h: No such file or directory` | Препроцессинг | Имя файла, каталог, кавычки, пути поиска заголовков. |
| `sphere_volume was not declared` | Компиляция единицы | Подключён ли `sphere.h`, совпадает ли имя. |
| `undefined reference to sphere_volume(double)` | Компоновка | Есть ли определение; передан ли `sphere.cpp`; совпадает ли сигнатура. |
| `multiple definition of sphere_volume` | Компоновка | Не определена ли обычная функция в заголовке и в нескольких файлах; нет ли повторно включённого `.cpp`. |
| `undefined reference to main` | Компоновка/выбор входа | Включён ли файл с `main` и есть ли корректная точка входа. |

Сообщение компоновщика обычно называет символ, который он не смог найти или нашёл несколько
раз. Сравни его с объявлением и определением **символ в символ**, затем проверь список исходных
файлов команды.

## Расширения файлов не задают правила языка

`.h`, `.hpp`, `.cpp`, `.cc`, `.cxx` — распространённые соглашения. Компилятор получает язык
по типу файла/параметрам, а команда проекта решает, что компилировать. Само имя `sphere.hpp`
не делает его «более C++», чем `sphere.h`.

## Как это делают в проекте

Разделяй по смыслу, не по количеству строк. Публичный интерфейс содержит необходимые типы,
объявления и документы о требованиях; частные детали остаются в реализации. Каждый `.cpp`
должен явно включать собственные зависимости. Не включай `.cpp` через `#include` и не добавляй
один исходник дважды в список компоновки.

## Типичные заблуждения

| Заблуждение | Как на самом деле |
|---|---|
| «Заголовок — готовая библиотека, которую отдельно компилируют» | В классической модели заголовок подключается к `.cpp`; отдельной единицей обычно служит `.cpp`. |
| «`#include` создаёт определение функции» | Заголовок обычно сообщает объявление; реализация должна присутствовать в соответствующей единице компоновки. |
| «Include guard предотвратит дублирование функции во всём проекте» | Он работает отдельно в пределах одной единицы трансляции и не устраняет несколько определений из разных `.cpp`. |
| «`undefined reference` — синтаксическая ошибка» | Это чаще ошибка компоновки: тело не нашлось, файл не передан или сигнатуры расходятся. |
| «Любые два одинаковых определения допустимы, если они одинаковы» | Обычная не-inline-функция должна иметь одно определение по правилам ODR. |
| «`#pragma once` — обязательная часть C++20» | Это распространённая поддержка компиляторов, но не стандартная директива языка. |

## Ключевые термины

| Термин | Объяснение |
|---|---|
| Заголовочный файл | Файл с объявлениями и публичными типами, подключаемый через `#include`. |
| Единица трансляции | Обработанный исходный `.cpp` с включёнными заголовками, компилируемый отдельно. |
| Объявление | Описывает существование имени и его тип/сигнатуру. |
| Определение | Полностью задаёт функцию или объект; обычной внешней функции нужно одно определение. |
| Include guard | Условная директива, предотвращающая повторную обработку заголовка в одной единице. |
| Компоновка | Связывание объектных файлов и библиотек в программу. |
| ODR | One Definition Rule — правила единственного определения для сущностей программы. |
| Undefined reference | Диагностика линкера, когда определение используемого символа не найдено. |
| Multiple definition | Диагностика линкера, когда конфликтуют определения одного символа. |
