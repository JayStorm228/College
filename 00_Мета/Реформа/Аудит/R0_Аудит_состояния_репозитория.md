# 1. Краткое резюме

Репозиторий — зрелое Obsidian-хранилище на ~320 тыс. слов (метрика `word_count` экспортёра, `подтверждено прогоном`),
244 Markdown-файла, 7 учебных дисциплин колледжа старой нумерации + 5 курсов вне программы + фрагмент веб-курса.
Техническое здоровье высокое: все автоматические проверки зелёные (0 проблем), битых ссылок нет даже в строгом
режиме, 174 Mermaid-диаграммы разбираются парсером, 648 Python-блоков компилируются.

Главная проблема — **не качество текстов, а архитектура**:

1. Нет разделения на сырьё колледжа (Поток A) и каноническую учебную базу (Поток B): сырые HTML/PDF/RAR лежат
   вперемешку с выверенными лекциями, происхождение материала нигде системно не фиксируется.
2. Действуют **две несовместимые нумерации дисциплин**: репозиторий `01–07` и генеральный план `01–24`
   (`01_Технология_Разработки_ПО` ≠ ГП-01 «Операционные системы»). Любая будущая сессия без карты соответствия
   будет путать дисциплины.
3. Генеральный план (`МОДЕРНИЗАЦИЯ/02`) описывает состояние сентября, а не октября: его таблица «Исходное
   состояние» местами противоречит факту (например, ГП-04 «ситуация слабая» — при сильнейшем в базе курсе Python).
4. Отсутствует проверяемый слой «компетенция → траектория → курс → тема → практика → проект»: зависимости
   описаны прозой, prerequisites нигде не формализованы.
5. Из 24 дисциплин ГП в базе реально присутствуют ~5 (в разной степени), 3 гуманитарные дисциплины репозитория
   (04, 05, 07) вообще вне контура ГП-24 — решение об их месте не принято.

Ничего из этого не требует срочного переписывания. Требуется зафиксировать карту, утвердить модель метаданных
и отделить сырой контур — это задачи R1–R3, не R0.

# 3. Что уже сделано хорошо

1. **Техническая гигиена образцовая.** Три чекера + Mermaid-валидатор, все зелёные; единая команда проверки;
   журнал фиксирует только реально прогнанное. Такого уровня нет у большинства учебных vault'ов.
2. **Дисциплина 02 — настоящий курс «с нуля»**: 16 лекций Python с прогоняемым кодом, 47 задач с разборами,
   5 мини-проектов, карта зависимостей с курсами. Это готовый кандидат в эталон R4.
3. **Курсы К2–К4 (NumPy/Pydantic/Matplotlib)** — единый академ. стандарт, подробные разборы, 0 проблем.
   Курс C++ — крупнейший (56 заметок), с g++-аудитом примеров.
4. **Происхождение помечается там, где принято решение**: блоки «Что из материала преподавателя, а что добавлено»
   (философия), явные оговорки в 06 («не является пересказом занятия»). Практика есть — нет системы.
5. **Правила Р7/Р8** (материалы только из колледжа; понятные якоря) — архитектурно верные, приняты владельцем.
6. **Решения владельца фиксируются**, а не переспрашиваются (таблица «Не переспрашивать», карточки В8–В12).
7. **Дорожная карта** честно разводит «требование специальности / подтверждено в колледже / личное дополнение»
   и прямо оговаривает, что это не официальный учебный план. Это ровно тот стандарт честности,
   который требует реформа.
8. **Связи внутри Python-кластера плотные**: 357 межраздельных ссылок, правило приоритета дисциплин соблюдается
   (курсы ссылаются на дисциплину 02 как на первоисточник: 48+29+27+7 входящих).

# 4. Главные архитектурные проблемы

## A1. Нет границы Поток A / Поток B (критично для реформы, не для учёбы)

Сырьё и канон лежат в одних папках без системной маркировки:

- `01_Лекции/презентация занятие 11.html` (83 КБ, сырьё преподавателя) рядом с `09. Паттерны...` (канон);
- `02_Практика/Самостоятельная работа ИСС-24-1.html` (43 КБ) рядом с практиками;
- PDF-учебники (41 + 6,5 МБ) внутри учебных папок;
- `02_Курсы/Веб.rar` (5,9 МБ) — непрозрачный бинарник, нигде не описан, `требует проверки`;
- черновики с пар (`05/`, `Веб/`, Django) отличаются от канона только статусом в YAML.

YAML не имеет полей `origin`/`content_type`/`reviewed`. Маркировка происхождения — прозой в отдельных заметках.
**Пока не переделывать** — сначала утвердить модель (R1.1), затем мигрировать пилотами (RF-02, RF-03).

## A2. Двойная нумерация дисциплин (ловушка для всех будущих сессий)

| Номер | В репозитории | В генеральном плане |
|---|---|---|
| 01 | Технология разработки ПО | Операционные системы |
| 02 | Основы алгоритмизации | Архитектура аппаратных средств |
| 03 | Написание кода ИС | Информационные технологии |
| 04 | Психология личности | Алгоритмизация и программирование |
| 05 | Психология общения | Проектирование БД |
| 06 | Моделирование и анализ ПО | Стандартизация и документирование |
| 07 | Основы философии | Численные методы |

Совпадений по смыслу — ноль. Любое упоминание «дисциплина 04» без уточнения системы двусмысленно.
Нужна карта соответствия + договорённость об именовании (RF-01). Переименовывать папки в R0 запрещено —
только зафиксировать.

## A3. Нет слоя «компетенция → траектория → тема → практика → проект»

- Зависимости — прозой («Опора на дисциплину 02», таблицы в `00_Курс`). Машиночитаемого графа нет.
- Prerequisites темы нигде не формализованы (нет полей `requires`/`feeds_into`).
- «Траектория» = нарративная Дорожная карта (срочный Django-маршрут), а не модель.
- Проекты — внутрикурсовые мини-проекты; сквозного проекта через дисциплины нет.
- Матриц «тема → практика / источник / компетенция» нет (предусмотрены ГП, не начаты).

Минимальная будущая модель (предложение, не внедрение): YAML-поля `requires: [...]`, `feeds_into: [...]`
со ссылками на заметки + реестр компетенций отдельным файлом. Сначала — R3, пилоты на 1–2 курсах.

## A4. Модель понятий не построена

- Канонических понятий как сущностей нет; «Карты понятий» в `00_Курс` — таблицы прозой.
- Одни темы покрыты в нескольких местах без явного «канон vs проекция»: Git (01-Л05 + К1-Л13),
  тестирование (01-Л07 + К1-Л08), dataclass (02-Л16 + К1-Л04 + сравнения в Pydantic).
  Сейчас это управляется правилом приоритета дисциплин и перекрёстными ссылками — приемлемо,
  но при росте базы потребует реестра понятий (RF-09).

## A5. Таблица состояний ГП §2 устарела относительно репозитория

Генеральный план (v1.0, 07.10.2026) фиксирует «Исходное состояние на 06.10.2026», которое местами неверно:

- ГП-04 «Необходим курс с нуля; текущая ситуация слабая» — факт: курс Python собран (37 заметок, 71k слов),
  слаб только Django-блок. Статус `требует проверки` и ergodic пересмотра.
- ГП-13 «C++ ошибочно воспринимался как весь предмет» — уже исправлено 03.10 (курс вынесен, вводная переписана).
- ГП-10/15/17/18/19 «Изучается сейчас» — в репозитории из этого ряда есть только материалы 01≈ГП-10 и 03≈ГП-15
  (частично); ГП-17/18/19 материалами не представлены — `требует проверки` у владельца
  (возможно, материалы есть, но не переданы в базу).

ГП нельзя править в R0 (стратегический документ), но расхождения зафиксированы для сессии R3.1 (RF-08).

# 5. Главные образовательные проблемы

1. **Django — срочный провал семестра.** Дисциплина 02 (семестр 01.09–31.12.2026) имеет 1 черновик + PDF-учебник
   41 МБ. Разбор учебника (П3) и веб-курс (П4) открыты. Это единственный пункт с календарным дедлайном колледжа.
2. **Баз данных нет вообще.** Ни проектирования (ГП-05), ни SQL, ни СУБД. Тетрадь ожидается (В4).
   Для специальности «Информационные системы» — критический пробел.
3. **Нулевой фундамент системных дисциплин.** ОС (ГП-01), архитектура (ГП-02), сети (ГП-08), ТСИ (ГП-09),
   математика (ГП-22/23), численные методы (ГП-07), моделирование (ГП-12) — отсутствуют полностью.
4. **Rust используется раньше, чем введён.** Лекция 09 (паттерны) даёт примеры на Python+Rust,
   лекция 06 — пары Rust/Python, но курса Rust в базе нет (В7 не выполнен). Читатель встречает незнакомый
   язык без опоры. По §6.3 требуется либо пометка, либо опора — сейчас её нет.
5. **Тестирование — только концептуально** (01-Л07 + шаблон практики 05). Системного курса (ГП-16) нет.
6. **Веб-маршрут фрагментирован**: сырая заметка с пары + PDF 2019 года + черновик Django. HTTP/DNS/формы/JS —
   только в Дорожной карте прозой.
7. **ИИ/интеллектуальные системы (ГП-19)** — только лекция 04 (LLM в разработке) + входящее ТЗ на Rust (не ИИ).
   ML-фундамента нет — и не должно быть раньше математики/данных (верная позиция ГП §21).
8. **Сквозных проектов нет.** Каждый курс замыкается своими мини-проектами; путь
   «требования → модель → БД → код → тесты → развёртывание» нигде не проходится целиком.
9. **Гуманитарный блок вне ГП.** Дисциплины 04/05/07 (психология, философия) не входят в 24 ГП.
   Решение `требует проверки`: держать как «общеобразовательное приложение» или исключить из контура реформы.
   Удалять запрещено; нужна маркировка слоя.

# 6. Проблемы актуальности

1. **Миграция `black` → `ruff` не завершена** (новое, найдено в R0). Курс 1 учит `ruff`, но:
   - `02_Курсы/02. NumPy/02_Практика/04. Мини-проект...` — чек-лист требует `black --check` (4 упоминания);
   - `02_Курсы/03. Pydantic/00. Pydantic.md` — `uv add --dev pytest mypy black ruff`;
   - аналогичные следы в `04. Matplotlib/00. Matplotlib.md` и лекциях 03/04/06.
   Ученик получает противоречащие инструкции. Приоритет P1 (RF-15).
2. **Версии зафиксированы точечно, не системно.** Python 3.11 (5 упом.) vs 3.12 (3 упом.) vs 3.8 (1 упом.);
   ruff 0.16.10, numpy 2.4.6, pydantic 2.13.5 — только в журнале/текстах, не в манифесте. Полей
   `technology.version`/`reviewed` в YAML нет (предусмотрены реформой, не внедрены).
3. **Реестра источников нет.** 113 уникальных внешних URL, в основном официальная документация
   (docs.python.org 12, numpy.org 10, peps 6, learn.microsoft.com 5 — иерархия источников соблюдается де-факто).

# 13. Что НЕ следует менять

1. **Учебные тексты** — не переписывать, не «улучшать заодно», не мигрировать на новые метаданные.
2. **Структуру папок дисциплин и курсов** — не переименовывать, не переносить файлы (ловушка A2!).
3. **Соглашения/контракт** — не расширять до утвержденной модели R1 (иначе разъедется checker).
4. **Статусы `готово`** — не понижать массово (31 шт. без диаграмм — чинить диаграммами в М1, не статусами).
5. **Сырьё** (HTML/PDF/RAR/черновики) — не удалять, не переносить; RAR не распаковывать без владельца.
6. **CSV/оценки/историю** — не переписывать журнал и аудиты задним числом.
7. **PII в контактах** — не публиковать шире; править только по слову владельца.
8. **Ветку и историю git** — squash-ветка R0; слияние — только владельцем.

# 15. Рекомендуемый порядок дальнейшей реформы

> Согласован с `МОДЕРНИЗАЦИЯ/03` (этапы R0–R10) и не конфликтует с `00_Мета/Модернизация` (косметика формы —
> идёт параллельно, этапы 1–10).

1. **R0.2 — Карта и словарь.** RF-01 (соответствие нумераций) + фиксация словаря «канон/сырьё/курс/траектория».
   Без этого любая следующая сессия будет путать дисциплины.
2. **R1.1 — Модель метаданных.** RF-02: `origin`, расширенный `status`, `content_type`, pilot `requires/feeds_into`.
   Контракт → 2–3 пилотные заметки → обновление чекеров. Соглашения правит только эта сессия.
3. **R2.1 — Raw-контур.** RF-03: структура входящих, YAML сырья, правило «принял → зарегистрировал → не канон».
   Миграция существующего сырья — отдельными сессиями, после R2.1.
4. **R3.1 — ГП в мета-слой.** RF-08: перенос + сверка §2 с фактом + привязка ГП-номеров к папкам.
5. **R3.2 — Зависимости.** RF-07 + RF-09: минимальный граф (пилот: Python-кластер + Git).
6. **R4 — Эталоны.** Django-мост (срочно, семестр!), затем ГП-05 (БД с нуля), ГП-08+ГП-01 (сети+ОС).
   Параллельно — косметическая Модернизация этапов 1–10 (не блокирует R-серии).
7. **Позже:** R5 миграция партиями → R6 практика/проекты → R7 источники → R8 gates → R9 публичный слой.
