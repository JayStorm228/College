# 3. Формат материалов — контракт

Один и тот же формат используется в дисциплине 02 и во всех курсах. Новые материалы пишутся
**только так** — иначе курс перестаёт быть связным.

| Вид заметки | Обязательные секции |
|---|---|
| **Лекция** | `> [!abstract] О чём лекция` → теория → `# Как это делают в проекте` → `# Типичные заблуждения` (таблица) → `# Проверь себя` (5–6 вопросов + свёрнутые ответы) → `# Практика` → `# Опора на дисциплину 02` → `# Связи с другими темами` |
| **Практика** | `> [!abstract]` → `> [!important] Как работать с задачей` → `## Задача N` ★☆☆/★★☆/★★★ → свёрнутый разбор `> [!example]- Разбор` (идея → код → вывод → что важно → типичная ошибка → границы) → `# Что запомнить из практики` → `# Связи с другими темами` |
| **Мини-проект** | `> [!abstract]` → результат → требования (таблица с ссылками на лекции) → `# Как идти` → **пример-аналог из другой темы** под спойлером (без стартовых файлов!) → чек-лист `☐` → «Если застрял» → «Что сдать» → типичные ошибки → связи |
| **Обзор курса** | `> [!abstract] О чём курс` → «Как проходить» → `# Программа` (таблица лекция → тема → практика) → маршрут практик → `# Опора на дисциплину 02` → «Что понадобится» → «Что вы сможете» → связи |

Правила, которые легко нарушить:

- **Все числа — только из фактического прогона** в окружении (версии в §7). Ничего «по памяти».
- В задачах и примерах **не использовать `random`**: данные заданы в условии или вводятся.
- В таблицах экранировать пайп: `X \| None`, иначе markdown ломается.
- Открытые задачи в учебной заметке обозначаются `☐` (в мини-проектах — чек-лист),
  а не `- [ ]`: при `status: готово` это ошибка проверки.
- Практики блока Б не переписывать (решение владельца): архивный код — не эталон,
  но и не переписывается.
- Правки в чужие дисциплины — только чтобы починить ссылку, ведущую в них.

**Ловушки, проверенные на практике:**

- `.git` в песочнице может откатиться к старому клону (`6284155`). Поэтому **все git-команды —
  одним вызовом**: точечный `git fetch origin "refs/heads/<ветка>:refs/remotes/origin/<ветка>"`
  (обычный `git fetch origin` тянет только `main`), затем `git reset --mixed <ref>`,
  `git status --porcelain`, `git add -A`, commit, push. Пуш — **только в `arena/01a0dabe-college`**.
- Если откат случился **внутри** вызова с коммитом, коммит может лечь на устаревшего родителя
  (например на `6284155`) — push отклонится с `non-fast-forward`, хотя ветка выглядит «своей».
  Лечение (проверено 26.09.2026): `git fetch` ветки → `git reset --mixed refs/remotes/origin/<ветка>`
  → `git status --porcelain` и `git diff --stat` (убедиться, что в diff только ожидаемое)
  → `git add -A` → commit заново → push. Рабочая копия при этом не теряется.
  Признак проблемы заранее: `git merge-base --is-ancestor refs/remotes/origin/<ветка> HEAD`
  отвечает «НЕ предок».
- Владелец правит файлы **прямо на GitHub**: после fetch нужно перенести его версии
  (`git checkout <его-коммит> -- <файл>`) **до** `git add -A`, иначе правка потеряется.
- Чекер: python-блоки внутри врезок (`> `) снимаются автоматически; `- [ ]` при `status: готово` —
  ошибка; `type:` должен быть из контракта [[Соглашения]]; вложенные репозитории не проверяются.
- Крупные тексты писать `write_file`, правки — `edit_file`; после записи проверять смешение
  алфавитов (латинские буквы внутри кириллических слов) и парность секций grep-ом.
- Если правишь несколько якорей одним скриптом — падение `assert` отменяет часть замен:
  прогонять целиком и сверять результат.

# 8. Как выгрузить работу в `main`

На момент передачи `main` — прямой предок ветки, поэтому слияние возможно **без конфликтов
и без решения спорных мест**. Два равнозначных способа:

**Вариант А — fast-forward командой (быстрее всего):**

```bash
git fetch origin main arena/01a0dabe-college
git checkout main
git merge --ff-only arena/01a0dabe-college
git push origin main
```

**Вариант Б — через pull request:** ветка `arena/01a0dabe-college` → `main`, в описании
сослаться на этот файл и на [[Журнал_изменений]] (проходы 11–18 — там весь состав).
**Решение владельца 26.09.2026: PR не открывать** — владелец сливает сам, поэтому выбран
вариант А (fast-forward). Если понадобится всё же оформить PR — ветка уже запушена
и готова, ничего дополнительно готовить не нужно.

После слияния работа по курсам продолжается в новой ветке от `main`; тогда `02_Курсы`
и собранная дисциплина 02 доступны сразу, а этот файл остаётся точкой входа.

**Проверка перед слиянием** (одной командой):

```bash
git fetch origin main && git merge-base --is-ancestor origin/main HEAD \
  && echo "fast-forward возможен" || echo "нужен merge: сверить конфликты"
```
