# Варианты хранения архива электронных учебников

> [!important] Выбран отдельный репозиторий-библиотека; миграции пока нет
> Владелец выбрал отдельный публичный репозиторий для централизованной библиотеки учебников, с папками по темам и общим каталогом с ID, названием, автором, годом, источником, статусом прав и ссылками. Учебные материалы College смогут ссылаться на устойчивые записи каталога. Публично размещать PDF можно только при наличии права на распространение; для остальных книг в публичном каталоге остаются метаданные и ссылки на легальные источники, а сами копии хранятся закрыто. Текущие файлы **сохранить на прежних местах**. Пока ничего не перемещать, не удалять, не добавлять в `.gitignore`, не переписывать историю и не включать LFS.

В текущем репозитории учтены два PDF; это не полный будущий фонд — владелец планирует собрать в отдельной библиотеке все свои учебники. Перед миграцией повторно построить инвентарь: список и размеры могут измениться. Размеры выше указаны на **01.10.2026** и не являются постоянными.

## Варианты

### 1. Оставить книги рядом с курсами — текущее состояние

PDF лежат в папке дисциплины или курса, где на них есть ссылка и где ими пользуются.

**Плюсы**

- книга находится рядом с материалом, который по ней создаётся;
- существующие ссылки и локальная работа в Obsidian не меняются;
- вся база клонируется и открывается автономно;
- не нужна отдельная инфраструктура или авторизация.

**Минусы**

- бинарные файлы увеличивают обычный Git-клон (сейчас около 47,33 МиБ только эти две книги);
- изменения PDF плохо сравниваются как текст, а предыдущие версии занимают место в истории;
- большие библиотеки могут раздувать репозиторий.

**Когда подходит:** если библиотека небольшая и важнее надёжно открыть материалы вместе с базой, чем минимизировать её размер.

### 2. Собрать централизованную папку книг внутри этого репозитория

Например, `Учебники/` в корне с тематическими подпапками, коротким каталогом и ссылками из курсов. Физические PDF по-прежнему отслеживаются Git.

**Плюсы**

- единый понятный архив и единая точка инвентаризации;
- курс не определяет физическое место файла; учебник можно использовать в нескольких направлениях;
- остаются автономность клона и история Git.

**Минусы**

- размер репозитория и история бинарных файлов почти не уменьшаются;
- нужно исправить все относительные ссылки и проверить их после перемещения;
- читателю иногда придётся идти из курса в центральный каталог и обратно.

**Когда подходит:** если владельцу важнее порядок и централизованный поиск, а размер Git приемлем.

### 3. Отдельная локальная или облачная библиотека вне Git

Хранить оригиналы на диске или в синхронизируемом облачном/сетевом хранилище; в репозитории оставить каталог с автором, названием, годом, назначением и способом открыть книгу. Возможны системные ссылки, которые владелец подставляет на своём устройстве.

**Плюсы**

- Git-клон становится меньше, история не содержит новые версии PDF;
- можно выстроить резервное копирование и единые папки библиотеки;
- легче отдельно управлять большой коллекцией.

**Минусы**

- Obsidian-копия базы больше не гарантирует наличие самого учебника;
- локальные абсолютные пути зависят от устройства и не работают у других читателей;
- внешняя ссылка может требовать доступа, сети или оплаты; доступность и резервные копии нужно контролировать;
- при случайной чистке базы книгу легко потерять, если в архиве нет проверенной второй копии.

**Когда подходит:** если у владельца уже есть надёжное синхронизируемое хранилище и резервное копирование, а автономность Git-клона не обязательна.

### 4. Git LFS

Git хранит в истории указатели на бинарные файлы, а сами объекты — в LFS-хранилище.

**Плюсы**

- книги остаются привязаны к версиям базы и путям в репозитории;
- обычные Git-объекты для PDF заменяются небольшими pointer-файлами;
- при настроенном LFS книга выглядит в рабочем дереве почти как обычный файл.

**Минусы**

- LFS нужно включить у всех, кто клонирует репозиторий; без загрузки LFS-объектов вместо книги останется указатель;
- действуют лимиты хранения и трафика хостинга, иногда требуется оплата;
- если PDF уже попадали в Git, простое добавление `.gitattributes` не удаляет старые объекты из истории; для реального уменьшения истории нужна отдельная миграция с переписыванием и force-push;
- после переписывания истории остальным клонам требуется отдельная инструкция и, часто, новое клонирование.

**Когда подходит:** если книга должна быть частью версии проекта, но есть готовая политика LFS и все пользователи готовы поддерживать её.

### 5. Отдельный репозиторий-библиотека или подмодуль

Создать отдельный Git-репозиторий для книг, а в базе оставить каталог и, при необходимости, подмодуль.

**Плюсы**

- история учебников и история конспектов изолированы;
- можно разделить доступ, резервирование и правила обновления;
- основная база легче, если книги не подтягиваются в обычный клон.

**Минусы**

- нужны второй репозиторий, отдельные права доступа и ещё один процесс резервирования;
- подмодули требуют дополнительной команды при клонировании и обновлении;
- доступность библиотеки зависит от отдельного Git-сервера и его квот;
- это может усложнить простую учебную базу сильнее, чем оправдывает две книги.

**Когда подходит:** если библиотека станет большой и ею будут управлять независимо от конспектов.

### 6. Игнорировать файлы Git, оставив их только на одном устройстве

PDF лежат в рабочей папке владельца, но Git их не отслеживает; в хранилище остаётся только запись о том, где их искать.

**Плюсы**

- Git-репозиторий и новые клоны заметно легче;
- не нужен LFS и не переписывается история, если файлы никогда не были в коммитах.

**Минусы**

- новый клон не содержит книг, а заметка может вести в никуда;
- потеря диска, случайная очистка или переустановка системы могут уничтожить единственную копию;
- синхронизация и резервное копирование целиком ложатся на владельца;
- если файл уже коммитился, `.gitignore` не уберёт его из старой истории.

**Когда подходит:** только если владелец осознанно принимает хранение вне Git и уже проверил независимую резервную копию.

## Сравнение по критериям

| Вариант | Уменьшает новый Git-клон | Открывается вместе с обычным клоном | Сложность поддержки | Риск потери доступности |
|---|---|---|---|---|
| 1. Рядом с курсами | Нет | Да | Низкая | Низкий |
| 2. Централизованная папка в Git | Нет | Да | Низкая/средняя из-за ссылок | Низкий |
| 3. Внешняя библиотека | Да | Нет | Средняя | Средний/высокий без резервов |
| 4. Git LFS | Обычно да для обычного Git-клона; LFS всё равно загружает объекты | Только с LFS | Средняя/высокая | Средний: квоты и настройка |
| 5. Отдельный репозиторий | Да, если не клонировать библиотеку | С подмодулем — по настройке | Высокая | Средний |
| 6. Локально, вне Git | Да | Нет | Низкая технически, высокая лично | Высокий без резерва |

## До публикации библиотеки

- **Текущее расположение не менять.** Ничего не удалять и не перемещать, в том числе существующую копию PDF Django.
- Для каждого файла проверить разрешение или лицензию на публичное распространение. Неавторизованные PDF не выкладывать: для них в публичном каталоге оставить метаданные и ссылку на легальный источник, а копию хранить закрыто.
- Будущий отдельный репозиторий организовать по темам и дополнить единым реестром с устойчивым ID, названием, автором, годом, источником, статусом прав и permalink. Учебные заметки College должны ссылаться на запись каталога, а не на случайное локальное имя файла.
- После того как владелец прикрепит библиотеку/книги и подтвердит режим доступа, повторно построить инвентарь, проверить резервные копии и доступность ссылок.
- Историю Git не переписывать; Git LFS не включать без отдельного согласования последствий.

**Решение владельца:** отдельная публичная библиотека с гибридной структурой «папки по темам + общий каталог»; все учебники должны быть учтены. Не подтверждены только права на публичное распространение каждого файла и фактический состав будущей библиотеки. Текущие PDF не перемещались.
